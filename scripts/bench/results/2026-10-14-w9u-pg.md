# Sync benchmark: w9u-pg (2026-10-14)

- v4: meerschaum 4.1.4 (reference venv)
- v5: `mrsm` release build (Meerschaum v5.0.0-a1), façade at c4425369 + working tree
- Python 3.14.8, Linux x86_64, 40 CPUs
- repeats: 5 (1 extra warm-up per case up to 100k; 1M uses at most 2); the table shows the median seconds
- `py` columns are timed around the call in-process; `cli` columns are whole-process wall time (startup included)
- `x` columns: v5 time / v4 time for the same style (`py`, `cli`). Below 1.00 is faster; **bold** marks a regression (> 10% slower)
- `v5pyp` (when run): the façade with `MRSM_CORE=python`, for reference only (no `x`); `lat_*` cases are per call, in milliseconds

## Context (wave 9 task U, hand-written)

- Run: `python scripts/bench/run.py --label w9u-pg --backends postgis --sizes 10k,100k --cases sync,inc,filter_existing,latency --repeats 3 --impls v4py,v5pyp,v5py --pg-schema w9u_bench`, then `--backends sqlite --sizes 10k --cases latency --repeats 5`. CLI columns were not run: `target/release/mrsm` predates this wave.
- Before task U, the façade re-resolved cross-pipe `{{ Pipe() }}` templates on every parameter read. A `{{ Pipe() }}` chain of 8 derived pipes on postgis then cost, in rust mode, `get_rowcount` 107 ms, `get_sync_time` about 300 ms and `get_data` about 450 ms per warm call on the leaf (python mode: 1.8 / 2.1 / 10 ms). The 8-pipe dump took 3.2 s against 0.65 s. See `crates/meerschaum-py/PERF.md`, "Wave 9 (task U)".
- `lat_template_get_sync_time` covers that path: a new `Pipe` per call for the leaf of the 3-pipe chain.

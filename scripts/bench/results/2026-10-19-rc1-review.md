# rc1 validation and performance review

**Performance is accepted for the rc1 testing release with the known limitations below. Raw timing thresholds did not all pass, and no runtime optimization was applied. This is an explicit rc1-only disposition, not final 5.0.0 acceptance.**

These preparatory measurements compare released Meerschaum 4.1.4 with local v5 `5.0.0a1` acceptance artifacts on Python 3.14.8 / Linux x86_64. The subsequent rc1 change is version metadata only; these measured artifact identities and samples remain unchanged. rc1 packaging and exact-commit release checks establish separate final artifact provenance.

## Completed validation

- Correctness: **2,759 passed, 97 skipped, no failures**. Skip reasons match the reviewed baseline; no stale-binary skips were added.
- Upgrade and transition: all **28 setup/required stages** passed, including all 14 required stages. Coverage includes an actual offline v4-to-v5 wheel upgrade, SQLite behavior, jobs and compose, plugin execution and dependency provenance, DuckDB continuation/reopen, and equal PostGIS/GeoPackage control/candidate snapshots. Expected behavior differences remain classified individually.
- Main benchmark: **146 result rows, 438 raw measurements**, with three repeats for every row, including one-million-row cases. Startup, PostGIS, TimescaleDB and SQLite coverage is complete. Of 80 matched v5/v4 comparisons, one exceeded the 10% slowdown threshold. None of 14 mapped historical comparisons exceeded the 20% drift threshold; historical coverage is limited to cases that actually have a counterpart.
- Supplemental DuckDB: each of the original and three-extra-repeat confirmation runs completed **18 writer cells, 18 post-exit verifiers and two preflights**, with accepted identity, row/value, sync-count, cross-API persistence and owned cleanup evidence. Four timing flags remain confirmed below.

The [main benchmark](2026-10-19-rc1.md) retains its original threshold failure; the [raw measurements](2026-10-19-rc1.json) remain unchanged.

## Known TimescaleDB fresh-object limitation

The affected case creates a new Python `Pipe` for every `get_sync_time()` call on the warmed 50-row TimescaleDB fixture. Three extra uninstrumented repeats confirmed the original flag:

| Measurement | v4 median | v5 median | v5/v4 |
| --- | ---: | ---: | ---: |
| Main run | 4.726 ms | 5.608 ms | 1.1866 |
| Three-repeat confirmation | 4.577 ms | 5.378 ms | 1.1750 |

The confirmed increase is **0.801 ms per fresh-object call, or 17.5%**. It remains above the threshold and is **not fixed**. Reused-Pipe Timescale sync-time calls and the PostGIS/SQLite fresh-object comparisons were not flagged in these runs; this bounds the observed case, not production frequency or tail latency.

Separate phase sampling and method-only profiles identify construction and metadata/parameter hydration work, but do not account for every microsecond of the uninstrumented difference. No repeated pool creation or additional column-catalog fetch was demonstrated. Profile timings are diagnostic and do not replace the confirmation.

This precisely scoped submillisecond increase is explicitly accepted **for the rc1 testing release only**, with public semantics and correctness retained. Tight loops that repeatedly construct fresh Pipes for metadata polling are affected. Before final 5.0.0, revisit constructor/hydration/bridge costs with a supported semantics-preserving optimization and unchanged comparison, or record an explicitly reviewed final-release limitation. This rc1 exception does not turn the raw threshold result into a pass or waive other regressions.

| ---: | --- | ---: | ---: | ---: | ---: | --- |
| 1k | first Pipe open | 54.046174 / 84.930943 | 1.5715 | 52.068856 / 82.794466 | 1.5901 | yes |
| 100k | first Pipe open | 55.421051 / 79.715839 | 1.4384 | 56.849757 / 75.491673 | 1.3279 | yes |

| 1M | warm SELECT | 1.959903 / 2.435390 | 1.2426 | 2.084383 / 2.234827 | 1.0722 | no |

First Pipe open occurs **before any data sync, while the target does not exist**: `get_rowcount()` followed by `exists()`, including first native Pipe context for v5, with construction outside the timer. The labels identify prepared input frames, not existing table cardinalities or COUNT queries over those rows. The confirmed extra times are approximately **30.73 ms, 18.64 ms and 49.06 ms** for those three preparations; this variation does not demonstrate linear row-scan scaling. Timed 1k get_data adds approximately **3.98 ms**.

Both original warm-SELECT flags were unconfirmed: their extra-repeat ratios are below 1.10, and there are no new timing flags. The original samples are retained. Separate diagnostic profiling completed for the four reproduced cases and does not replace these uninstrumented measurements.

Original-run fresh-sync medians and whole-writer peak RSS show the workload tradeoffs alongside those latency flags:

| Rows | v4 fresh sync | v5 fresh sync | v4 writer peak RSS | v5 writer peak RSS | RSS change |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1k | 1.590647 s | 0.377059 s | 294,785,024 bytes | 271,351,808 bytes | −7.9% |

RSS includes the writer's complete workload and validation, rather than isolating the sync call. Confirmation repeated the 1M memory tradeoff: **962,781,184 bytes (918.180 MiB) v4 versus 1,287,778,304 bytes (1,228.121 MiB) v5**, about **+309.94 MiB / +33.76%**. Fresh-process verifier RSS was roughly equal. These peaks include imports, prepared frames, validation and operations; they are not per-sync allocations, proof of a leak, or a bound on concurrent writers. Faster fresh sync coexists with this higher measured 1M writer peak.

### Completed diagnostic attribution and rc1 disposition

The separate diagnostic completed **six writers, six post-exit verifiers, two preflights and eight valid scoped profiles**, with accepted correctness, identity and owned cleanup evidence. It profiled the original missing-target expression at each prepared size and the timed 1k get_data call. Warm SELECT remained unprofiled. The one-repeat diagnostic timings are kept separate from both uninstrumented runs.

Cold metadata initialization/hydration dominates the observed first-Pipe boundary. Instance-table readiness is retained as successful connector/process state; it is not inherently repeated for every Pipe sharing an initialized connector. Both versions perform metadata initialization through their respective implementations. Transport-anchor preparation alone does not account for the measured difference, and the profile does not establish a connection leak or an exact SQL-query count.

The small read immediately follows native sync. v5 deliberately invalidates Python column/layout caches after that sync to prevent stale schema, dtype and parameter state; the next read can reflect the columns again. v4 may retain its column cache when no schema DDL occurred. Profiles and source establish this freshness difference, but do not allocate the full uninstrumented **3.98 ms** increase to reflection. Simply retaining the old cache would undo an existing correctness repair. A safe final-schema handoff requires proof before relaxing invalidation.

Attribution remains partial: cumulative spans overlap, profiling perturbs the two stacks differently, and some native/blocking-thread work is opaque. The profiles neither partition every millisecond nor provide a complete wire-query census.

The **four confirmed timing limitations and large-writer memory tradeoff are explicitly accepted for rc1 testing only**, with public semantics, freshness and persistence retained. Short-lived processes, small reads immediately after sync, and memory-limited or concurrent large writers may be materially affected. Bulk speedups do not cancel those costs. No runtime change was applied to make these thresholds appear to pass.

Before final 5.0.0, investigate cold instance-table/catalog readiness, a verified schema handoff/cache-invalidation path, and large-frame memory. Preserve public behavior and freshness/persistence, then repeat unchanged comparisons after any supported optimization or explicitly review a final-release limitation. The TimescaleDB exception above remains separately scoped. This disposition is not a production latency SLO, p99 estimate or universal backend/platform guarantee.

## Interpretation limits

Main results compare complete installed environments, not Meerschaum algorithms in isolation. The reviewed dependency versions intentionally differ:

| Dependency | v4 environment | v5 environment |
| --- | --- | --- |
| pandas | 3.0.0 | 3.0.6 |
| NumPy | 2.4.2 | 2.5.4 |
| Polars | 1.44.1 | 2.0.0 |
| PyArrow | 23.0.0 | 26.0.0 |
| SQLAlchemy | 2.0.51 | 2.1.5 |

Both main interpreters are Python 3.14.8 and use psycopg 3.3.6. The supplemental DuckDB run instead uses one selected interpreter and identical explicit dependency paths for both versions, with the public Python DuckDB transport and 40-thread settings. First-open measurements use fresh processes and owned files; OS caches are not dropped. RSS is whole-worker peak, including validation. These results establish neither a production service-level objective nor a universal speedup, and the rc1 acceptance retains the failed thresholds and documented limitations.

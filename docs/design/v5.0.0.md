# Meerschaum v5.0.0 Design Spec

**Status:** Draft. The decisions are agreed; implementation has not started.
**Branch:** `v5` (cut from `main` at v4.1.4)
**Date:** 2026-10-11

## 1. Theme

v5 starts moving Meerschaum's core from Python to **Rust**. It ships a Rust kernel, a Rust CLI and shell, and Rust plugins, while keeping the Python package and Python plugins fully supported. Rust becomes a first-class way to use Meerschaum.

v5 also replaces the lap-based syncing engine with a **dependency-aware Syncing Engine**. The new engine:

- understands the pipe graph (parents and children);
- decides which syncs need to run and how wide their bounds must be;
- runs independent branches in parallel;
- makes progress visible as a Gantt chart in the terminal and in the web console.

Polars is already the preferred DataFrame format. v5 uses the same Arrow/Polars memory model for everything that crosses a language boundary.

## 2. Goals and non-goals

### Goals (all ship in 5.0.0)

1. **Syncing Engine and pipelines.** A Rust graph, planner and executor; a `Pipeline` API; `pipe.sync(parents=..., children=...)`; a dirty-range ledger; run history; a Gantt chart and DAG view in the CLI and in Dash.
2. **Rust CLI and shell.** `mrsm` is a native binary. It runs Python plugins and actions through a pool of Python worker processes.
3. **Rust plugins.** A stable C-ABI plugin interface that exchanges data through the Arrow C Stream Interface.
4. **Rust data kernel.** Dtype enforcement, the `filter_existing` diff and serialization are implemented in Rust and exposed to Python through PyO3. Geometry is stored as GeoArrow WKB, with GeoPolars as the preferred geometry frame.

### Non-goals for 5.0

- Porting the FastAPI server or the Dash console to Rust. Both stay Python and use the Rust kernel.
- Rust-native connectors for SQL and other instances. They are planned for v5.x. In 5.0, connectors stay Python, and the engine and kernel call into them.
- WebAssembly plugins (v5.x, see §6.5).
- New `SQLConnector` flavors (v5.x roadmap, separate from the engine):
  - **Turso**, the Rust SQLite rewrite, as a `sql:` flavor alongside `sqlite`, gated on its multi-process WAL support leaving experimental status.
  - **DuckDB**, reintroduced. DuckDB allows one read-write process per file, which suits analytics instances better than instances shared by several jobs.

  Once either is an instance flavor, it holds engine state automatically through the internal pipes in §5.7.
- Removing `attempt_import` (see §8).

## 3. Decision log

| # | Decision | Chosen | Alternatives considered |

| D2 | How the Rust CLI runs Python | A pooled **Python worker process** speaking Arrow IPC over a Unix socket. When Python is the host, the kernel runs in-process through PyO3. | Embedding CPython in the binary; keeping a Python host |

| D7 | API and Dash | Stay **Python** in 5.0 | Port the API to axum |

## 4. Architecture

### 4.1 Workspace layout

```
crates/
  meerschaum-core/      # Pipe keys, parameters model, dtype system, SuccessTuple/SyncResult, config
  meerschaum-kernel/    # Arrow/Polars: dtype enforcement, diff (filter_existing), serialization, GeoArrow
  meerschaum-engine/    # Graph, planner, executor, ledger, run events
  meerschaum-plugin/    # Stable plugin API (C ABI vtable, macros, Arrow C Stream helpers)
  meerschaum-cli/       # `mrsm` binary: clap CLI, reedline shell, Python worker pool, Gantt TUI
  meerschaum-py/        # PyO3 bindings -> `meerschaum._core` (built into the `meerschaum` wheel)
meerschaum/             # The existing Python package (mixed maturin project)
```

Who hosts what:

| Host process | Kernel and engine | Python plugins and connectors | Rust plugins |
|---|---|---|---|
| Python (library, API server, Dash, jobs started from Python) | In-process via `meerschaum._core` | Called directly | `dlopen` from Rust, inside the Python process |
| Rust (`mrsm` CLI and shell, Rust daemons) | Native | **Worker pool** (D2) | `dlopen` |

### 4.2 Python interop (D2, D3)

- **`meerschaum._core`** is the PyO3 extension module. Python's `Pipe`, `enforce_dtypes`, `filter_existing` and the engine entry points call into it. DataFrames cross the boundary without copying through the Arrow PyCapsule interface (`__arrow_c_stream__`). Pandas inputs are converted at the boundary.
- **The Python worker** (`python -m meerschaum.worker`) is started by the Rust host and runs inside the right plugin venv. It speaks a small RPC protocol:
  - control messages are JSON or msgpack;
  - data is Arrow IPC streams over a Unix domain socket (named pipes on Windows);
  - shared memory is an optimization for later.
  - Operations: `fetch`, `sync`, `register`, `action`, `get_data`, `get_sync_time`, … (one for each `SyncExecutor` and connector method the engine needs).
- **Pool policy.** Workers are pooled per venv, sized by `system.engine.python_workers`. A worker crash fails only the node it was running.
- Running each worker as a separate process removes GIL contention with the parallel executor. Free-threaded CPython is not needed.

### 4.3 CLI and shell (goal 2)

- **clap** is the single source of truth for core arguments (ported from `_internal/arguments/_parser.py`). A generated JSON schema of the argument spec is read by the Python argument parser, so `parse_arguments` (still used by the API's actions route and by jobs) stays in sync.
- The **shell** uses `reedline` and keeps today's behavior: switching instances, the `:` flags that apply to a whole chained command, `+` action chaining, and history.
- **Plugin action manifests.** `@make_action`, `add_plugin_argument` and the action docstrings are collected into a cached manifest when plugins are installed or set up (`mrsm setup plugins`) and when they change. As a result `--help`, tab completion and argument validation never start Python. Python starts only when a Python action actually runs.
- **Distribution (D8).** `pip install meerschaum` pulls in `meerschaum-cli`, which installs the `mrsm` binary. The binary finds the Python environment that installed it so it can start workers. A binary installed with `cargo install` asks for a Python interpreter (`MRSM_PYTHON` or config) the first time Python is needed.

## 5. Syncing Engine (goal 1)

### 5.1 The pipe graph

- **Node.** `(instance_keys, connector_keys, metric_key, location_key)`. Edges may cross instances.
- **Edges** come from three sources, which are combined and deduplicated:
  1. `parameters['parents']` / `parent` (edge parent → self);
  2. `parameters['children']` / `child` (edge self → child);
  3. `{{ Pipe(...) }}` references found in SQL definitions. These are implicit edges, extracted statically and without running anything, by parsing the template the same way `replace_pipes_syntax` (`utils/pipes.py:217`) does.

  Today `parents` and `children` are declared independently (`core/Pipe/_attributes.py:856`, `:924`), and nothing records the reverse direction. The graph builder must look at both sides.
- `reference` / `references` only means parameter inheritance. It is **not** a data edge.
- A **cycle** is a planning error. The message prints the cycle path.
- The graph is built by `meerschaum-engine` from a batch `fetch_pipes_keys` (dict form, so all parameters come back in one round trip) and cached for each run.

### 5.2 Selection API (D4, D5)

```python
import meerschaum as mrsm

pipe = mrsm.Pipe('sql:main', 'daily_rollup', instance='sql:main')

pipe.sync()                        # v4 behavior, unchanged
pipe.sync(parents=True)            # sync all ancestors in dependency order, then this pipe
pipe.sync(parents=1)               # direct parents only
pipe.sync(children=True)           # sync this pipe, then propagate to all descendants
pipe.sync(parents=True, children=True)

pipeline = mrsm.Pipeline(pipe, parents=True, children=False)   # or mrsm.Pipeline([p1, p2, ...]) / tags=...
plan = pipeline.plan(begin=None, end=None)   # dry run; no data movement
print(plan)                                  # table: node | action | bounds | chunks | reason
run = plan.execute(workers=8)                # or pipeline.run(...)
for event in run.events():                   # live event stream (§5.6)
    ...
run.result                                   # SuccessTuple-compatible
```

CLI:

```
mrsm sync pipes -c sql:main -m daily_rollup --parents [N] --children [N]
mrsm plan pipes ...             # print the plan only (like `terraform plan`)
mrsm show graph ...             # ASCII DAG of the selection
mrsm show runs [--last N]       # run history; `show run <id>` renders the Gantt chart
```

A `Pipeline` is a **selection**: a set of target pipes plus traversal depths. It is not stored as its own entity. Saved pipelines are just jobs whose sysargs include `--parents` / `--children`.

### 5.3 Planner

The planner gives every node in the selection one action:

| Action | When | Bounds |
|---|---|---|
| `skip` | The node is up to date: its watermark ≥ the lowest watermark among its parents, there are no unconsumed dirty ranges, and its definition hash is unchanged | none |
| `incremental` | Parents have advanced past this node | `[own watermark − backtrack, min(parent watermarks))` |
| `backfill` | Unconsumed dirty ranges from parents (§5.4) | The dirty ranges, mapped onto this node's chunk grid |
| `rebuild` | The definition hash changed (SQL text, `fetch` config, dtypes) | Full range. Needs `--yes` / `force` unless configured otherwise. |
| `root` | The node has no parents in the selection | v4 semantics (`begin=''` = sync time minus backtrack) |

- **Watermark.** A pipe's watermark is its sync time (`get_sync_time`). It is derived on demand (not persisted) and cached in memory for the duration of a run.
- **The capping rule.** Inside an engine run (`Pipeline`, `parents=`, `children=`, continuous mode), a child is never synced past `min(parent watermarks)`. This prevents half-built aggregates. A bare `pipe.sync()` keeps v4 behavior and never caps (R1).
- **Pipes without a datetime column** cannot have a watermark. Any change in a parent triggers a full re-sync of the child, which relies on its own `filter_existing`.
- **Pipes with an integer datetime axis** behave the same way on the integer grid.

### 5.4 Dirty-range ledger

This mechanism lets the engine know "how wide the bounds need to be" without running a full verify.

- After each successful sync, the instance records the **changed intervals**. These are the min/max of the datetime column over the rows that were inserted, updated or upserted (the delta that `filter_existing` already computes), bucketed onto the epoch-aligned chunk/partition grid (`get_chunk_bounds(align=True)`, `verify.chunk_minutes`).
- Each ledger entry carries a **monotonically increasing sequence number** for its pipe.
- Each **edge** stores a cursor: the last parent sequence number the child has consumed. This works like Kafka consumer offsets. During planning, the unconsumed entries are combined into a set of intervals and drive `backfill`.
- **Mapping parent ranges onto a child.** By default this is the identity mapping on the datetime axis, widened to the child's chunk grid. Each edge can override it with `lookback` / `lookahead` (for example, a 7-day rolling window widens each range by 7 days):

  ```yaml
  parents:
    - {connector: sql:main, metric: raw_events, lookback_days: 7}
  ```

- **Compaction.** Entries that every child has consumed get pruned.
- `Pipe.verify()` writes ledger entries for the chunks it repairs, so repairs flow downstream automatically.

### 5.5 Executor and scheduling

- **Dynamic ready queue** (Kahn's algorithm) on tokio. A node is *ready* when all of its in-selection parents have succeeded.
- **Concurrency limits:**
  - the global worker count;
  - per-connector semaphores (`system.engine.limits.connectors['sql:main'] = 4`);
  - per-instance semaphores;
  - the Python worker pool size.
- **Priority:** the critical path goes first. Each ready node's priority is its *upward rank*: its expected duration plus the largest upward rank among its children (the critical-path / HEFT list-scheduling heuristic). When workers are scarce, the longest remaining chain starts first, which minimizes the total time span.
- **Durations** are an exponentially weighted moving average (EWMA) per `(pipe, action)` from run history, with a configurable default for pipes that have never run.
- **CPM output.** The plan also records the earliest/latest start and finish and the slack for each node. These drive the planned bars and critical-path highlighting in the Gantt chart.
- **Overlapping chunks (precedence relationships).** In 5.0, edges at the pipe level are finish-to-start. During `backfill`, the executor may also plan at **(pipe, chunk)** granularity, so a child can start chunk *k* once every parent has finished chunk *k* (start-to-start with a lag of one chunk). This is a flag (`system.engine.chunk_pipelining`); see open question Q4.
- **Failures:**
  - A node failure marks every descendant `upstream_failed`. Independent branches keep running (like `make -k`).
  - Each pipe can have a retry policy (`parameters['retry'] = {max: 3, backoff_seconds: 30}`).
  - `mrsm sync pipes --resume <run_id>` re-plans only the nodes that failed or never ran.
- **Leases.** Before running a node, the executor acquires a per-pipe lease (§5.7). Two jobs therefore never sync the same pipe at the same time. If the lease is held elsewhere, the node waits or is deferred.
- **Continuous mode (replaces laps).** `--loop` starts a long-running engine:
  - root nodes run on their own cadence (`parameters['schedule']`, or `--schedule` / `--min-seconds`);
  - a child is triggered when a parent's watermark advances or new ledger entries appear, with debouncing (`system.engine.debounce_seconds`).

  The v4 lap engine stays available as `--engine laps` throughout 5.x, is deprecated, and is removed in 6.0.

### 5.6 Results, events and run history

- **`SyncResult`** is a subclass of `tuple` and stays `(bool, str)`-compatible, so existing `SuccessTuple` code keeps working. It adds structured fields: `inserted`, `updated`, `upserted`, `deleted`, `changed_intervals`, `duration`, `begin`, `end`. Today the counts exist only inside message strings (`connectors/sql/_pipes.py:2298`, `:2910`).
- The **event stream** emits one typed event per transition: `run_started`, `node_planned`, `node_started`, `chunk_started`, `chunk_finished`, `node_finished{SyncResult}`, `node_failed{error, traceback}`, `node_skipped{reason}`, `run_finished`. The CLI and Dash both render from this stream.
- Events, run history and every other piece of engine state persist as described in §5.7.

### 5.7 Engine state

**Principle.** The engine adds no database files to the root directory. Every piece of durable state lives **on the instance, as internal pipes**. This follows the existing pattern of `InstanceConnector.get_users_pipe()`, `get_tokens_pipe()` and `get_plugins_pipe()`: `mrsm.Pipe('mrsm', <name>, instance=self, target='mrsm_<name>', temporary=True, static=True, ...)`. Every SQL access goes through `SQLConnector`.

**Inventory:**

| State | Persisted? | Where |
|---|---|---|
| Graph (edges) | No. Derived from pipe parameters and `{{ Pipe() }}` references. | Memory, built per run from a batch `fetch_pipes_keys` |
| Watermarks | No. Derived from `get_sync_time()`. | Memory and the existing pipe cache |
| Definition hash | Yes | `mrsm:engine_state` pipe (primary key `pipe_id`, upsert) |
| Dirty-range ledger | Yes. Shared across processes and machines. | `mrsm:engine_ledger` pipe (datetime `created`, ids `pipe_id`, `seq`; columns `begin`, `end`) |
| Edge cursors | Yes. Shared. | `mrsm:engine_cursors` pipe (primary key `(parent_id, child_id)`, upsert; last consumed `seq`) |
| Runs and per-node results | Yes. Dash must see runs from jobs on any machine. | `mrsm:engine_runs` and `mrsm:engine_nodes` pipes |
| Events (chunk-level timeline) | Yes, written in batches, granularity configurable | `mrsm:engine_events` pipe (datetime-partitioned) |
| Duration estimates | No. Computed from `engine_nodes` history during planning. | Memory |
| Live event stream | No | Memory; jobs already stream their logs |
| Continuous-mode timers and debounce | No. Recomputed from watermarks and the ledger on restart. | Memory; daemon properties already persist |
| Leases | Yes, short-lived, and need an atomic acquire | See below |

**Why pipes:**

- Every instance type that can store pipes (SQL, Valkey, API, custom connectors) can hold engine state with **no new data methods**.
- Running pipelines on an `api:` instance (R2) needs no new API routes; the existing pipe routes carry the state.
- On SQL instances, the targets live in the internal schema (`SQLConnector.internal_schema`, `_mrsm_internal`) through `parameters['schema']`, so they stay out of the user's schema. They also inherit native partitioning, compression and maintenance.
- **Retention** is `clear_pipe(end=now - system.engine.run_history_days)` (default 30 days) on the runs, nodes and events pipes. Ledger entries consumed by every child are pruned the same way.

These pipes are `temporary=True` (never registered). They are therefore excluded from the graph, from `show pipes` and from the planner.

**Write ordering (at-least-once delivery):**

1. A parent writes its ledger entry *before* committing its data. A crash in between leaves a spurious entry that causes one harmless extra re-sync of the child, never a missed change.
2. A child advances its edge cursor only *after* its sync succeeds. A crash before that point re-processes the same ranges next time.

Both cases are safe because syncs are idempotent (`filter_existing` / upsert).

**Leases** are the one exception, because pipes offer no atomic compare-and-set. There is one optional method pair on `InstanceConnector`, `acquire_pipe_lease(pipe, holder, ttl)` / `release_pipe_lease(pipe, holder)`:

- **`SQLConnector`:** `INSERT` into an internal lease table in `_mrsm_internal`, with a unique key on `pipe_id` (the same pattern as the temporary-tables log in `connectors/sql/_instance.py`). The insert succeeds or hits a duplicate-key error, which is portable across every flavor. Expired leases are removed with a conditional `DELETE`. A heartbeat extends the TTL.
- **`ValkeyConnector`:** `SET NX PX`.
- **`APIConnector`:** passes the call through to the server (two small routes).
- **Base `InstanceConnector` fallback:** the existing interprocess file locks (`meerschaum/utils/locks.py`), under the existing locks path in the root directory. This logs a one-time warning that the lease only protects against other jobs on the same machine.

**Read-only instances.** If engine state can't be written, the engine runs in a degraded mode: planning uses watermarks only (`skip` / `incremental` / `root`), with no ledger-driven `backfill` and no persisted run history. A warning explains this.

### 5.8 Visualization

**CLI and shell Gantt:**
- On a TTY, a live `ratatui` view while the run is in progress. One row per pipe shows planned (CPM) and actual bars, a status glyph, row counts and a marker for the critical path.
- Elsewhere (jobs and logs), progress is written as line-oriented events, followed by a static ASCII Gantt summary when the run finishes.

```

```

**Dash console:** a new `/pipelines` page.
- A **DAG view** (`dash-cytoscape`). Nodes are colored by status or staleness, edges show ledger lag, and clicking a node opens its pipe card.
- A **Gantt chart** (Plotly timeline) per run. It overlays planned and actual bars, colors errors, uses tooltips for row counts and errors, and lets you click through to logs and tracebacks.
- A **runs table** with filters (status, tags, date range).
- The pipe card gains **Parents/Children** tabs that render the pipe's local neighborhood.

## 6. Rust plugins (goal 3, D1)

### 6.1 Contract

- A plugin is a `cdylib` that exports `mrsm_plugin_v1() -> *const MrsmPluginV1`. That struct is a `#[repr(C)]` vtable:
  - `abi_version`, `name`, `version`;
  - optional function pointers: `register`, `fetch`, `sync`, `setup`, `actions`, `connector` (for custom connector types);
  - `free_*` functions for memory the plugin allocated.
- **Data** crosses the boundary only as `FFI_ArrowArrayStream`, the Arrow C Stream Interface. `fetch` writes a stream of record batches, which gives chunked and streaming output for free.
- **Context** (pipe keys, parameters, begin/end, config) crosses as UTF-8 JSON, which keeps the ABI surface small and versionable.
- **Errors** come back as a status code plus an owned error string. Panics are caught with `catch_unwind` at every boundary.
- The `meerschaum-plugin` crate hides all `unsafe` code behind macros:

  ```rust
  use meerschaum_plugin::prelude::*;

  #[mrsm::fetch]
  fn fetch(pipe: &PipeContext, begin: Option<Bound>, end: Option<Bound>) -> Result<impl RecordBatchStream> { … }

  mrsm::export_plugin!(name = "noaa", version = env!("CARGO_PKG_VERSION"));
  ```

- The interface is also written as **WIT** (`crates/meerschaum-plugin/wit/plugin.wit`), so the WebAssembly host in §6.5 implements the same contract.

### 6.2 Compatibility

- `abi_version` is checked at load time. Breaking the vtable requires `mrsm_plugin_v2`, and the host keeps loading v1 for at least one major release.
- The host and the plugin do **not** need to share a Rust compiler version. Only the `extern "C"` and Arrow C interfaces cross the boundary, so `abi_stable` is not required.

### 6.3 Distribution

- Plugins live in `MRSM_PLUGINS_DIR` as `<name>/plugin.toml` plus a `lib<name>.{so,dylib,dll}`.
- The plugin repository (`mrsm register plugin`) stores **per-target-triple artifacts** plus a source tarball. On install, the matching triple is downloaded; if none matches, the plugin is built with `cargo build --release` when a toolchain is available.
- Python plugins are unchanged. A plugin directory may contain both kinds; Rust entry points take precedence (Q8).

### 6.4 Rust plugins inside a Python host

`meerschaum._core` loads Rust plugins itself, so Python users can sync Rust-plugin pipes without the CLI.

### 6.5 WebAssembly (v5.x)

A wasmtime component host for the same WIT interface. Its purpose is to run sandboxed, capability-limited plugins (transforms, plugins hosted by the API server, untrusted plugins from the repository). Data crosses as Arrow IPC buffers, which means a copy.

## 7. Data kernel and geometry (goal 4)

- `meerschaum-kernel` ports these pieces to Rust, operating on Arrow and Polars:
  - the dtype system: Meerschaum dtype strings ↔ Arrow types ↔ DB types (`utils/dtypes/__init__.py`, `utils/dtypes/sql.py`);
  - `enforce_dtypes`;
  - the `filter_existing` diff (anti-join plus a value comparison keyed on the index columns);
  - serialization for json, uuid, numeric, bytes and geometry.
- Python's `Pipe` calls these through `meerschaum._core`. The pandas paths convert at the boundary.
- **Parity gate.** The Python implementations stay in place behind `MRSM_KERNEL=python` for all of 5.x. CI runs the full suite in both modes, plus golden tests that diff the kernel output against the legacy output. This guards against problems seen in earlier cycles, such as `large_string[pyarrow]` not being treated as equal to string dtypes.
- **Geometry (D10):**
  - Canonical storage is the GeoArrow `geoarrow.wkb` extension type, with the CRS taken from the `geometry[srid]` dtype.
  - `as_polars=True` returns a GeoPolars `GeoDataFrame` when GeoPolars is installed. Otherwise geometry columns come back as Binary WKB with CRS metadata.
  - The pandas path returns GeoPandas, as it does today.
  - Rust uses the `geoarrow` and `geo` crates.
  - If GeoPolars has not released by 5.0, the WKB path ships anyway, and the GeoPolars preference is switched on in a non-breaking 5.x minor release.

## 8. Python modernization

- **Floor: 3.11** (D6). `abi3-py311` wheels; CI covers 3.11 through 3.15.
- **Lazy imports (PEP 810, Python 3.15).** Adopt `__lazy_modules__` in hot modules now. Python 3.15 imports the listed modules lazily, and older versions ignore the attribute, so the change is backward compatible.
  - `attempt_import` keeps its *install-on-demand and venv isolation* role.
  - Its lazy-module shim (`lazy=True`) becomes deprecated and is removed in the first breaking release that requires Python ≥ 3.15.
- Free-threaded wheels (3.14t/3.15t) need separate builds that are not abi3; see Q7.

## 9. Compatibility and migration

- Python plugins, `SuccessTuple`, `Pipe` keys and parameters, and existing jobs keep working **unchanged**. `pipe.sync` gains only keyword arguments.
- **Behavior changes:**
  - `--loop` uses the new engine. `--engine laps` restores the v4 behavior.
  - `mrsm` is now a native binary. The `python -m meerschaum` entry point remains.
- **Instance migration.** None needed. The internal engine pipes (§5.7) are created lazily on first sync, and watermarks are derived from `get_sync_time`.
- The **`rust` branch**: its 33 commits that are not on `main` were triaged; everything is already on `main`, so nothing needs to be kept (R4).

## 11. Risks

- **Scope.** Four major pieces in one release. Mitigations: the pre-release train, and the strangler-fig approach (Python implementations stay behind flags for all of 5.x).
- **Two implementations drifting apart** (Python and Rust kernels). Mitigation: the parity gate in CI.
- **Wheel build matrix and Windows** (named pipes for workers, plugin `.dll` loading). Set up CI in a1, not at the end.
- **Engine metadata load on instances.** Ledger and event writes on every sync add work. Write in batches, and make event persistence granularity configurable.
- **Crate names on crates.io.** Check whether `meerschaum`, `meerschaum-*` and `mrsm` are available and reserve them early.

## 12. Resolved questions

- **R1 (was Q1).** A bare `pipe.sync()` keeps **v4 behavior**: no capping to parent watermarks and no graph traversal. Capping applies only inside engine runs.
- **R2 (was Q3).** On an `api:` instance, pipelines run **on the client**. The engine runs locally and uses the API instance only for metadata, pipe state, the ledger, leases and run persistence, through the new `InstanceConnector` methods proxied by `APIConnector`. No server-side `POST /pipelines/run` in 5.0.
- **R3 (was Q6).** The shell and CLI **`+` and `:` syntax is preserved unchanged.** It is general logic for chaining actions (a simplified form of bash boolean logic), not a sync-only feature, and the engine does not reinterpret or merge chains. The engine simply makes complicated sync-ordering chains unnecessary, because dependency order comes from the graph.
- **R4 (was Q9).** The `rust` branch was triaged on 2026-10-11. All of its content is already on `main` (shipped in v4.0–v4.1). Of the 68 tests it added, 66 exist on `main` by name. The remaining two were superseded: `test_filter_unseen_df_polars_preserves_boolean_dtype` → `test_filter_unseen_df_polars_matches_boolean_dtype`, and the Windows install-lock test → the `msvcrt` path in `utils/locks.py`. **Nothing needs to be kept.** The branch can be archived (tagged) and deleted.

- **R5 (was Q2).** No local engine database. Engine state lives on the instance as internal `temporary` pipes (§5.7). Leases use one optional `InstanceConnector` method pair, falling back to the existing file locks. The root directory gains only lock files, which it already uses.

## 13. Open questions

- **Q5.** Should `{{ Pipe() }}` implicit edges be on by default, or opt-in (`system.engine.implicit_edges`)? Leaning toward **on by default**. Both real-world corpora in §10 express their dependencies *only* through `{{ Pipe() }}` references, with no `parents` or `children` parameters at all. Without implicit edges, the engine would see no graph in these projects.

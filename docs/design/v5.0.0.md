# Meerschaum v5.0.0 Design Spec

**Status:** Revised through D26 (2026-10-27). The decision log (§3) is binding.
**Branch:** `v5` (cut from `main` at v4.1.4)
**Date:** 2026-10-11 (revised 2026-10-12, 2026-10-19, 2026-10-22, 2026-10-24, 2026-10-27)

## 1. Theme

v5 rewrites Meerschaum in **Rust**. It is a clean break: the Rust implementation is the only implementation of the core, the server, the MCP server, jobs, compose, and the CLI. The web console is the Plotly Dash app of v4 on the Python install (D21, revised in 5.0.0rc2). There is no Python fallback inside the package and no planned v6 to finish the job.

v5 keeps the **existing ecosystem working**. Python plugins, custom Python connectors, API plugins, Dash plugins and web pages, MCP tools registered from plugins, compose projects, jobs, config files, instances, Docker images and the HTTP API all keep working as they do on v4.1. The `meerschaum` Python package survives as the **SDK and extension host**: a façade over the Rust core for pipe and connector work, plus the plugin SDK, plus one Python-hosted extension point (the API host, which serves API plugins, plugin MCP tools and the Dash web console with its plugin pages) for the objects a Rust server cannot run itself.

v5 also replaces the lap-based syncing engine with a **dependency-aware Syncing Engine** that understands the pipe graph, decides which syncs need to run and how wide their bounds must be, runs independent branches in parallel, and shows progress as a Gantt chart in the terminal and in the web console.

Polars is already the preferred DataFrame format. v5 uses the same Arrow/Polars memory model for everything that crosses a language boundary.

## 2. Goals and non-goals

### Goals (all ship in 5.0.0)

1. **Rust core.** `Pipe`, parameters, configuration, the connector registry, `{{ Pipe() }}` templating, compose, and the built-in `sql:`, `valkey:` and `api:` connectors are Rust. Every SQL flavor supported today has a Rust driver (D13). A standalone `sql:` → `sql:` sync never starts Python. In an existing Python host, DuckDB may use its public Python driver as transport to share the same database instance with SQLAlchemy; all Pipe and SQL algorithms remain Rust.
2. **Rust data kernel.** Dtype enforcement, the `filter_existing` diff and serialization are Rust and exposed to Python through PyO3. Geometry is stored as GeoArrow WKB with GeoPolars preferred and GeoPandas preserved for Python callers.
3. **Syncing Engine and pipelines.** A Rust graph, planner and executor; a `Pipeline` API; `pipe.sync(parents=..., children=...)`; a dirty-range ledger; run history; a Gantt chart and DAG view in the CLI and in the console.
4. **Rust server.** The HTTP API (every route in `meerschaum/api/routes`), OAuth2 and tokens, job log websockets, the web terminal, and the MCP server are an `axum` server. Python API plugins and plugin-registered MCP tools keep working through a proxied **Python extension host** (§7.3).
5. **Web console (D21).** The v4 Plotly Dash console, ported onto the façade and served by the API host at the same `/dash` paths, plus the v5 pipelines page (§8). Dash plugins register into that one app at the v4 paths (§8.4); the language-neutral **page contract** (HTML fragments plus Plotly figure JSON, §8.3) is shown in an iframe. The standalone binary serves the API, MCP, the web terminal and a pointer page at `/dash`. (5.0.0a/b/rc1 rendered the console from Rust; that console was deleted in rc2.)
6. **Rust CLI, shell, jobs and compose.** `mrsm` is a native binary. Every core action is native. Jobs are Rust-supervised with the same on-disk layout. Compose is native.
7. **Rust plugins.** A stable C-ABI plugin interface that exchanges data through the Arrow C Stream Interface.
8. **Ecosystem compatibility.** The compatibility contract in §11 is a release gate, verified against two private real-world corpora on every pre-release.

### Non-goals for 5.0

- Re-implementing Dash. The console and `@dash_plugin` callbacks / `@web_page` layouts are Python functions that need a Dash runtime. They run in the one Dash app inside the API host (§8), not in Rust. (A Rust-rendered console shipped in rc1 and was reversed by D21.)
- Re-implementing FastAPI. `@api_plugin` functions receive a FastAPI app. They run in the Python extension host, not in Rust. Meerschaum's own routes no longer use FastAPI.
- WebAssembly plugins (v5.x, see §9.5).
- Turso as a `sql:` flavor (v5.x, gated on its multi-process WAL support leaving experimental status; with a Rust connector this is a driver addition).
- Removing `attempt_import`, `Venv` or the per-plugin venv model. They are the plugin SDK and stay.

**D24 — registered Pipelines and console workspace (approved 2026-10-21, revised 2026-10-22):** Pipelines are registered, instance-owned selections over the implicit Pipe graph with a full CLI lifecycle (§5.2.1–§5.2.3); `pipeline-{name}` tags are applied only after analysis and explicit approval. Timelines show observed time, not forecasts (§5.9). Temporary execution workers are distinct from persistent Jobs and expire by policy (§6.4). Custom Compose filenames name their project (§6.3). Interactive SQL prefers Rainfrog (§4.3). Console Exec and Manage submit into the existing web terminal exactly once (§8.1); the Pipelines page is a list of registered Pipelines with a per-Pipeline detail view, guided creation and an explicit Edit mode, and node-local output (§8.2; revised 2026-10-26). Native core route groups can be disabled (§7.1, §7.3). These supersede earlier console, CLI and saved-Pipeline prose.

**D25 — installation ownership and runtime images (approved 2026-10-24):** Keep the
shared engine and both entry points. Self-upgrade resolves the running installation from
the launcher, Cargo receipt or standalone executable; `MRSM_PYTHON` identifies only an
optional extension host. One release/channel planner feeds the owning installer and verifies
the result. A separately selected Python host requires explicit consent to align; a native-only
upgrade never provisions Python. Shells restart after updating the engine. Containers are
upgraded by replacing their images. `rust` is a Python-free native runtime, `rust-full` adds
Cargo/rustc and native build tools without Python, `slim`/`minimal` retain the base Python
wheel, and `full`/`latest`/deprecated `api` include the native executable, Python SDK with
all extras and both language build toolchains. This supersedes earlier Docker wheel-only
and full-image size assumptions. Budgets are 250 MB for rust/slim, 1600 MB for rust-full,
and 2500 MB for full (uncompressed). All variants share configuration and plugin formats.

**D26 — usability for small teams (approved 2026-10-27):** 5.0 is aimed at small teams of developers,
many new to programming, who need simple, friendly defaults (time-series first) with depth for
power users. The console gets one shell: a top navigation on every console page, an Overview at
`/dash`, v4's dashboard as the Terminal page, a read-only Connectors page, a Pipes table with a
page per pipe and **New pipe**, and Jobs (New job, Restart, Delete, health), Users (administration)
and Plugins (Installed and Repository) pages; no subtitles or helper captions, dark by default,
usable at phone width (§8.1, §8.2). Console callbacks need a session unless marked public (§7.3).
On the CLI, a flag alters an action's behavior or supplies input but never turns it into another
action, so new functionality gets its own action or subaction: `verify schema`, `start pipeline` /
`stop pipeline` for saved Pipelines' background jobs, with action chains serialized under a hidden
`chain` action (§4.3). `mrsm help` starts with grouped actions, and the frozen part of `--help` is
the argument surface, not its text. Output is styled only where it is read on a terminal (`NO_COLOR`,
`FORCE_COLOR`). `--loop` works for any action, and jobs report their health (§6.4). Jobs use the
systemd executor in every root (§6.4). Data: `replace` windows (§5.10), NULL-safe upserts and
null-like strings kept as text in text columns (§6.2), database errors that raise from the Python
read methods (`silent=True` restores v4's results), protected connectors (§6.5), row estimates and
hidden internal pipes. Every sync records a per-pipe sync status on the pipe's instance (§5.8). The
Python Pipeline API loads saved Pipelines by name and never registers or overwrites by accident
(§5.2). The v5-only HTTP routes share one response shape, and the HTTP API and MCP gain Pipeline,
run, job and connector surfaces, a public preset and fail-closed permissions (§7.1, §7.2). The web
terminal runs its own tmux server. Rust plugins get host calls and a manifest builder (§9.1); the
Python SDK gets session and static-file helpers, page themes and head tags, multi-word action
names, a cache helper and a pytest plugin (§12). These supersede earlier prose where they differ.

## 4. Architecture

### 4.1 Workspace layout

```
crates/
  meerschaum/           # front crate (Polars model): thin re-exports + cargo features; the crate users depend on
  meerschaum-core/      # Pipe, keys, parameters, dtype strings, config registry, {{ Pipe() }} templating,
                        # users/tokens/plugins registries, SuccessTuple/SyncResult, static.toml
  meerschaum-kernel/    # Arrow/Polars: dtype enforcement, diff (filter_existing), serialization, GeoArrow
  meerschaum-connector-sql/       # SQLConnector: drivers per D13, query building, partitioning, upsert, metadef, maintenance
  meerschaum-connector-valkey/    # ValkeyConnector (fred)
  meerschaum-connector-api/       # APIConnector client (reqwest) and the shared route/auth models
  meerschaum-engine/    # Graph, planner, executor, ledger, run events
  meerschaum-jobs/      # Daemon supervision, log rotation, systemd executor, api: executor
  meerschaum-compose/   # Compose YAML model, project isolation, subactions
  meerschaum-server/    # axum HTTP API, OAuth2/JWT, tokens, websockets, webterm, MCP, extension-host proxy
  meerschaum-web/       # Web terminal (xterm assets, `/webterm`), job-log stream (SSE), native plugin pages, sessions; the console itself is Dash (D21)
  meerschaum-plugin/    # Stable plugin API (C ABI vtable, macros, Arrow C Stream helpers)
  meerschaum-cli/       # the CLI library (internal): clap CLI, reedline shell, Python worker pool, Gantt TUI; `run_main()` is the whole process entry (its own `mrsm-cli` binary only runs its integration tests)
  meerschaum/           # the front crate: curated re-exports behind features; its default `cli` feature builds the standalone `mrsm` (`cargo install meerschaum`)
  meerschaum-py/        # PyO3 bindings -> `meerschaum._core` (built into the `meerschaum` wheel)
meerschaum/             # The Python package: façade, plugin SDK, API host (with the Dash console), MCP SDK
```

Who hosts what:

| Host process | Core, kernel, engine, connectors | Python plugins and custom Python connectors | Python API/Dash plugins | Rust plugins |
|---|---|---|---|---|
| Python (library, scripts, tests) | In-process via `meerschaum._core` | Called directly through the adapter | n/a | `dlopen` from Rust, inside the Python process |
| Rust (`mrsm` CLI, shell, jobs, server) | Native | **Worker pool** (D2) | **API host** (D17), proxied | `dlopen` |

### 4.2 Python interop (D2, D3)

- **`meerschaum._core`** is the PyO3 extension module. The Python `Pipe`, connectors, `enforce_dtypes`, `filter_existing`, `get_config`, templating and the engine entry points delegate to it. DataFrames cross the boundary without copying through the Arrow PyCapsule interface (`__arrow_c_stream__`). Pandas and GeoPandas inputs are converted at the boundary.
- **The Python worker** (`python -m meerschaum.worker`) is started by the Rust host when a Python plugin, Python action or custom Python connector is needed. It speaks a small RPC protocol: control messages as msgpack, data as Arrow IPC streams over a Unix domain socket (named pipes on Windows). Operations mirror the `Connector` and `InstanceConnector` traits (`fetch`, `sync`, `register`, `setup`, `subscribe`, `sync_pipe`, `get_pipe_data`, `get_sync_time`, …) plus `action`, `pre_sync_hook` and `post_sync_hook`.
- **Pool policy.** One pool, sized by `system.engine.python_workers`. Meerschaum venvs are `sys.path` entries activated by the `Venv` context manager, not separate interpreters, so one worker serves any plugin's venv. A worker crash fails only the node it was running.
- **Hooks.** `@pre_sync_hook` / `@post_sync_hook` run in the worker after each native sync with the same kwargs as today (`success_tuple`, `sync_timestamp`, `sync_complete_timestamp`, `sync_duration`, …). When no plugin registers a hook (known from the manifest, §4.3), no worker starts.

New roots select Polars with `meerschaum.dataframe`; earlier roots are pinned once to pandas during bootstrap. `MRSM_DATAFRAME` overrides the process, and `as_pandas` / `as_polars` override a read. `frame_from_arrow` centralizes Arrow-to-frame conversion and dtype hints; enforcement/filtering preserve DataFrame input types, while fetches and hook frames follow the configured library. Polars geometry is WKB with CRS metadata; pandas requests retain GeoDataFrames. The console converts internally when Dash/Plotly require pandas.

### 4.3 CLI and shell (goal 6)

- **clap** is the single source of truth for core arguments (ported from `_internal/arguments/_parser.py`). A generated JSON schema of the argument spec is read by the Python `parse_arguments`, which the SDK keeps for plugins that build sysargs.
- **Core actions are native.** Every action in `meerschaum/actions/` is Rust: `sync`, `verify`, `show`, `register`, `edit`, `delete`, `drop`, `clear`, `copy`, `deduplicate`, `index`, `vacuum`, `analyze`, `compress`, `decompress`, `partition`, `tag`, `bootstrap`, `start`/`stop`/`pause`/`attach`/`restart`, `login`, `install`/`uninstall`/`upgrade`/`setup`, `reload`, `stack`, `compose`, `api`, `os`, `sh`, `sql`, `flush`. `python` starts an interpreter with the SDK loaded, as today. The Python `meerschaum.actions` module keeps the same function names and dispatches to `_core`, so `python -m meerschaum sync pipes` and the API's `/actions` route behave identically.
- **Python starts only for Python code**: plugin actions, custom-action loops, the API host, and any pipe whose connector is Python.
- **The shell** uses `reedline` and keeps today's behavior: switching instances, the `:` flags that apply to a whole chained command, `+` action chaining, and history. `-d` detaching into a job and `--name` work identically.
- **Interactive parity.** The prompt_toolkit experience is reproduced on top of `reedline`: the bottom toolbar (instance, repo, executor, connection status, compose project), the completion menu that opens while typing with v4's candidates and colors, history auto-suggest limited to valid commands, `(reverse-i-search)`, Ctrl-C/Ctrl-D behavior and the background update check. It is verified against v4 with pseudo-terminal screen snapshots (`crates/meerschaum-cli/tests/shell_screens.rs`). **No CLI daemon:** actions run natively in `mrsm`, so v4's experimental CLI daemon (`system.experimental.cli_daemon`) has no v5 counterpart; the `daemon` shell command keeps its toggle and message and says that v5 does not use a daemon.
- **Shell sync feedback** uses the native Rust progress renderer (spinner, bar, elapsed time); it is disabled for redirected output and cleared around output and interruption. Ctrl+C at a prompt aborts the prompt and returns to the shell.
- **Debug output.** `meerschaum_core::dprint!` is a `tracing` `DEBUG` event from the caller's module, emitted only while a process-wide switch is on (one atomic load otherwise). `--debug` on any action (counted scopes, so overlapping actions in one process leave it off when the last ends) and the shell's `debug` toggle set the switch; the API server's action requests do not (`without_scopes`), and full-screen views hold the output until they exit; the CLI subscriber (`meerschaum-cli` `debug_log`) prints the Meerschaum crates' `DEBUG`/`INFO` events in v4's `dprint` format on stderr, around the progress line, independently of `RUST_LOG`. Python's `dprint()` also writes to stderr. `--debug` travels to every Python worker call (`debug=True` in the call's kwargs); in the extension a binding called with `debug=True` (or inside `_core.debugging()`) routes the Rust events to Python's `dprint()`. Instrumented: dispatch (redacted arguments), connector creation (`sql:`, `api:`, `valkey:`), every SQL statement (emitted at the `SqlDriver` entry points), sync stages including fetched chunks, engine plans and every engine event, worker calls, plugin discovery and manifest builds.
- **Interactive SQL (D24).** `mrsm sql <keys>` prefers [Rainfrog](https://github.com/achristmascarl/rainfrog) (an external Rust TUI) for the flavors it supports (PostgreSQL family, MySQL family, SQLite, DuckDB, Oracle; Oracle needs client libraries and some builds omit DuckDB). A connector's `cli` attribute or `system.connectors.sql.cli.<flavor>` overrides the preference; the Python clients (`pgcli`, `mycli`, `litecli`, ...) stay explicit choices and the next fallback, then the flavor's plain client; `--nopretty` forces the plain client. MSSQL keeps its existing choices. A missing executable falls through with installation guidance (`cargo install rainfrog --locked` or `meerschaum[cli-tools]`). Credentials never appear in argv; a failing interactive client fails the action; the terminal is restored on exit, including in the web terminal.
- **Plugin action manifests.** `@make_action`, `add_plugin_argument`, hook registrations, `@api_plugin`, `@dash_plugin`, `@web_page`, MCP tool registrations and action docstrings are collected into a cached manifest when plugins are installed or set up. Staleness is detected by hashing each plugin's source tree mtimes and sizes at startup; a stale manifest is rebuilt in a worker. `--help`, tab completion and argument validation never start Python unless a plugin changed. The manifest also tells the server whether the API host is needed (a `console` flag covers the Dash console) and which plugin pages the console navbar links. Each action carries `words` (`ActionManifest::action_words()`, falling back to splitting `name` on `_`; `@make_action(name='weather wait')` writes them) and `handles_loop` (its function names a `loop` parameter; written by the host's worker extension, and a cached manifest without it is stale once). The schema version is unchanged.
- **Help (D26).** The global help (`mrsm help`, `-h`, `--help`, `show help`, the shell's `help`) is the usage line, the actions in groups (`help::ACTION_GROUPS`: Create, Sync, Run, Inspect, Maintain, Configure; a Shell group in the shell) with each docstring's first line, a Plugins group (every plugin action and v4-style subaction under its words), then the options in argparse's layout, the engine flags under "Pipeline options" and one "Plugin '<name>' options" group per plugin. Per-action help is one text (the former "v5 additions" block is folded in) and regenerates a main action's `Options:` line from the live subaction table. `help` is a core action. Help starts no Python: plugin actions come from the cached manifest, and help says when that cache is stale (`meerschaum_plugin::discovery::manifest_cache_is_current`, `help::plugins_cache_is_current`). The frozen part of `--help` is the argument surface (option strings, `dest`, `nargs`, types, choices, groups and their order); arguments added in 5.0 (`replace`, `public`, `allow_protected`, `spec::V5_ONLY_DESTS`) come last, and the Python mirror (`_internal/arguments/_parser.py`) declares them too.
- **Action chains and Pipeline jobs (D26).** Chains (`+`, `:`) serialize as the hidden action `chain <flags> -P '{"sub_args_line", "patch_args"}'` (`meerschaum_core::chain`, shared by the CLI, jobs and compose); the dispatcher runs `chain` only with that payload, before plugin resolution, and never lists it. v4's `start pipeline ... -P` form runs as a chain, and sysargs bound for an API server are written in v4's form so any server version runs them. `start pipeline(s)` / `stop pipeline(s) NAME` act on a saved Pipeline's background job (§5.2.1); `-s` on them is the job's schedule, never the dispatcher's.
- **`--loop` for any action (D26).** The dispatcher wraps every action that does not loop by itself in a lap loop (`native::jobs_laps`, `meerschaum_jobs::LapPacer`: `--min-seconds` after each run, a cooldown of `2 × (min + 1)` growing ×1.5 per consecutive failure and capped at `max(3600 s, 2 × (min + 1))`), plugin actions included, and calls the action with `loop=False` on each lap. Actions that loop themselves or hand `--loop` to a job (`sync pipes`, `verify pipes`, `deduplicate pipes`, `sync pipelines`, chains, `start` / `stop pipeline`, the jobs and server actions, `show logs`, `compose`, `stack`, `watch`) are not wrapped, nor is a Python plugin action with `handles_loop` (4.1's contract: `loop=True`, it repeats by itself). The host runs a plugin action's `-s` schedule: `host_action` calls carry `host_schedules`, and the worker's `op_action` then runs once per fire.
- **Output styles (D26).** Styles depend on the destination: `FormatSettings::detect` turns ANSI off when stdout is not a terminal unless the process is a job (`MRSM_DAEMON_ID`) or `FORCE_COLOR` is set, `NO_COLOR` renders no SGR at all (terminal features such as the live region and the full-screen views keep working without colors), and `formatting:ansi: false` turns styles and the full-screen views off. stdout and stderr decide separately (`Runtime::{out_terminal, err_terminal, err_settings}`; `eprint` strips SGR when stderr takes none); a relayed child gets `FORCE_COLOR=1` when the parent styles (`format::relay_env`), and worker output is stripped of SGR when the CLI prints plain. Python's `meerschaum.utils.formatting.ansi_allowed(stream=None)` applies the same rule (a Jupyter kernel counts as a terminal), and the façade's runtime passes Python's own stream decisions to `mrsm.entry()`.
- **Scripts and messages (D26).** For `python <file> ...` the parser reads only the words up to the file and the rest are the script's (`parse::python_script_index`, mirrored in `_parse_arguments.py`; `parse_dict_to_sysargs` writes them last, so the shell and jobs keep them). An undefined connector is reported by one message shared by the CLI and Python (`undefined_connector_message`: "Connector 'sql:nope' is not defined. ..."), and an unreachable `sql:main` with its shipped host, port and database (no `MRSM_SQL_MAIN`) appends the next step (`mrsm stack up -d db`, or `sql:local`) once per command. The API server serves native HTTPS through rustls when key/certificate files are supplied, otherwise plain HTTP; invalid pairs fail before startup and renewals reload on SIGHUP or a 30-second poll.
- **Distribution (D8).** `pip install meerschaum` installs one wheel. Its `mrsm` console script calls the native CLI entry point inside the `_native` extension, so the shell, every native action, `start api` and jobs run from the same library the Python façade uses (start-up is the cost of loading the extension, about 0.15 s, against 0.01 s for the standalone binary). `cargo install meerschaum` builds the standalone `mrsm` binary from the front crate (default `cli` feature; library users depend on `meerschaum` with `default-features = false`). The standalone binary asks for a Python interpreter (`MRSM_PYTHON` or config) the first time Python is needed, and runs without one as long as no Python plugin, connector or extension is used. `MRSM_BIN` makes the Python package use a standalone binary instead.

### 4.4 The inversion: Python as a façade (D12)

**Façade.** The public Python API stays identical. Internally:

- `meerschaum.Pipe` wraps a `_core.Pipe`. Keys, `parameters`, `columns`, `dtypes`, `indices`, `tags`, `target`, `sync`, `get_data`, `get_docs`, `get_doc`, `get_value`, `get_sync_time`, `get_rowcount`, `get_backtrack_data`, `get_chunk_bounds`, `verify`, `filter_existing`, `enforce_dtypes`, `clear`, `drop`, `register`, `edit`, `delete`, `exists`, `update_parameters`, the cache and `{{ Pipe() }}` resolution call into Rust. **Constructing a `Pipe` never touches the instance**, so module-level pipe definitions in plugins import cleanly and tests can swap stubs.
- `meerschaum.connectors.SQLConnector`, `ValkeyConnector` and `APIConnector` wrap their Rust counterparts for every pipe, user, token and plugin method. Per D16, raw SQL and metadata use the native driver too, while `.engine` and caller-provided SQLAlchemy connections remain optional.
- `meerschaum.config.get_config`, `write_config`, `get_plugin_config` / `write_plugin_config` (including the no-argument form that infers the calling plugin from the stack), `MRSM{}` symlinks, `config.paths.ROOT_DIR_PATH` and friends, and the environment-variable connectors (`MRSM_SQL_<LABEL>`) are served by the Rust config registry. The YAML files and their layout do not change.
- `meerschaum.core.User` and `Token` wrap Rust types but keep their attributes, including the private ones plugins read (`_password_hash`, `_attributes`, `_user_id`). `hash_password` / `verify_password` keep passlib's `pbkdf2-sha256` modular-crypt format so existing user tables validate unchanged.
- `SuccessTuple`, `warn`, `error`, `info`, `dprint`, `pprint`, `attempt_import` (including `venv=` and `lazy=`), `Venv`, `pip_install`, `import_pandas`, `Plugin(name).module`, `from_plugin_import`, `import_plugins`, `make_connector`, `make_action`, `add_plugin_argument`, the hook decorators, `prompt`, `yes_no`, `wget`, `round_time`, `select_pipes`, `string_to_dict`, `items_str`, `filter_keywords`, `filter_arguments`, `parse_df_datetimes`, `print_options`, `print_tuple`, `query_df`, `none_if_null`, `get_current_timestamp`, `serialize_bytes`, `deserialize_bytes_string`, `serialize_geometry`, `replace_pipes_syntax` and `utils.threading.STOP_EVENT` stay Python (every name here is imported by at least one corpus plugin). `meerschaum.jobs.Job` stays as a façade over `meerschaum-jobs`; `utils.daemon.Daemon` is removed. They are the plugin SDK. Where one of them has a Rust implementation (`query_df`, `replace_pipes_syntax`, dtype helpers), the Python name is a thin wrapper.

**Adapter.** Rust calls Python only for user and plugin code: plugin connectors (`plugin:` keys with `fetch`/`sync`/`register`/`setup`/`subscribe`), custom connectors declared with `@make_connector` (both plain connectors with `fetch`, and `IS_INSTANCE = True` connectors implementing the instance interface), actions and hooks. A `PythonConnector` type implements the Rust `Connector` and `InstanceConnector` traits by forwarding each call to Python, in-process through PyO3 when Python is the host and through the worker when Rust is the host. Data crosses as Arrow. The fetch contract accepts everything it accepts today: a DataFrame, a GeoDataFrame, a list of dicts, a dict of lists, a JSON string, or a generator of any of those.

**Rule.** Rust never calls a Python implementation of something it implements itself. The adapter and the API host forward only to user and plugin code.

**What the façade must preserve** (verified by the existing pytest suite and the compatibility contract in §11):

- The `parameters` dict is live: `pipe.parameters['x'] = 1` followed by `pipe.edit()` persists. The façade exposes a dict-like proxy over the Rust parameters, not a copy.
- `pipe.columns`, `pipe.dtypes`, `pipe.indices`, `pipe.tags` and the attribute aliases (`pipe.upsert = True`) stay assignable.
- `Pipe.__getstate__` / pickling, `__eq__` and `__hash__` by keys, and `str(pipe)`.
- `get_data()` follows `meerschaum:dataframe` (Polars on fresh roots, pandas pinned on upgraded roots). `as_pandas=True` returns pandas and a GeoDataFrame with its CRS set for `geometry[...]`; `as_polars=True` returns Polars with WKB geometry and CRS metadata (GeoPolars when installed). `as_iterator=True` and `as_chunks=True` keep their generator shapes; `as_docs=True` keeps the list-of-dicts shape.
- Partial-row `sync([{dt, id, col}])` on a non-upsert pipe updates the matching row without nulling the other columns.
- Duck typing: plugins and tests substitute stub objects for pipes and users. The façade never `isinstance`-checks user objects.

## 5. Syncing Engine (goal 3)

### 5.1 The pipe graph

- **Node.** `(instance_keys, connector_keys, metric_key, location_key)`. Edges may cross instances.
- **Node identity in persisted state.** Pipe IDs are instance-local (integers on SQL, strings on Valkey), so persisted engine state never keys on `pipe_id` alone. Every persisted row uses `pipe_ref`: the string `"{instance_keys}|{connector_keys}|{metric_key}|{location_key}"`. Edges are `(parent_ref, child_ref)`.
- **Edges** come from three sources, which are combined and deduplicated:
  1. `parameters['parents']` / `parent` (edge parent → self). `parent` may be a `"Pipe(...)"` string, a dict, or keys.
  2. `parameters['children']` / `child` (edge self → child);
  3. `{{ Pipe(...) }}` references found in SQL definitions and in parameter values. These are implicit edges, extracted statically by the Rust template parser (§6.3). A reference to a pipe that does not exist is a planning warning, not an error, because corpora contain stale references.

  Today `parents` and `children` are declared independently (`core/Pipe/_attributes.py:856`, `:924`), and nothing records the reverse direction. The graph builder must look at both sides.
- `reference` / `references` only means parameter inheritance. It is **not** a data edge.
- A **cycle** is a planning error. The message prints the cycle path.
- The graph is built by `meerschaum-engine` from a batch `fetch_pipes_keys` (dict form, so all parameters come back in one round trip) and cached for each run.
- **Cross-instance edges** store their ledger entries and cursor on the **child's** instance. The child's planner reads the parent's watermark through the parent's instance connector. If the parent's instance cannot be reached, the edge is treated as `upstream_failed`.

### 5.2 Selection API (D4, D5)

```python
import meerschaum as mrsm

pipe = mrsm.Pipe('sql:main', 'daily_rollup', instance='sql:main')

pipe.sync()                        # v4 behavior, unchanged
pipe.sync(parents=True)            # sync all ancestors in dependency order, then this pipe
pipe.sync(parents=1)               # direct parents only
pipe.sync(children=True)           # sync this pipe, then propagate to all descendants
pipe.sync(parents=True, children=True)

pipeline = mrsm.Pipeline(pipe, parents=True, children=False)   # or mrsm.Pipeline([p1, p2, ...]) / tags=...
daily = mrsm.Pipeline('daily')               # a saved Pipeline, by name (§5.2.1)
plan = pipeline.plan(begin=None, end=None)   # dry run; no data movement, registers nothing
print(plan)                                  # table: pipe | action | bounds | chunks | reason
run = plan.execute(workers=8)                # or pipeline.run(...)
run = pipeline.sync(on_event=print)          # live event stream (§5.7): one dict per event
run.events()                                 # the run's persisted events, after the fact
run.result                                   # SuccessTuple-compatible
```

CLI:

```
mrsm sync pipes -c sql:main -m daily_rollup --parents [N] --children [N]
mrsm plan pipes ...             # print the plan only (like `terraform plan`)
mrsm show graph ...             # ASCII DAG of the selection
mrsm show runs [--last N]       # run history; `show run <id>` renders the Gantt chart
```

A `Pipeline` may be an unsaved selection (above) or a **registered** one (§5.2.1). `mrsm compose sync pipes --parents` works the same way inside a compose project.

**Python construction (D26).** In `Pipeline(pipes, ...)`, a `str` without `|` is a saved Pipeline's name, a `str` with `|` is a `pipe_ref`, and a list may mix names, refs, `Pipe` objects and key tuples (names contribute their members, whose traversal settings must agree unless `parents=` / `children=` are passed). `Pipeline(name=...)` without pipes loads that Pipeline. `graph: Optional[bool]` defaults to `True` for Pipelines bound to saved definitions and `False` otherwise: a name alone never implies graph semantics. `save(name=None, overwrite=False, description=None, defaults=None)` returns a `SuccessTuple`; it refuses to replace a different saved Pipeline unless `overwrite=True`, saves a loaded Pipeline's edits with the loaded revision as `expected_revision`, and writes nothing when the selection is unchanged. `plan()` and `.pipes` never register (unregistered members are listed in `Plan.unregistered` and the plan's warnings); `sync()` registers only members passed as `Pipe` objects, never a saved member reference. `get_pipelines()`, `Pipeline.exists/delete/rename/copy/analyze/apply_analysis/schedule` and the `members` alias of `targets` complete the API, and `Plan`, `RunResult`, `get_runs` (with `pipeline=`, `pipe=`, `since=`) and `get_pipelines` are top-level exports. `RunResult.inserted/updated/upserted/deleted` sum the node outcomes, and `duration` stays the run's wall-clock seconds. `pipe.get_data()`, `get_docs()`, `get_doc()`, `get_value()` and `get_backtrack_data()` warn once per call about a keyword nothing reads, with a suggestion (an error-raising warnings filter makes it raise).

#### 5.2.1 Registered Pipelines (D4, D24)

- **Registration.** Pipelines are registered on instances just like Pipes. A registration owns its name, identity, exact member references, traversal settings (`parents`/`children` depths), execution defaults and revision. Each member reference carries its own instance keys: selecting the registry with `-i` never rebinds members. Names are unique within a registry; the same name on two registries is two Pipelines. Definitions hold connector references, never credentials. Schema/revision migration preserves existing definitions, member references and schedules.
- **Not a second graph.** The implicit Pipe graph (§5.1) stays authoritative for dependencies; a Pipeline is a persisted selection over it. Pipelines may share Pipes, and shared-Pipe protections (leases, §5.8) still apply. Each admitted run records the resolved selection and the definition revision; later edits affect later runs only.
- **Failures are visible.** A missing instance, credential or member is an error naming it, never a silently dropped target. Changes spanning instances report per-instance partial failures rather than promising atomic rollback.
- **Python.** `repr` of a saved `mrsm.Pipeline` uses its name and includes a non-default registry instance, without network access.
- **Initialization is read-only.** Neither the console nor the CLI registers discovered connected components; they are offered as suggestions the user may save. (rc5 auto-registered every connected component, isolated Pipes included; those single-member registrations are preserved, since automatic deletion could remove intentional definitions.)
- **Jobs.** Scheduling is an ordinary Job referencing the registered Pipeline. `start` / `stop` / `pause jobs` act on named Jobs and cancellation on one execution, never on every Job sharing a Pipeline. A Pipeline's background Job is a Job whose sysargs are `sync pipeline(s) NAME ... -i <registry>` (the console's Schedule and `Pipeline.schedule()` create them). **`start pipeline(s) NAME` (D26)** starts the Pipeline's scheduled Jobs when it has any (naming the Jobs it left alone), else its other Jobs, else creates `pipeline-NAME` (or `--name`) running `sync pipelines NAME -i <registry> --loop --min-seconds 60` (`pipeline_jobs::DEFAULT_JOB_MIN_SECONDS`, unless the Pipeline saves a `min_seconds` default), or `--schedule S` with `-s`, carrying `--allow-protected` and the Compose stamps; it warns when a loop Job and another Job of the Pipeline both run. `stop pipeline(s) NAME` stops every Job of the Pipeline (also of a Pipeline deleted since). A name that is neither saved nor synced by a Job is refused before anything starts or stops, with the saved names. `sync pipelines NAME --loop/--listen` runs in continuous mode (§5.5).

#### 5.2.2 Analysis and approved tags

- **Tags.** `pipeline-{name}` is the tag on explicit members and detected traversal Pipes (separate from Compose's unprefixed project-name tag). Tags are indexes: editing a tag never rewrites a registration. Tag ownership is tracked so same-name Pipelines on other registries, pre-existing tags and overlapping membership never cause a wrongful removal.
- **Analysis.** `analyze pipelines [NAME ...]` does the graph work `show` never does: resolve exact members and configured traversal, detect missing/unavailable references and cycles, identify shared members, and compare actual with expected tags. It prints the discovered Pipes, their instances, why each is included and the proposed tag changes.
- **Approval.** Tagging needs approval: interactively after the findings, or `--yes` for the displayed proposal in batch mode; non-interactive analysis without `--yes` only reports. No discovery, page load, read-only plan or ordinary sync applies tags, and save/edit may offer analysis but never hides the mutation. Notices about untagged Pipes point at `analyze pipelines`. A stale proposal is re-resolved before applying and needs renewed approval if its targets changed. Only a fully resolved analysis may propose removing stale owned tags (a failed read leaves reconciliation pending); failed writes are reported per Pipe and can be retried. Deleting or renaming a Pipeline removes only the tags it owns and never touches member registrations or data.

#### 5.2.3 CLI lifecycle

`pipelines` (singular aliases kept) appears in action discovery, help, contextual completion (names from the selected registry), the Python façade and API discovery. Additive v5 actions are never hidden to match v4 fixture listings; parity tests exclude them at the comparison boundary.

| Action | Behavior |
|---|---|
| `show pipelines [NAME ...]` | Saved definitions plus batched recent execution summaries; no discovery, no member resolution, no edits. The listing shows member and instance counts and status symbols with a Keys legend; a named detail shows explicit references and traversal settings. |
| `analyze pipelines [NAME ...]` | Resolve, diagnose, preview and (on approval) apply tag changes (§5.2.2). |
| `bootstrap pipelines NAME` | Guided creation from existing Pipes or with new Pipe registration. |
| `register pipelines NAME` | Create or import a versioned definition; never overwrites by accident. |
| `edit pipelines NAME` | Edit membership, traversal, name, description and defaults as YAML in the editor; revisions are validated. |
| `plan pipelines NAME` | Read-only preview of resolved actions, dependencies and bounds. |
| `sync pipelines NAME ...` | Run the resolved selections with the usual bounds/workers/retries/force options and report run IDs; identical member references across a combined selection are deduplicated. |
| `delete pipelines NAME` | Delete the definition and its owned tags; Pipe data and history stay. Refused while a scheduled Job references it. A bare `delete pipelines` previews every definition and keeps confirmation and the scheduled-Job check. |
| `drop pipelines NAME` / `clear pipelines NAME` | Drop-Pipe / bounded clear-Pipe semantics on explicit members only (traversal is not inherited); the exact targets, instances and shared membership are frozen and previewed before the usual confirmation; results per Pipe. Registrations and the definition stay. |
| `copy pipelines NAME NEW_NAME` | New identity referencing the same Pipes; no data is copied. |
| `start pipeline(s) NAME ...` / `stop pipeline(s) NAME ...` | Start or stop the Pipeline's background Job, creating `pipeline-NAME` when it has none (§5.2.1, D26). |

Named selections warn about and skip missing registrations. Import/export uses the definition schema. Runs, history and logs use the existing commands with Pipeline, run and Pipe filters.

### 5.3 Planner

The planner gives every node in the selection one action. **The ledger cursor is the primary signal** (§5.4); watermarks are a fallback for edges with no ledger history.

| Action | When | Bounds |
|---|---|---|
| `skip` | No unconsumed ledger entries on any in-selection parent edge, no parent watermark has advanced since the edge cursor was last moved, and the definition hash is unchanged | none |
| `incremental` | A parent watermark advanced since the cursor last moved, with no unconsumed ledger entries beyond the new tail | `[own watermark − backtrack, min(parent watermarks))` |
| `backfill` | Unconsumed dirty ranges from parents (§5.4) | The dirty ranges, mapped onto this node's chunk grid |
| `rebuild` | The definition hash changed (SQL text, `fetch` config, dtypes, columns) | Full range (see below) |
| `observe` | The node is a stream source (§5.6) | none. Watermark and ledger are read only. |
| `root` | The node has no parents in the selection | v4 semantics (`begin=''` = sync time minus backtrack) |

- **Why cursors first.** Comparing a child's watermark to its parents' assumes both datetime columns measure the same thing. They often don't: a daily rollup's watermark is the day floor and is always below the raw pipe's watermark, so a watermark-only rule would never produce `skip` for aggregates. The cursor records exactly what the child consumed, so `skip` is decidable for every shape.
- **Edge cursor also stores the parent watermark** it last consumed (`parent_watermark_at_cursor`). That is what `incremental` compares against, not the child's own watermark.
- **Watermark.** A pipe's watermark is its sync time (`get_sync_time`). It is derived on demand (not persisted) and cached in memory for the duration of a run.
- **The capping rule.** Inside an engine run (`Pipeline`, `parents=`, `children=`, continuous mode), a child is never synced past `min(parent watermarks)`. A bare `pipe.sync()` keeps v4 behavior and never caps (R1).
- **`rebuild` semantics.** `rebuild` runs `clear_pipe()` over the full range and then a full sync, because a definition change can drop rows or columns that `filter_existing` would never remove. `rebuild` needs `--yes` / `force` unless `system.engine.auto_rebuild: true`. **In a non-interactive context** (jobs, `--loop`, the API) a node that needs `rebuild` without `--yes` is marked `rebuild_pending`, its descendants run against the stale data, and a warning is logged on every run until someone confirms. It never blocks the run.
- **Pipes without a datetime column** (most of corpus B: `primary`-keyed GIS layers) cannot have a watermark. Any change in a parent triggers a full re-sync of the child, which relies on its own `filter_existing`. Their ledger entries carry no interval, only a sequence number.
- **Pipes with an integer datetime axis** behave the same way on the integer grid.

### 5.4 Dirty-range ledger

- **When it is written.** A ledger entry is written **before the data commit** of the sync that produced it (see Write ordering in §5.8). The entry's intervals are the min/max of the datetime column over the rows that will be inserted, updated or upserted (the delta that `filter_existing` computes), bucketed onto the epoch-aligned chunk/partition grid (`get_chunk_bounds(align=True)`, `verify.chunk_minutes`). With `check_existing=False` the delta is the whole input.
- **Chunked and generator syncs** write one entry per chunk, before that chunk's commit. A sync with no changed rows writes nothing.
- Each ledger entry carries a **monotonically increasing sequence number** for its pipe, assigned by the instance (an autoincrement on SQL, `INCR` on Valkey).
- Each **edge** stores a cursor: the last parent sequence number the child has consumed. During planning, the unconsumed entries are combined into a set of intervals and drive `backfill`.
- **Mapping parent ranges onto a child.** By default this is the identity mapping on the datetime axis, widened to the child's chunk grid. Each edge can override it with `lookback` / `lookahead`:

  ```yaml
  parents:
    - {connector: sql:main, metric: raw_events, lookback_days: 7}
  ```

- **Different time axes across an edge.** When a parent's datetime axis is an integer epoch (for example epoch-milliseconds with `precision: millisecond`, as the MQTT landing pipes in corpus A use) and the child's is a datetime, ledger ranges and watermarks are converted using the parent's `precision` before mapping onto the child's chunk grid. An edge can override this with `axis: {unit: ms}` when it can't be inferred.
- **Compaction.** Entries that every child has consumed get pruned.
- `Pipe.verify()` writes ledger entries for the chunks it repairs, so repairs flow downstream automatically.

### 5.5 Executor and scheduling

- **Dynamic ready queue** (Kahn's algorithm) on tokio. A node is *ready* when all of its in-selection parents have succeeded.
- **Concurrency limits:** the global worker count; per-connector semaphores (`system.engine.limits.connectors['sql:main'] = 4`); per-instance semaphores; the Python worker pool size.
- **Priority:** the critical path goes first. Each ready node's priority is its *upward rank*: its expected duration plus the largest upward rank among its children (the HEFT list-scheduling heuristic).
- **Durations** are an exponentially weighted moving average (EWMA, alpha 0.3) per `(pipe, action)` from run history, falling back to any action, then to a configurable default (§5.10). They are internal scheduling estimates.
- **CPM output.** The plan records the earliest/latest start and finish and the slack for each node, for priorities and optional forecasts (§5.9). CPM does not model worker or semaphore contention, so its times are never the default timeline.
- **Overlapping chunks.** In 5.0, edges at the pipe level are finish-to-start. During `backfill`, the executor may also plan at **(pipe, chunk)** granularity. This is off by default and enabled with `system.engine.chunk_pipelining` or `--chunk-pipelining` (R6).
- **Failures:** a node failure marks every descendant `upstream_failed`; independent branches keep running. Each pipe can have a retry policy (`parameters['retry'] = {max: 3, backoff_seconds: 30}`). `mrsm sync pipes --resume <run_id>` re-plans only the nodes that failed or never ran.
- **Leases.** Before running a node, the executor acquires a per-pipe lease (§5.8). Two jobs never sync the same pipe at the same time.
- **Continuous mode (replaces laps).** `--loop` starts a long-running engine. Root nodes run on their own cadence (`parameters['schedule']`, `--schedule`, or `--min-seconds`); a child is triggered when a parent's watermark advances or new ledger entries appear, with debouncing (`system.engine.debounce_seconds`). **`--loop --min-seconds N` on a flat selection behaves exactly as v4 laps did**: every selected pipe syncs, then the engine sleeps `N` seconds **after the lap ends** (`actions/sync.py:419`; an earlier draft of this spec said "after the lap began", which v4 does not do), with v4's error cooldown of `2*(N+1)` seconds. The lap engine is not shipped; the continuous engine reproduces its observable behavior for the job sysargs that corpus A runs (`-c`/`-m`/`-l`/`-t` filters, `-l _negation`, `-w 1`, `--min-seconds` from 20 to 604800).
- **Custom actions with `--loop`.** Plugin actions that implement their own loops (a function with a `loop` parameter) keep doing so; the engine does not wrap them. Every other action is repeated by the CLI's lap loop (§4.3, D26).
- **Pipeline loops (D26).** `sync pipelines NAME --loop/--listen` runs `Engine::run_loop` over the Pipelines' resolved members (`native::sync::run_continuous`, shared with `sync pipes --loop`), so a member with its own `schedule` syncs when it is due and a lap with nothing due records no run; `LoopOptions::run_name` names each lap's run after the Pipeline. The CLI re-reads the definitions every 30 s and, on a new revision, finishes its lap and restarts the loop with the new members; an edit it cannot run is retried like a failing lap. The Job's expected interval for health (§6.4) follows the schedules of its root members.

### 5.6 Streaming sources

Some sources push data continuously (MQTT, Kafka, AMQP, webhooks) instead of being fetched over a bounded window. They become a distinct node kind.

**Declaration.** A connector declares streaming support with `IS_STREAMING = True` and implements `subscribe(pipe, sink)`. Rust plugins do the same through the C ABI with a pull model: `subscribe` returns a handle, the host calls `next_batch(handle, timeout_ms)` (an Arrow batch, a timeout or the end) only after the previous batch reached the sink, acknowledges committed batches with `ack_batches` (tokens are scoped to their subscription: a token flushed after a resubscribe is dropped, never acknowledged on the new subscription), and calls `close_subscription` once; `subscribe` receives the same listen kwargs as a Python `subscribe`; these stream calls are not serialized with the plugin's other calls (`crates/meerschaum-plugin/src/subscribe.rs`). **Compatibility:** a Python connector that only implements the v4 pattern (a `sync()` that subscribes and returns immediately, with callbacks calling `pipe.sync()`, as the public MQTT connector plugin does) still works under `--listen`: the adapter runs its `sync()` in a worker, keeps the worker alive, and forwards each callback `pipe.sync()` to the native sync path. The engine supervises that worker the same way it supervises a `subscribe` stream (restart with backoff, throughput, Gantt lane). Upgrading the connector to `subscribe` is recommended but not required.

**Ingestion stays separate from transforms.** A stream source lands raw rows in its own pipe. Downstream transforms read bounded windows from that pipe.

**Micro-batching.** The engine-provided `sink` buffers rows and flushes on whichever trigger happens first:

| Trigger | Default | Purpose |
|---|---|---|
| `idle_ms`: no message for this long | 250 ms | A burst has ended, so flush now |
| `max_latency_ms`: age of the oldest buffered row | 2000 ms | Limits staleness, and limits loss for sources that can't acknowledge |
| `max_rows` / `max_bytes` | 5000 rows / 8 MB | Caps memory and transaction size |

Configured as `parameters['stream'] = {idle_ms, max_latency_ms, max_rows, max_bytes}`. `idle_ms: auto` sets the idle window from the moving average of gaps between messages, bounded by `[50 ms, max_latency_ms]`.

**Each flush** does one `sync`, writes one combined ledger entry per affected time chunk before committing its data, and emits a `watermark_advanced` event. Ledger writes for streams use the engine-state write path (§5.8), so a per-message flush costs one extra `INSERT`, not a full pipe sync.

**Durability: acknowledge after commit.** The source's own acknowledgement protocol provides the durable buffer. The sink contract is that `flush()` commits, and only then does the source's `ack(tokens)` run. MQTT: QoS ≥ 1, a persistent session, manual acknowledgement. Kafka: commit offsets. AMQP: `basic.ack`. Webhooks: respond after the commit. Delivery runs at the lower of the publisher's and subscriber's QoS, so the MQTT defaults must change to QoS 1 with a persistent session for engine-managed streams. Redelivered messages (MQTT `dup`) sync with `check_existing=True` even when the stream otherwise uses `--skip-check-existing`. The engine sets MQTT 5 *Receive Maximum* to at least `max_rows`, or caps `max_rows` at the broker's in-flight limit on MQTT 3.1.1. On a graceful stop the engine flushes and acknowledges before exiting. Sources that can't acknowledge lose at most one `max_latency_ms` window on a crash.

**Downstream triggering.** In continuous mode, a child of a stream source runs when the source flushes, rate-limited by its `min_seconds`. Late or backloaded data produces ledger entries for historical chunks, and children backfill exactly those chunks.

**One-shot runs.** `sync pipes --parents` never runs a stream source. The planner gives it the action `observe`.

### 5.7 Results, events and run history

- **`SyncResult`** is a subclass of `tuple` and stays `(bool, str)`-compatible. It adds structured fields: `inserted`, `updated`, `upserted`, `deleted`, `changed_intervals`, `duration`, `begin`, `end`.
- The **event stream** emits one typed event per transition: `run_started`, `node_planned`, `node_started`, `chunk_started`, `chunk_finished`, `node_finished{SyncResult}`, `node_failed{error, traceback}`, `node_skipped{reason}`, `node_rebuild_pending`, `watermark_advanced`, `stream_flushed{rows, bytes, trigger}`, `stream_restarted{error}`, `run_finished`. The CLI and the console render from this stream.
- **In Python (D26)**, a node result's `duration` (`RunResult.outcomes`, live `on_event` dicts and persisted events, top level and `payload`) is float seconds, converted at the façade (`_events.with_seconds`), so rows recorded earlier convert too; the engine's JSON (the HTTP event stream, stored `mrsm_engine_events` payloads) keeps serde's `{secs, nanos}` `Duration` shape, which the CLI live view, the TUI and `APIConnector`'s `EngineRunEvent` deserialize. Persisted events carry the live events' top-level keys and keep `payload`.

### 5.8 Engine state

**Principle.** The engine adds no database files to the root directory. Every piece of durable state lives **on the instance, as internal pipes**, following the pattern of `get_users_pipe()`, `get_tokens_pipe()` and `get_plugins_pipe()`: `Pipe('mrsm', <name>, instance=self, target='mrsm_<name>', temporary=True, static=True, ...)`.

| State | Persisted? | Where |
|---|---|---|
| Graph (edges) | No | Memory, built per run from a batch `fetch_pipes_keys` |
| Watermarks | No | Memory and the existing pipe cache |
| Definition hash | Yes | `mrsm:engine_state` pipe (primary key `pipe_ref`, upsert) |
| Dirty-range ledger | Yes, shared | `mrsm:engine_ledger` pipe (datetime `created`, ids `pipe_ref`, `seq`; columns `begin`, `end`) |
| Edge cursors | Yes, shared | `mrsm:engine_cursors` pipe (primary key `(parent_ref, child_ref)`, upsert; `seq`, `parent_watermark_at_cursor`) |
| Runs and per-node results | Yes | `mrsm:engine_runs` and `mrsm:engine_nodes` pipes |
| Events | Yes, batched, granularity configurable (`system.engine.events`, default `all`: chunk events included) | `mrsm:engine_events` pipe (datetime-partitioned) |
| Duration estimates | No | Memory, from `engine_nodes` |
| Continuous-mode timers | No | Memory; recomputed on restart |
| Per-pipe sync status (D26) | Yes | `mrsm:engine_sync_status` pipe (primary key `pipe_ref`, upsert), on the pipe's own instance |
| Leases | Yes, short-lived, atomic | See below |

On SQL instances, the targets live in the internal schema (`_mrsm_internal`, the schema v4 already keeps for its temporary tables, after TimescaleDB's internal schema) and inherit native partitioning, compression and maintenance. **Placement (wave 17b, closes GAP-001).** The instance connector names the state pipe (`InstanceConnector::engine_state_pipe(instance_keys, metric)`; the default keeps `mrsm_<metric>` beside the instance tables, so Valkey, API and custom instances are unchanged). On schema flavors (PostgreSQL family, MSSQL) the SQL connector sets `schema: _mrsm_internal` and suffixes the target with the instance schema when it is not the flavor's default (`public`, `dbo`): `_mrsm_internal.mrsm_engine_runs` for the default schema, `_mrsm_internal.mrsm_engine_runs_analytics` for a connector on schema `analytics`. A plain identifier of at most 15 characters is used verbatim; anything longer or with other characters becomes exactly 16 characters, its first (at most 7) characters lowercased with `_` for the rest, `_`, and the leading hex digits of its SHA-256, so the two forms never meet and every derived name (indices, partitions, MSSQL partition functions) stays under PostgreSQL's 63 bytes without v4's lossy truncation. Two instances sharing a database therefore keep disjoint state even when both are labelled `sql:main` in different configs. Schema-less flavors (MySQL, MariaDB, SQLite, GeoPackage, DuckDB, Oracle) keep the tables in the connection's default database, where v4's temporary tables go (v4's `internal_schema` is `self.schema`, `None` there). Leases need no namespace: the lease key is the resolved schema plus the pipe keys, never the connector label. **Retention** is `clear_pipe(end=now - system.engine.run_history_days)` (default 30 days) on runs, nodes and events; consumed ledger entries are pruned the same way. These pipes are `temporary=True` (never registered; `pipe.id` is `None` for them and nothing keys on it) and are excluded from the graph, `show pipes` and the planner. More generally, pipes with the connector keys `mrsm` (such as a saved Pipeline's registration) are left out of every listing and bulk selection on every instance type (`fetch_pipes_keys` implementations, `meerschaum_connector::{hides_internal_pipes, hide_internal_pipes}`) unless a connector key is exactly `mrsm`; registry reads by exact keys are unaffected (D26).

**Per-pipe sync status (D26).** Every sync path records its outcome for the pipe (C2 record: `pipe_ref`, keys, `last_attempt`, `last_success`, `last_failure`, `success`, `message`, `rows_inserted`, `rows_updated`, `rows_upserted`, `duration_seconds`, `consecutive_failures`, `source`, `job`) through `meerschaum_connector::sync_status` (in the connector crate because the server, which records data posts, does not depend on the engine), behind the trait methods `record_sync_status`, `get_sync_status` and `get_sync_statuses`. It is the one engine-state row a bare `pipe.sync()` writes: R1 still holds for the ledger, cursors, hashes and history. Failures count until a success; an outcome older than the latest attempt only moves `last_success` / `last_failure`. Reads match by connector and metric keys, filter the location in Rust (so no `'None'` string semantics apply) and re-key the rows under the instance keys they were read with. `mrsm` and temporary pipes have none, and `pipe_ops::forget_engine_state` (drop, delete, full clear) forgets it. Python: `pipe.get_sync_status()`, `mrsm.get_sync_statuses(instance=None)`; the console's Pipes table and Overview and the end of `show pipes` read it in one bulk read.

**Engine-state write path.** State pipes are written through `sync_pipe(check_existing=False, enforce=False, _check_temporary_tables=False)` with batching: ledger entries and events are buffered and flushed in one insert per node, and at most every `system.engine.state_flush_ms` (default 500 ms) in continuous mode. Cursor and definition-hash updates are single upserts. The cost target is **at most two extra statements per user sync** on a SQL instance. The sync status (D26) adds one read and one upsert per recorded sync, off the sync's path: `sync_status::record` returns at once and one background writer per pipe merges the outcomes queued meanwhile into one write, bounded by 3 s under the pipe's write lock and never failing the sync (errors are logged at debug level). Successes are debounced to one write per pipe per 5 s (the held one is written when the window ends, unless the pipe no longer exists); failures and the first success after a failure are written at once. A run waits for its nodes' queued writes before returning (held successes stay held, so `--loop` keeps its debounce), a read in the same process first settles that process's own writes for the pipes it reads (read-your-writes), and hosts call `sync_status::flush` before exiting (the CLI's `run`, `start api`, the extension's `atexit`). `sync_status::forget(pipe_ref)`, which `forget_engine_state` calls first, drops what the process holds for the pipe, waits for a write in progress and keeps the write lock while the row is cleared.

**API instances (R2).** The server refuses pipes with connector keys `mrsm` over the generic routes (today at `api/__init__.py:270`; the Rust server keeps that rule). Engine state travels over a dedicated `/engine` route family: `POST /engine/ledger`, `GET /engine/ledger?child_ref=&after_seq=`, `PUT /engine/cursors`, `GET`/`PUT /engine/state`, `POST`/`GET /engine/runs`, `POST /engine/events`, `POST`/`DELETE /engine/leases`. Writes require the `pipes:write` scope and reads (`GET /engine/runs`, `/engine/ledger`, `/engine/state`, the event stream) `pipes:read` (D26); every `/engine/*` route answers the v5 envelope (§7.1). `GET /engine/runs` takes `run_id`, `pipeline`, `pipe`, `status`, `since` and `limit` (`EngineBackend::get_runs(&RunsFilter)`; the instance store pushes `run_id`, the pipe's node rows, finished/running and `since` into its reads and pages newest-first only when it must check the rest itself), and `GET /engine/runs/{run_id}` returns one run with its nodes; a store that cannot be read is an error, never "no runs". **Sync status over HTTP.** `GET /engine/sync-status` (`pipes:read`, `?pipe_ref=`) and `POST /engine/sync-status` (`pipes:write`, what `api:` clients post) keep statuses on the server's instance under its own keys, and the client re-keys them with its `api:<label>` keys. v5 clients record their own outcomes and mark their data posts with `x-mrsm-sync-status`; the server records unmarked posts (older clients) with source `api`. **Run event stream (5.0).** `GET /engine/runs/{run_id}/events/stream` serves a run's typed events as Server-Sent Events (`event:` = kind, `id:` = `seq`, `data:` = the `Event` JSON), resumable with `Last-Event-ID` / `?after_seq=`, ending after `run_finished` or, for a run that will never send it, a synthetic `run_closed` (`reason`: `interrupted` when the record closed, `holder_gone` when the `mrsm:<host>:<pid>` holder names this host and a process that is gone and the run has been quiet for 2 minutes, `idle` after `?idle_timeout=`, default 15 minutes). Events published to the server process (`engine_stream::EngineStreams`: an `api:` engine's `/engine/pipes/engine_events/write` batches, and the engine runs of the server's own actions, forwarded by `meerschaum_engine::add_process_event_sink`, which carries each run's home instance) are delivered live to the streams of that instance; otherwise the stream tails the persisted `mrsm_engine_events` rows of the instance that keeps the run (`instance_keys`) every 500 ms. Same scope as `/engine/runs`; the console's `EventSource` authenticates by session cookie (`meerschaum-web` installs a `BrowserAuth`); streams are bounded by `api:permissions:log_streams`. `APIConnector::follow_engine_run` is the client; the Dash Pipelines page follows live runs with it instead of polling. **Engine-pipe primitives (wave 17b).** The engine reads and writes its state through its six `mrsm:engine_*` pipes (`InstanceState`), so an `APIConnector` routes exactly those pipes' `get_pipe_data` / `sync_pipe` / `clear_pipe` / `pipe_exists` to `POST /engine/pipes/{metric}/read`, `/write`, `/clear` and `GET /engine/pipes/{metric}/exists` (rows as `orient='records'` JSON, rebuilt with the pipes' static dtypes; reads need `pipes:read`, writes `pipes:write`; any other metric is a `404`, so `mrsm` keys stay closed on the generic routes). `start api` keeps all `/engine/*` state on the server's own instance (`meerschaum_server::engine_store::InstanceEngine` over `InstanceConnector::engine_state_pipe`, so on SQL in `_mrsm_internal`), the per-shape routes included, and leases go to that instance's lease pair; it survives a server restart. The in-memory backend remains for tests and builds without an instance and answers the primitives with `501`. Rows are keyed on the client's `api:<label>` pipe refs, so the client (not the server) forgets a dropped, deleted or fully cleared pipe's state.

**Write ordering (at-least-once delivery):** a parent writes its ledger entry *before* committing its data; a child advances its edge cursor only *after* its sync succeeds. Both are safe because syncs are idempotent.

**Leases** need an atomic acquire, so they are the one exception to "everything is a pipe". `InstanceConnector` gains `acquire_pipe_lease(pipe, holder, ttl)` / `release_pipe_lease(pipe, holder)`. SQL: `INSERT` into an internal lease table with a unique key on `pipe_ref`, success or duplicate-key error, conditional `DELETE` for expiry, heartbeat extends. Valkey: `SET NX PX`. API: the `/engine/leases` routes. Custom instance connectors that don't implement the pair fall back to the existing interprocess file locks with a one-time warning that the lease is machine-local.

**Read-only instances.** If engine state can't be written, the engine runs degraded: watermarks only, no ledger-driven `backfill`, no persisted run history, with a warning.

### 5.9 Visualization

**Plan versus Timeline (D24).** A *plan* shows dependency order, readiness, planned actions, bounds and the relevant worker limits; it has no required time axis. Optional forecasts label historical versus default estimates and their provenance. A *timeline* shows observed starts and finishes, elapsed time, concurrency, retries and live running intervals, distinguishing queued, skipped and successful work; estimated bars are never the default and never stretch the axis. Run history keeps its fields and snapshots the estimates made at the time instead of recomputing old forecasts from newer history. Terminal and console apply the same separation.

**CLI and shell Gantt:** on a TTY, an inline live region (one row per running node: chunks, rows so far, rows/s, attempt; plan decisions, retries and finished nodes printed above it into the scrollback; no alternate screen) while the run is in progress, with `w` opening the full-screen `ratatui` run monitor; elsewhere, line-oriented events. Both end with a static ASCII timeline summary. The same monitor is `mrsm watch run [RUN_ID]` (v5 action `watch`: monitors, where `show` prints once; `watch jobs` is the jobs and logs monitor) and the shell's F2 / F3 keys (`shell:keybindings`); it reads a run in another process from the persisted events (`after_seq`), and off a TTY `watch run` follows the events line by line until the run ends (or has had no new events for `--timeout` seconds, 600 by default, since a killed run is never marked finished).

**Console:** the `/dash/pipelines` workspace (§8.2): a canvas of connected Pipe nodes with an inspector, node-local output, a plan table and an observed-time Runs timeline, plus the Lineage tab of a pipe's page.

**Plain words (D26).** Text shown to users avoids engine jargon: planner reasons are sentences ("up to date: Pipe('sql:main', 'raw') has no new data (latest 2026-10-12 09:45)") with no ledger, cursor, watermark or "v4 sync" wording; plan rows carry `bounds_text` (the window in words, "last sync − 1 day → latest data") and `backtrack`; the plan table's first column is `pipe`; a run's message lists only non-zero counts in words ("3 synced, 1 up to date", "Nothing to sync."); a blocked pipe's `node_skipped` reason has no `upstream_failed:` prefix. ### 5.10 Planner and executor semantics fixed during implementation

The first implementation of `meerschaum-engine` (wave 2) and its wiring to real instances (wave 4) had to decide the following where §5.3–5.8 were silent. These are now part of the spec; the items marked **open** need a decision before a4 ships.

- **Provisional plans.** A child of a node that runs in the same run is planned against current state, marked `provisional` (`*` in the plan table), and re-planned by the executor when its parents finish.
- **Cap bound.** The cap is `min(parent watermarks)` plus one unit, matching Python's `get_chunk_bounds`, so rows at exactly a parent's watermark sync in the same run (`system.engine.inclusive_cap`, default `true`; v4 table parity needs it). With the key set to `false` the cap is the half-open `[.., min(parent watermarks))`, which the golden plan fixtures use.
- **`incremental` versus `backfill`.** If every unconsumed dirty range starts at or after `own watermark − backtrack`, the action is `incremental`; otherwise `backfill` over the dirty ranges plus the tail when the parent watermark also advanced.
- **First engine run (no cursor).** The parent's unconsumed ledger entries decide, exactly as with a cursor, including entries the parent wrote earlier in the same run (the child is re-planned when its parents finish): late rows inside the child's synced range do not move the parent's watermark, so a watermark comparison alone would skip them (wave 9). Only a parent with no ledger entries at all falls back to watermark comparison. Either way the new cursor is seeded at the parent's latest sequence number. If either side has no datetime axis, the child syncs once. Entries are only compacted once every child has a cursor, so the first graph run after a long flat-only history (with `system.engine.flat_ledger`) backfills every range those flat runs changed; that is the at-least-once price of not losing late data.
- **Pipes without a datetime column.** Unconsumed entries mean `backfill` over the full range; a watermark advance or a missing cursor means `incremental` over the full range. An entry with no interval dirties a datetime child's whole (capped) range.
- **Rebuild.** Bounds are `[None, cap)` and user `begin`/`end` are ignored; `rebuild` outranks `root`; a missing stored hash is a baseline (written after the first success, including on `skip`), not a change; hashes carry a `v1:` scheme prefix; interactive runs without `--yes` get `rebuild` plus `requires_confirmation`, and declining makes it `rebuild_pending`; a `rebuild_pending` node neither syncs nor advances cursors and its children treat it as idle.
- **Definition hash** is computed over the raw, unresolved `columns`, `dtypes`, `fetch` and `sql` as canonical JSON with sorted keys, so reordering YAML keys never triggers a rebuild. `columns` joined the hash in 5.0.0rc2 (a changed datetime column is a definition change; scheme `v2:`, and a stored rc1 `v1:` hash is compared with the rc1 inputs so upgrading rebuilds nothing).
- **`lookback`/`lookahead`** describe the child's dependency window: `lookback_days: 7` means the child's row at `t` reads the parent over `[t−7d, t]`, so a parent change in `[b, e)` dirties the child over `[b, e+7d)`. Keys: `lookback_{seconds,minutes,hours,days,weeks}` and `lookahead_*`, or a bare number (raw units on an integer axis, minutes on a datetime axis). These keys are stripped before the parent reference is turned into a `Pipe`; the Python façade must do the same.
- **`axis: {unit}`** names the parent's unit. Integer-to-integer edges convert only when both units are stated. An integer parent with no `precision` feeding a datetime child uses core's derived unit and the graph emits an `AxisUnitInferred` warning.
- **Capping and cursors use in-selection parents only.** Roots are never capped. Parents outside the selection are ignored and their cursors do not advance.
- **User `begin`/`end`.** Roots take them verbatim; every other node's bounds are clamped to them. A bound of the wrong kind for the node's axis is ignored with a warning.
- **Flat selections** (no `--parents`/`--children`) keep v4 semantics: every node, stream sources included, is `root`; no cursor or hash writes; no failure propagation; nodes are still ordered by edges, and a cycle becomes a warning with registration order as the fallback. In a non-flat selection a cycle inside the selection is an error; cycles elsewhere in the graph are irrelevant. Flat runs still write ledger entries (`system.engine.flat_ledger`, default `true`) so a later graph run sees what they changed, but never cursors or hashes. A flat lap orders unrelated pipes like v4's `ORDER BY connector_keys, metric_key, location_key`, with edges taking precedence. A lap that cannot resolve the graph is v4's exception path and gets the `2*(N+1)` cooldown.
- **Provisional propagation.** A provisional `skip` makes its descendants provisional too (otherwise a chain stops after its second level); provisional `rebuild_pending` and `observe` nodes do not.
- **Date bounds.** The node action coerces explicit `begin`/`end` and the instance's raw sync time like v4's `Pipe.parse_date_bounds` before subtracting the backtrack: UTC-aware for a UTC datetime column, naive for a naive one, epoch integers for an integer axis with `precision` (an error without it).
- **Self-references.** A `{{ Pipe() }}` reference to the pipe itself (the incremental `MAX(ts)` pattern) is ignored. Declaring oneself as a parent is a warning.
- **Ledger granularity.** One entry per contiguous run of occupied grid cells, not one min/max span per sync.
- **Cross-instance ledger writes.** The parent writes its entries onto every cross-instance child's instance (`Graph::ledger_instances`). **Open:** confirm this is preferable to the child pulling them on plan.
- **Unreachable state.** Failing to read a parent's watermark, cursor or ledger makes the child `upstream_failed`; failing to read the node's own instance is only a warning.
- **Compaction** never waits on children that have no cursor yet, and always keeps each pipe's newest ledger entry (otherwise the sequence restarts and children silently miss data). Retention by age applies to runs, nodes and events only, never to unconsumed ledger entries.
- **Write-path cost target** counts write statements: one ledger insert before the data commit and one cursor upsert after it; reads and metadata queries are not counted. **Open:** ledger sequence numbers are `max + 1` under the node's lease plus an in-process lock; an instance-side counter (connector trait method) would remove the read.
- **Planner actions** also include `upstream_failed` and `rebuild_pending`. Observed and `upstream_failed` nodes emit `node_skipped` with a reason.
- **State pipe columns.** `engine_state`: `pipe_ref`, `definition_hash`, `updated`. Ledger `begin`/`end` are typed `json` because a bound may be a datetime or an int. The full column lists for `engine_runs`, `engine_nodes` and `engine_events` are the serde structs in `meerschaum-engine/src/runs.rs` and `events.rs`; the spec defers to them.
- **Retries and leases.** `retry.max` counts retries after the first attempt with a fixed backoff; a lease time-out counts as a failed attempt; leases are renewed every `ttl/3`. **Open:** a lease lost mid-sync is currently ignored rather than aborting the sync. Instances without the lease method pair (SQLite today) use the file-lock fallback.
- **Run outcome.** A run succeeds when nothing failed, was `upstream_failed`, or never ran; `rebuild_pending` counts as success. On `--resume`, nodes that succeeded, were skipped or observed are planned `skip` but still count as parents.
- **Stream-flush triggering (wave 7).** In `--listen` / `--loop`, each `stream_flushed` of a supervised `subscribe` stream triggers an ordinary engine run over the stream and its **in-selection** descendants (the stream is `observe`; children read the ledger entries the flush wrote). A flat selection has no in-selection descendants, so it keeps v4 semantics and triggers nothing; `--listen --children` is the trigger configuration. The rate limit of a node is its own `parameters['min_seconds']`, else `system.engine.debounce_seconds`, else the loop's `--min-seconds`; a node inside its window is **held back together with its descendants** (`RunOptions::hold`) and runs on a later trigger, so a slow child never delays a fast sibling and never runs more often than its limit. Flushes that arrive while a trigger run executes, or while every child is held, are **coalesced** into one later run. Each trigger emits `children_triggered{run_id, nodes, held, flushes}`. A v4-pattern (`LegacyStream`) worker's callback `pipe.sync()` calls go through the engine's `LegacySink` (wave 9): each sync of a graph node writes its ledger entry before the commit and is a `stream_flushed` with trigger `callback`, so its children trigger the same way. `stream_flushed` gained `success`, `begin`/`end` (the changed rows' extent), `inserted`/`updated`/`upserted` and `message`; only committed flushes trigger. A callback sync of a pipe outside the graph stays a bare `pipe.sync()`.
- **Chunk events (wave 7).** `chunk_started` / `chunk_finished` carry `source` (`window` for planned windows, `fetch` for the pieces of a fetched frame, numbered in fetch order across the node's sync), `rows`, `begin`/`end` (a fetch chunk's smallest and largest datetime value), `inserted`/`updated`/`upserted` and `duration_ms` on finish; `total` (window chunks) on start. All fields beyond `chunk`/`begin`/`end`/`success`/`message` are additive with defaults.
- **Native source kwargs (wave 7).** `ConnectorRegistry::source_for_sync(keys, args)` receives the whole `SyncArgs`; `sync::sync_kwargs(args)` is the map Python plugins get (`extra` plus `begin`, `end`, `params`, `check_existing`, `enforce`, `force`, `workers`, `chunksize`, `retries`, `min_seconds`), and a registry building a native (C ABI) plugin source uses it for the fetch context.
- **Per-root schedule and debounce (wave 7).** `meerschaum_jobs::RootScheduler` keeps schedule state (last and next fire of a job's `-s` schedule, resumed across restarts while the schedule text is unchanged) and debounce windows under `{root}/.internal/{schedules,debounce}`, with no process-global state: two roots never share either, while processes on one root do (atomic under `flock`).
- **Schedules in graph runs (D26).** In a flat selection every pipe is a root for `parameters['schedule']`. In a graph run only pipes without in-run parents follow their schedule; a scheduled pipe with parents syncs when its parents have new data, and `cadence::ignored_schedules` reports it once per loop (`LapEvent::Warning`, printed by the CLI, which also carries invalid-schedule warnings) and as a plan warning (`Plan::warnings`, carried into `RunResult.warnings`).
- **Sync status sources (D26).** The source is `api` for the API server process (whatever runs in it), else `job` when `MRSM_DAEMON_ID` is set (with the job's name), else `engine` for a node of a graph run, else the process role (`cli` for the command line, `python` for the extension). An engine node records once, after its windows and retries; nested syncs of the same pipe (a plugin's `pipe.sync()` inside its own `sync()`, native host calls) are part of it (`SyncArgs::status_owner`). Skipped, observed, blocked and rebuild-pending nodes record nothing, nor does an attempt that never ran because another holder kept the lease (its node row says why); a stream that stops with an error records a failure. `InstanceConnector::sync_pipe_with_counts` (default: the counts parsed from the message by `pipe_ops::sync_result_from_message`; the `api:` client sums its server's per-chunk counts and keeps v4's message) is what the engine's sync flow calls, so statuses, `RunResult` totals and changed ranges are right on `api:` instances.
- **Replace mode (D26).** `SyncOptions.replace` with `begin` / `end` / `params`: the instance deletes the window and inserts the frame's rows of that window in one transaction (on SQL the `DELETE` is the first statement of the insert transaction, `COPY` included through `SqlDriver::copy_in_after`); rows outside the window are skipped and counted, and the message is `Replaced {deleted} rows with {inserted} rows.` (`result_from_message` reads both counts). The window rule is `meerschaum_connector::replace::resolve_window`, shared by the engine, the API route (`SyncKwargs`, `WindowBound::{FromRows, Unbounded, At}`) and the connectors' `sync_pipe` bindings: a missing `begin` is the rows' earliest datetime and a missing `end` just after their latest; without rows a missing `end` is unbounded after a given `begin`, and neither given is refused (`400` over HTTP); a pipe without a datetime column takes no bounds and replaces its table. The engine sets it from `pipe.sync(replace=True)`, `--replace` (`extra["replace"]`) or `fetch.replace`. A replacing fetch into an existing table is never split into row chunks, and its chunks are joined as columnar frames (`Frame::concat`); into a missing table, where nothing needs replacing, it streams. The ledger marks the whole replaced window widened to the chunk grid together with the delta's cells (`DeltaObserver::before_replace`, `InplaceObserver::before_replace`, `engine::sync::replaced_intervals`). In-place replaces insert only the staged rows that match the `DELETE`'s own `WHERE` (`replace_window_where`). Valkey clears the window and then writes (no transaction). **Open:** a child's window still ends at its parents' latest data, so rows a parent's replace removed from its newest window stay in its children until they are rebuilt or cleared.
- **Crash injection points (wave 9).** `FaultInjector::after_ledger_write` fires before each data commit, `after_data_commit` after each window's or flush's commit, and `before_cursor_advance` after a node's whole sync committed and right before its cursors and definition hash advance. `tests/crash_restart.rs` exits a child process at the first and last of these on SQLite and PostgreSQL-family (schema `w9_engine`) and proves after a restart that nothing is lost or duplicated and a re-run converges. An interrupted run leaves no run record.
- **Planned durations (wave 9).** A node's planned duration (its CPM duration and its Gantt bar) is the EWMA of its successful runs with the same action, else with any action, else `system.engine.default_duration_seconds` (default 30); a provisional `skip` is planned as an `incremental`. Planned durations are forecasts only (shown on request, never as the default timeline, §5.9) and always have an end; the run's node rows carry the value in memory and readers recompute it from the history before the run (the static `engine_nodes` schema has no column for it).
- **Crash and lease tests (wave 7).** Crash injection reaches stream flushes (`Engine::with_faults`). Lease contention is tested across processes on SQLite, PostgreSQL-family (schema `w7_engine`) and Valkey, including a killed holder that blocks only until its TTL; MQTT QoS 1 redelivery and a crash mid-flush are tested through both stream paths against a disposable broker gated on `MRSM_TEST_MQTT_URI`.
- **Golden plan fixtures are JSON**, not YAML as §14 first said.

### 6.2 SQL connector (D13)

- One `SqlConnector` type with a `Flavor` enum. Query building is per flavor and ported function by function from `connectors/sql/` and `utils/sql.py`, with the SQL golden tests in §10.2 as the acceptance criterion.
- **Drivers.** `sqlx` (`postgres`, `mysql`, `sqlite` features) for nine flavors; `tiberius` for `mssql`; the `oracle` crate for `oracle` (Instant Client required, as it is today); DuckDB's own `libduckdb`, loaded at run time through its C API (`MRSM_DUCKDB_LIB`, the `<root>/drivers` cache, the system path, a checksum-verified download on first use; nothing of DuckDB is compiled in) for `duckdb`. The `geopackage` flavor is SQLite with GeoPackage binary geometry encoding and `gpkg_*` metadata tables maintained by the connector, because corpus B uses GeoPackage files as instances. Connection pools are per connector, sized from the existing `pool_size` config. The SQLAlchemy URI format in `connectors.yaml` is parsed into driver options, so config does not change.
- **DuckDB in Python hosts.** A lazy host factory registered by `_native` applies to SDK connectors, embedded CLI actions, and registry-created connectors. Without `MRSM_DUCKDB_LIB`, an already installed `duckdb >= 1.5.6` provides the public driver transport; selecting a transport never installs optional packages. Raw SQL does not require SQLAlchemy or the Python driver; explicit `.engine` access retains its optional dependency installation behavior. Public duplicate connections share an anchor per canonical file, or an opaque identity per SDK memory connector, while preserving independent transactions and held SQLAlchemy connections. Canonical cached memory connectors also share with embedded commands. Conflicting connection settings, custom `creator` / `module` overrides, and `do_connect` routing listeners fail before opening a second instance. Standalone and base-only hosts retain the C API. Once native mode is selected, later SQLAlchemy access refuses with an actionable restart message; changing the driver override or reusing opened handles after fork also refuses. This is a D13 transport exception, not a second Pipe implementation; D16 raw SQL methods use the selected Rust connector transport; only explicit SQLAlchemy connections use SQLAlchemy execution.

- **Bulk loading** uses `COPY` on PostgreSQL, `LOAD DATA LOCAL` where enabled on MySQL, the bulk path on MSSQL, and row-batch inserts as the fallback. Row counts for `SyncResult` come from the driver.
- **Geometry** round-trips as EWKB on PostGIS, GeoPackage binary on `geopackage`, and WKB elsewhere. The `geometry[...]` dtype parser accepts every form found in the corpora: `geometry[MULTIPOLYGON, 6570]`, `geometry[3361]`, lowercase types, Z types (`LINESTRINGZ`, `MULTIPOLYGONZ`), `geometry[EPSG:4326]`, `geometry[ESRI:102003]`, and bare `geometry`. Spatial indices (`indices: {geometry: ...}`) create GiST on PostGIS and R-tree on GeoPackage.
- **Dtype aliases.** Pandas-style dtype strings in `parameters['dtypes']` (`int32`, `Int64`, `float64`, `str`, `datetime64[ms, UTC]`, `date`, `bool`) map to the same DB types as today. Role-keyed dtypes (`dtypes: {datetime: ..., id: ...}`) resolve through `columns` as today.
- `read` / `exec` / `exec_queries` / `value` / `to_sql` on the Rust connector serve the core, plugins and Python SDK (D16). Boundary adapters preserve bindings, SQLAlchemy constructs, result objects and frame conversion; `.engine` remains explicit.
- **Read errors raise (D26).** The SQL reads behind the `Pipe` methods use checked catalog queries (`pipe_state_checked`, `table_exists_checked`, `value_checked`, `sync_time_checked`), so `get_data`, `get_rowcount` and `get_sync_time` raise database errors; a missing table is still empty, and a table without the datetime column has no sync time (no query). The internal sync paths keep the swallowing reads on purpose (they decide table creation). The Python `read` / `exec` / `value` raise unless `silent=True`. On `api:` instances the client raises on transport errors and `5xx` answers and keeps v4's empty results for `4xx`; the server's rowcount route answers `500` when its instance cannot count (`pipe_methods::try_get_rowcount`).
- **NULL-safe upserts (D26).** Upsert tables of `null_indices` pipes keep v4's unique key, declared `UNIQUE NULLS NOT DISTINCT` on PostgreSQL 15 and later (`supports_nulls_not_distinct`), so a v4.1 process can still upsert into them. `upsert_conflict_target` reads the arbiter's key list from the table and whether it is NULL-safe (`indnullsnotdistinct`, or a `COALESCE` key from older v4 indexes). When it is not and a batch has a `NULL` key, `UpdateQueriesArgs::null_safe_upsert` splits the work: rows whose keys are all set take v4's `ON CONFLICT`, rows with a `NULL` key get `UPDATE ... FROM` (`COALESCE` equality, `IS` on SQLite) and then `INSERT ... WHERE NOT EXISTS`. MySQL and MariaDB always take their `<=>` statements, keeping `ON DUPLICATE KEY UPDATE` (or `INSERT IGNORE`) on the insert; MSSQL and Oracle `MERGE` already matched `COALESCE` keys. Before these statement paths run, a repeated key keeps its last row (`last_row_per_key`). Internal `mrsm` pipes and Citus keep v4's statements, and `golden.rs` stays byte-identical to v4.
- **SQLite in-place syncs (D26).** On SQLite and GeoPackage the definition is staged first, its datetime columns rewritten in the canonical stored text (`YYYY-MM-DD HH:MM:SS.ffffff`, what `to_sql` writes). The target is v4's `CREATE TABLE ... AS SELECT` when every staged column has a declared type, else a typed table (the staged declared type, else the pipe's dtype, else the values' storage classes) filled in one transaction. On existing tables the staged rows are canonicalized and the target's non-canonical rows inside the sync's window are rewritten first, so tables an older version created heal. `get_pipe_metadef_for_sync` compares the canonical form behind a coarse date range (keeping index use); the public `SQLConnector.get_pipe_metadef()` keeps v4's text. On MSSQL a `DATE` datetime column's backtrack end is the next day, with no minute arithmetic.
- **Null-like strings (D26).** `meerschaum_core::dtypes::null_marker_text_columns` (declared text columns, plus index columns whose dtype is text, object or unknown) keeps `'None'`, `'NA'`, `'nan'`, `'NaT'`, `'NaTz'`, `''` and `'<NA>'` as text in PostgreSQL `COPY` (`ColumnEncoding::keep_null_markers`), in literal `params` filters (`build_where_literal`, the kernel's `query_df` with `QueryOptions::literal_null_markers`) and in the existing-row diff (`FilterExistingParams` / `FilterUnseenOptions::literal_null_markers`). Python `None` stays `IS NULL` and `'_None'` `IS NOT NULL` on every column. Oracle stores `''` as `NULL`, so there `''` is a null in every column (`Frame::null_empty_strings`, `oracle_empty_string_params`). Valkey keeps v4's document keys, so a `NULL` index value and the text `'None'` share a key there.
- **`verify schema` (D26).** `InstanceConnector::get_pipe_schema_plan(pipe)` / `apply_pipe_schema(pipe, &plan, safe_only)` (defaults: unsupported) over the `meerschaum_connector::schema` types (`SchemaPlan`, `SchemaChange { kind: AddColumn | Widen | Change, blocked, ... }`). The SQL planner reads each column's full type per flavor, takes the declared dtypes (`dtypes`, role keys through `columns`, the missing `datetime` and autoincrement `primary` roles), classifies both sides (`TypeClass`) and never narrows: widenings are int to bigint, int to float, int or float to numeric, `varchar(n)` to text, text to json/jsonb and json to jsonb, and anything else is a `Change` (`ALTER COLUMN ... TYPE ... USING` on the PostgreSQL family, `MODIFY` on MySQL/MariaDB, `ALTER COLUMN` on MSSQL, in-place `MODIFY` or a temporary column on Oracle, a table rebuild that replays its indices on SQLite). Native types are never downgraded to a flavor fallback, columns are never dropped, and static pipes are included. A change the database refuses is blocked with its reason and left out of the statements, so the rest applies: a partition key's type (`TableFacts::partitioned_by` from `pg_partitioned_table`, `timescaledb_information.dimensions`, `information_schema.PARTITIONS`, `sys.index_columns.partition_ordinal`, `all_part_key_columns`, allowing what each database can change), a hypertable with compressed chunks, an indexed MSSQL column, an Oracle `NOT NULL` type change, a GeoPackage type change. `apply_pipe_schema` plans again, refuses a stale plan and runs in one transaction (MySQL and Oracle DDL autocommits, as its failure message says).
- **Row estimates (D26).** `InstanceConnector::get_pipe_rowcount_estimate(pipe, query)` (default: the exact count) reads `pg_class.reltuples` on the PostgreSQL family (a partitioned parent sums its partitions), `approximate_row_count()` on TimescaleDB, `information_schema.TABLES.TABLE_ROWS` on MySQL/MariaDB, `sys.partitions` on MSSQL and `ALL_TABLES.NUM_ROWS` on Oracle, and counts exactly when the flavor keeps no estimate (SQLite, GeoPackage, DuckDB, CockroachDB), with `begin` / `end` / `params` / `remote`, or when the estimate is missing or below 100,000 rows; a failing estimate falls back to the exact count.
- **Caller-supplied SQL on protected connectors (D26).** `meerschaum_connector_sql::readonly::is_read_statement(sql, flavor)` accepts one statement starting with `SELECT`, `WITH`, `VALUES`, `TABLE`, `FROM`, `SHOW`, `DESCRIBE` or `EXPLAIN` with no write word outside quotes and comments, read the way the flavor reads them (dollar quotes, MySQL backslash escapes and `#` comments; MySQL's `/*! */` is refused). `SqlConnector::read_raw` (the path for caller-supplied reads: `mrsm sql`, a Rust plugin's `host::read_sql`, the MCP `read_sql` tool) refuses other statements on a protected connector without the allowance (§6.5) and runs the read in `SqlDriver::begin_read_only` (`BEGIN READ ONLY` / `START TRANSACTION READ ONLY`, a plain transaction elsewhere), always rolled back. Oracle relies on the statement check and the rollback: its read-only transactions fail with `ORA-01466` on tables altered seconds before. The Python `read()` / `value()` use this same Rust path, except when the caller explicitly supplies a SQLAlchemy connection. A `sql:` pipe's own fetch definition is configuration and is not checked.

### 6.3 Templating and compose

- **`{{ Pipe(...) }}`** is parsed by a Rust template engine that reproduces `replace_pipes_syntax`: table substitution in SQL, attribute chains evaluated into parameter values (`{{ Pipe(...).columns }}` becomes a dict, `.dtypes`, `.target`, `.indices`), `instance=` arguments, `{{ self.metric }}`, `{{ self.location }}`, `{{ self.parameters['x']['y'] }}`. Evaluation is lazy and cached per run.
- **Compose** (`meerschaum-compose`) reads the same YAML: `project_name`, `root_dir`, `plugins_dir` (string or list), `plugins` with `name@api:repo`, `connectors` with compose host references (`'{sql:label}'`, `'{api:label}'`), `MRSM{...}` symlinks, `{MRSM_ROOT_DIR}` interpolation, `${ENV_VAR}` and `$ENV_VAR` from `.env`, `config`, `environment`, `sync.schedule`, `sync.pipes` (including the nested-by-mistake form, with a warning), `jobs`, `isolation: subprocess`, and the subactions `up`, `down`, `ps`, `logs`, `run`, `explain`, `init`, `sync pipes`, `start jobs`, `stop jobs`, `delete jobs`, `start api`, `--file`, `--env-file`, `--dry`. Project isolation keeps using a per-project root and environment variables. The `compose` plugin from the repository is detected and warned about, as today.
- **Project name (D24).** An explicit or effective `project_name` (including environment substitution) wins. Otherwise a custom filename names the project without its final `.yaml`/`.yml` (`/acme/metrics.yaml` is `metrics`), while the conventional `mrsm-compose.yaml`/`.yml` keeps the containing directory's name with its dots intact (`/acme/mrsm-compose.yaml` is `acme`). Each included file derives its own name from its own path; duplicate names in a composition stay a validation error. Compose keeps its unprefixed project-name tags. This changes the implicit identity of existing custom-named files (a documented migration note recommends an explicit `project_name` to keep the old one).
- **Lint.** `mrsm compose explain` reports unresolved `{{ Pipe() }}` references, misspelled parameter keys (`dtype:` for `dtypes:`), and string-typed `tags`, as warnings. It never changes behavior. Since rc2 it is also side-effect free (no root init, no cache file, no installs, no plugin fetches), lists every unresolved connector, instance, plugin and symlink as a finding and keeps going, and colors its output like v4.
- **Trees (D22).** Two additive top-level keys. `include:` lists compose files, directories (every `*.yaml`/`*.yml` plus `<dir>/*/mrsm-compose.yaml`) and globs (a string or `{path, required}`), resolved relative to the including file and transitively; a cycle warns and skips the edge, a file reached twice loads once. Included projects keep their identity (project name, plugins directory, relative paths and `.env`) and default `root_dir` to the including project's. Operations span the root and the included projects depth-first (includes first in listed order, `down` reversed, `--project <name>` limits to one). **The root wins** every override: `config` is deep-merged, `environment`/`.env` pass down, pipes match by `(connector, metric, location, instance)` and the root entry replaces the included one entirely, plugins match by name, jobs stay per project (a root overrides one with `<project>/<job>`), and plugin lookup is own `plugins_dir` first, then the ancestors'. `parent:` is an explicit path (no upward discovery): a subaction run in a file with `parent:` is `compose <sub> --project <this>` run from the parent (`--standalone` opts out); a parent that does not include the project warns and adopts it; chains are transitive and a cycle stops at the last valid level. Jobs started from a root carry `MRSM__COMPOSE_ROOT`; running a subaction directly in an included project leaves them alone unless `--force`. `-f/--file` is accepted anywhere in a compose command and `compose init -c/-m/-l/-t/-i` adds the matching pipes.
- **Ownership first (D26).** `up` checks the ownership of every job it would start before registering or syncing anything, and again before starting them; a `local` job that the project's systemd executor takes over is not deleted first (`JobOps::moves_to_systemd`). `--allow-protected` is forwarded to every command and job compose runs, like `--debug`, and is a non-identifying flag for job matching.

### 6.4 Jobs

- `meerschaum-jobs` supervises daemons with the same layout under `MRSM_ROOT_DIR/jobs/<name>/` (properties, pid, log rotation, stdin file), so jobs created on 4.1 are picked up and `show logs`, `attach`, `pause`, `stop`, `delete jobs` behave identically. Cron `-s` schedules keep the same grammar (names, ranges, `and`/`or`, `starting`). The systemd executor writes the same user units. The `api:` executor uses the same routes. Native plugins may declare further executor types (`executor_types` in the manifest, `<type>:<label>` keys accepted by `-e`, the shell's `executor`, configuration and the Python `Job`); the jobs crate resolves them through `JobsContext::with_executors` and a method the plugin leaves out reports "not supported by the '<keys>' executor". Each executor call carries the host's `mrsm` command and the jobs' `root_dir` (compose manages project roots from the host process). The server's `/jobs` routes stay local-only, as in v4.
- `Job(name).get_logs()`, `monitor_logs(callback)` and the job websocket keep their shapes.
- **Jobs versus execution workers (D24).** Console and Pipeline actions run as temporary execution workers on the same supervisor, distinct from persistent user-managed Jobs; a manually created one-shot Job is still a Job. Records state their kind, origin, owner, Pipeline identity and revision, run ID, parent Job and retention policy explicitly (new manual Jobs carry `mrsm_execution.kind = persistent_job`, even when named `execute-*`); security and retention are never inferred from the `execute-` prefix alone, the Pipeline identity is stored rather than parsed from run IDs, and legacy records keep working. Default Jobs views and cards exclude automatic workers; Runs (and each Pipeline) show active and historical executions.
- **Execution retention.** Automatic output is kept 24 hours after success and 7 days after failure, run summaries 30 days (`api.execute.retention.{success,failure,summary}_seconds`). Pruning runs at startup and in the background, never needs a new execution and never expires active work. Retained output links survive worker cleanup, and a temporary execution can be retained or promoted into a persistent Job. Retained execution Jobs reconcile unfinished run summaries and timeline endpoints after a reload; a worker's termination overrides stale running node events.
- **Startup gate (D23).** A job's worker is not started the moment its supervisor (or systemd unit wrapper) runs: the host first passes a per-root admission gate. Bulk and automatic starts wait a random `[0, jobs.startup.jitter_seconds]` (default 30) and while the 1-minute load average exceeds `ncpu * jobs.startup.max_load` (1.5) or available memory is below `jobs.startup.min_free_memory_percent` (10; Linux, a no-op elsewhere). Every start then takes one of `jobs.startup.max_concurrent` (default `max(2, ncpu/2)`) `flock` slots under `<root>/jobs/.startup/`, shared by every process starting jobs on the root (compose, local daemons, systemd) and freed when its holder dies. The slot is held until the first lap is done (`signal_first_lap_done`), the worker exits, it settles (idle under 10% of a core for `settle_seconds`, 15; Linux) or `slot_timeout_seconds` (300) pass; the wait is capped by the same timeout. Bulk means `start jobs` with several jobs, `restart jobs`, systemd restarts and compose (which sets `MRSM_JOB_START_KIND=bulk` in the child `mrsm`); an explicit single `start job x` skips jitter and the load wait but takes a slot; `--no-stagger` skips the gate. Per-job overrides live in the job's `startup` property (compose `daemon:`). Generated units get `RestartSec=5` (the wrapper applies the jitter, since `RandomizedDelaySec` is a timer-only key). **Schedule jitter** is off by default (`jobs.schedule.jitter_seconds: 0`); `-s '... jitter N unit'` or `--jitter N` give each job a FIXED offset in `[0, N]` (FNV-1a of the job name) so cadence stays stable while jobs spread out.
- **Executor selection (D26).** The configured executor, else `systemd` when it is available and this is not a development install (`meerschaum_jobs::job::is_development_install`: a debug build, a binary under a Cargo target directory, or the extension's source-checkout flag), else `local`; the root no longer matters. Unit names are per root: `mrsm-<job>.service` in the default root, `mrsm-<compose project>.<job>.service` (the project from the job's environment at creation) or `mrsm-<sha256(root)[..8]>.<job>.service` elsewhere, with the root's hash added to the scope when another root already installed that unit. A root lists the units of its own `systemd/services/<job>/` directories whose installed user unit links back to them, so roots never see each other's units. Units of non-default roots export `MRSM_ROOT_DIR`, and unit files are written `0600`. `create_job` migrates a `local` job of the same name (stop it, move `logs/<job>.log.*` to the unit's log, clean up keeping logs); `restart jobs` (no `-e`, a non-default root) and `compose up` trigger the move.
- **Job health (D26, C3).** The supervisor and the unit wrapper pass `MRSM_JOB_LAPS_PATH` (`jobs/<name>/laps.json`, deleted with the job). Looping workers (`sync --loop/--listen`, the generic `--loop`, `-s` schedules, repeated chains, `verify` / `deduplicate --loop`) record `run_started`, `lap_started`, `last_lap`, `last_success`, `last_failure`, `last_progress`, `next_lap`, `consecutive_failures`, `laps`, `lap_seconds`, `interval_seconds`, `stall_seconds`, `noun` and `message`, through one recording heartbeat per process (a nested loop leaves it to the outer one, and helper children never record); failures are written at once and successes and progress at most every 5 s, atomically, with URIs redacted. `Job::health()` (from the file for `local` and `systemd` jobs, from the job metadata's `health` for `api:` and custom executors), the Python `job.health` and the server's job metadata assess `stopped`, `stalled` (no lap end or progress for `max(3 × max(interval, lap_seconds), 60 s)` after `next_lap`; a fixed 3600 s for `--listen`; at least `FIRST_LAP_STALL_SECONDS` (3600 s) while the first lap runs, read as `unknown` / "first sync in progress"), `failing` (`consecutive_failures > 0`), `healthy` or `unknown`. `show jobs` adds the health to a job's status.

### 6.5 Protected connectors (D26)

- **The attribute.** `protected: true` on a connector, or `?protected=true` in any connector's URI (`meerschaum_core::protected::uri_marks_protected`; stripped before a database client sees it), makes `Connector::is_protected()` true (default `false`); Python reads it as `Connector.protected`.
- **The allowance.** `meerschaum_core::protected` holds `MRSM_ALLOW_PROTECTED`, the process-wide counted scopes behind `--allow-protected` and Python's `meerschaum.connectors.allow_protected()`, and the refusal text: "Refusing to <op> <target> on protected instance '<keys>'. Pass --allow-protected (or set MRSM_ALLOW_PROTECTED=1)." The CLI dispatcher holds a scope around each action run with the flag (`-y` never counts), Python workers receive the allowance with each call, the API host gets `MRSM_ALLOW_PROTECTED=1` when the server allows it, and jobs keep the flag in their sysargs. The allowance is process-wide, so in a long-lived shell or API process an allowed action also lets concurrent writes from other threads through while it runs.
- **Enforcement.** `meerschaum_connector::policy::{protected_refusal, check_protected}` guard every change through the core: sync (the engine refuses before it fetches from the source), register, edit (tags included), delete, drop, clear, deduplicate, `verify schema`, indices, compression and its policies, vacuum, repartition, the Valkey and API clients' writes (refused before any request), custom Python instances in the worker, `SQLConnector.exec()` / `exec_queries()` (`PermissionError`) and `to_sql()`, and caller-supplied SQL (§6.2). Reads and `analyze` are never blocked. Internal `mrsm` pipes are exempt, so logins, sessions, run history, sync status and saved Pipeline definitions keep working on a protected instance (a saved Pipeline's tag edits on member pipes are refused). A native plugin's host writes go through the same helpers.

## 7. Rust server (goal 4)

### 7.1 HTTP API

- `meerschaum-server` is an `axum` application with **every route** in `meerschaum/api/routes` at the same path, method, query and body shape: `/pipes/*` (keys, metadata, data, csv, docs, sync, register, edit, delete, drop, clear, exists, id, attributes, cache, chunk_bounds, columns/types, columns/indices, indices/names, rowcount, sync_time, size, vacuum, analyze, compress, decompress, partition), `/connectors`, `/actions`, `/jobs/*` and the logs websocket, `/users/*`, `/tokens/*`, `/plugins/*` (including archive upload), `/login`, `/metadata`, `/chaining`, `/info`, `/version`, `/healthcheck`, `/id`, `/favicon`, `/webterm` and its websocket, `/mcp`, and the new `/engine/*` family. The existing `APIConnector` test suite and the `api` test flavor are the acceptance test.
- **OpenAPI** is generated by `utoipa` and served at `/docs` and `/openapi.json`.
- **Auth.** OAuth2 password flow at `/login` issuing HS256 JWTs with the same claims and the same secret file in the root directory (`generate_secret_key()`), so tokens issued by 4.1 and by the API host validate on both sides. Scoped tokens keep their scopes, hashes and expiry. `ScopedAuth` semantics (route group scopes, `pipes:read`, `pipes:write`, `jobs:*`, custom scopes such as plugin-defined ones) are preserved. Password hashes are passlib `pbkdf2-sha256` modular-crypt strings, verified and generated with the `pbkdf2` crate using the same adapted-base64 encoding.
- **Permissions config.** `api.permissions.registration.users` is false after bootstrap unless explicitly enabled; `api.permissions.default_role` is Editor, and the shipped config does not grant non-admin action execution. `api.permissions.routes.allowlist` / route groups, `api.uvicorn.forwarded_allow_ips` (renamed `api.server.forwarded_allow_ips`, old key honored), and the `--production` / `--secure` / `--host` / `--port` flags keep their meaning. **New:** `api.permissions.rate_limits` per route group, so plugins no longer need HTTP middleware to throttle `/login`; and `api.permissions.routes.disabled` (D24), a list of route-group patterns that are not served at all, `login` included (which the allowlist never removes); a disabled path is never forwarded to the API host either, so it cannot reappear through host fallback. OpenAPI and the effective external endpoint surface reflect it.
- **Static files** at `/static`, `/assets` and plugin-mounted directories (via the API host) are served by `tower-http`.
- **Webterm.** The web terminal keeps its tmux session model (`api.webterm.tmux.session_suffix`), with the PTY bridge in Rust (`portable-pty`) and xterm.js served from `/webterm/assets/*` and embedded in the Dash console as an iframe (D21). `POST /execute/validate` authorizes the dashboard command without starting a worker; Exec submits it exactly once through the existing iframe terminal readiness/acknowledgment channel. Background Pipeline/Manage actions use `POST /execute` and `GET /logs/{name}/stream` (bearer or session cookie); `POST /execute` names the stream only when the server serves it (`null` with `--no-dash` or without the `jobs` routes, with `logs` as the alternative). **Its own tmux server (D26):** a dedicated server per root, on the socket `tmux.sock` in the webterm resources directory (`0700`; a short path in the temporary directory when that one is too long for a Unix socket), started with Meerschaum's `tmux.conf` (no status bar, mouse scrolling, a long history; written `0600`) or the file `api:webterm:tmux:config` names, never the user's default server. The API stops the server when it exits if this process started it; two API servers on one root share it.
- **Chaining.** `/chaining` and the parent/child instance chaining config are preserved.
- **One envelope for the v5 routes (D26).** `/pipelines*`, `/engine/*` and `/execute*` answer `{"success": bool, "message": str, ...}` with real status codes (`400` invalid input with `errors`, `401` / `403`, `404`, `409` conflicts, `429`, `500`, `501`). A middleware installed outermost (`meerschaum_server::envelope`) gives every error of those paths that shape (the router's `404` / `405`, the limiter's `429` with `Retry-After`, auth errors with `WWW-Authenticate`, validation errors, plain-text `500`s) and shows a `500`'s cause only to administrators (and `--no-auth`). Reads return named fields (`entries`, `state`, `runs`, `run` / `nodes`, `rows`, `exists`, `pipelines` as a list, `keys`, `id`, `attributes`). v4's routes are untouched (the contract replays pass unchanged), and the Rust `APIConnector` and the console read both shapes.
- **Saved Pipelines over HTTP (D26).** `GET /pipelines/{name}` (the definition, its members with `registered` true / false / `null` when their instance cannot be opened, and `last_run`), `POST /pipelines/{name}/plan` (read-only; `backends::PipelinesBackend::plan`, which the CLI implements by running `plan pipelines NAME -i REGISTRY --nopretty` with its output captured) and `POST /pipelines/{name}/sync` (a temporary execution job `sync pipelines NAME -i REGISTRY --run-id ID`, `mrsm_execution.origin = api_pipeline_sync`, shared with the MCP `sync_pipeline` tool; it answers `run_id`, `job` and the event `stream`). Sync needs `pipes:write`, `jobs:execute` and edit rights on every member it will change, plus access to the registry and each member's instance. Sync-locked members are skipped and their existing data remains available to children. `--secure` further restricts remote mutation to administrators. A Pipeline named `keys` or `leases` is not reachable through `GET /pipelines/{name}` (the static routes win).
- **Authorization fails closed (D26).** A failed read of a principal's scopes, user ID or token answers `503`, never "every scope" (`User::scopes_from_read` in core), on every instance connector: the Valkey connector's user reads return `ConnectorResult` (a missing key is `Ok(None)`), and the CLI's token scope cap (`native/tokens.rs::grant_cap`) refuses on a failed read. `start api --secure` reaches the console too: the host config carries the server's effective `actions_non_admin`, which the console's `is_session_authenticated` requires.
- **Rate limits (D26).** Entries take `{requests, seconds}` or `{max, window_seconds}` (the primary spelling wins; the window defaults to 60 s), keys are route groups or path prefixes (`/my-plugin`: longest prefix, segment-aware, one bucket per prefix), and every entry the server cannot use is a startup notice.
- **The public preset (D26).** `api:permissions:preset: public` or `start api --public` narrows the served route groups to `version` and, of `misc`, `/healthcheck` and `/favicon.ico`, plus explicitly allowlisted groups other than a bare `*`; `routes.disabled` still wins. It turns off the docs and `/openapi.json` (unless `docs` is allowlisted), the web terminal and user registration, prints a startup line, and tells the Python host (`MRSM_API_HOST_CONFIG.public`) to serve only the login page and plugin pages; the host gates `docs_url`, `redoc_url` and `openapi_url` the same way.
- **Decoded paths (D26).** Request classification (route group, path-prefix rate limit, `is_proxyable`, the console paths, the envelope) uses `routes::decoded_path`, the path percent-decoded once as uvicorn decodes it, so `/%64ocs` is `/docs`. Requests are still forwarded unchanged, and the server's own routes match the path as sent.
- **Row counts (D26).** `GET .../rowcount` takes `estimate=true` (`InstanceConnector::get_pipe_rowcount_estimate`, §6.2) and `?params=<JSON object>` when there is no body, and answers `500` when the instance cannot count.

### 7.2 MCP server

- Streamable HTTP at `/mcp` and stdio via `mrsm start mcp`, implemented in Rust with the same protocol version, the same tool, resource and prompt names, the same per-tool scope rule (a tool needs the same scope as its REST route and is omitted from `tools/list` otherwise), and the same read-only server mode.
- **Plugin tools.** Tools and resources registered from Python plugins with `meerschaum.mcp.tool(...)` / `resource(...)` are hosted by the API host (§7.3). The Rust server **federates** them: `tools/list` merges the host's registry (fetched once at startup and on manifest change), `tools/call` for a plugin tool is forwarded to the host with the caller's scopes. The Python `meerschaum.mcp` module keeps `tool`, `resource`, `get_tools`, `get_resources` and its registry so duplicate-registration guards in plugins keep working.
- **SQL guards.** HTTP `read_sql` scans the raw query as well as parsed identifiers: internal `mrsm_*` / `_mrsm_*` names, quoted names and literals, SQL-text functions and `U&` escapes are refused. This follows the native plugin host-call guard; local stdio MCP keeps its trusted local check. Hidden pipe targets and resolved pipe references follow the caller's visibility rules.
- **The v5 overlay (D26).** The registry is v4's generated `registry.json` plus an overlay (`mcp::v5`): eight tools (`list_pipelines`, `plan_pipeline`, `sync_pipeline`, `list_runs`, `get_run`, `list_jobs`, `get_job_logs`, `list_connectors`) with the scopes, annotations and output schemas of their HTTP routes, hidden and refused over HTTP when their route group is not served (stdio sees all); `begin` / `end` typed `["string", "integer"]` on every tool; `sync_pipe` graph syncs with `parents` / `children` (`McpBackend::sync_pipe_graph`, which the CLI implements with `sync pipes --parents/--children`); and an addendum to the primer (Pipelines, runs, jobs, connectors) in `initialize` and `mrsm://docs`. `list_jobs` and `get_job_logs` follow the job visibility of `/jobs` and redact credentials. The pipe tools (`resolve_pipe`, `register_pipe`, `list_pipes`, the `mrsm://pipes` resource) refuse or skip the internal `mrsm` pipes like the HTTP routes. `docs/zensical/reference/mcp/tools.md` is rendered from the Rust registry (`mcp::docs::render_tool_reference`; `scripts/generate_mcp_docs.py` runs the `mcp_docs` test), and the MCP contract test maps each served entry back to v4's before replaying the recording.

### 7.3 Python API host (D17)

Plugins extend the API with `@api_plugin` functions that receive a FastAPI `app` and add routes, middleware, static mounts and background threads. Corpus A adds about 116 routes and three middleware layers that way; corpus B adds 47 routes and a GZip middleware. These are Python objects and need a Python ASGI runtime.

- **Process.** `python -m meerschaum.api.host` starts a FastAPI app, runs every `@api_plugin` function against it in plugin order, and serves it with uvicorn on a Unix socket under the root directory. The Rust server starts it when the manifest shows any installed plugin registers `@api_plugin`, `@dash_plugin`, a Python `@web_page` or an MCP tool, supervises it like a job, and restarts it on crash. The Dash console (§8) is mounted inside this same app, and the host also starts whenever the console is available (D21). With no such plugin and no console, it never starts. On Windows the host listens on TCP loopback with a per-start token header instead of a Unix socket.
- **Routing.** The Rust server matches its own routes first. Every unmatched request, including websockets and streaming bodies, is reverse-proxied to the host with the path, method, headers, cookies and body unchanged. Plugin routes therefore keep their exact public paths. Plugin middleware applies to proxied requests only; Meerschaum's own routes are not wrapped by plugin middleware (the rate-limit config in §7.1 covers the case corpora used middleware for).
- **The `meerschaum.api` module** stays in the Python package as the host's surface: `app` (the host's FastAPI app), `endpoints`, `get_api_connector`, `get_cache_connector`, `production`, `debug`, `ScopedAuth`, `CurrentScopes`, `_oauth2.SECRET` (read from the same secret file), `_tokens.get_token_from_authorization`, the `models`, and `get_pipe`. `ScopedAuth` validates the same JWTs. `api_plugin` returns the decorated function unchanged so tests can call it against a bare `FastAPI()`.
- **Route lockdown.** `api.permissions.routes.allowlist` and `api.permissions.routes.disabled` (§7.1) are enforced on the Rust side by route group. A plugin that strips core routes by filtering `app.router.routes` by module name finds nothing to strip in the host (Python mutations cannot remove native endpoints) and migrates to `disabled`; the migration guide documents this, and the server logs a hint when the host exposes an `/mcp` or `/login` of its own. Namespaced plugin login routes stay supported through the host. Replacing an exact core method and path from a plugin is deferred and documented as a limit, not claimed as parity with arbitrary FastAPI mutation.
- **Dash sessions from API plugins.** `meerschaum.api.dash.sessions` (`set_session`, `get_user_from_session`, `get_username_from_session`, `delete_session`, `is_session_active`, `session_is_admin`, `EXPIRES_SECONDS`, `set_session_cookie`) stays in the package and reads and writes the console's own session store (§8.1), so plugins that mint sessions keep working, and plugin Dash pages see the same login state. `set_session()` and `update_session()` return whether they wrote.
- **Session IDs (D26).** A session ID is only the UUID the login mints (`str(uuid.uuid4())`): `sessions.valid_session_id()` gates every Python session read, write and delete (the cookie, `get_session_id_from_request`, the callback guard's `session-store` value, the helpers and the instance store's own `params` lookups), so a filter value such as `_None` can never match a stored session. This matches the Rust readers' `uuid::Uuid::parse_str` gate (`meerschaum-web`'s `cookie()`, the terminal's session lookup). The instance store's `params` filter must never see a non-UUID.
- **The callback guard (D26).** The host guards the one Dash app with a Flask `before_request` hook (`meerschaum/api/host/_callbacks.py`, installed by `mount_console()`). A `_dash-update-component` request needs an active session (the `mrsm-session-id` cookie, or the request's `session-store` value, then mirrored into the cookie in `after_request`) unless its callback is public. The callback's identity is the request's `output`, the key Dash dispatches by (`callback_map[output]`), so naming a public callback cannot run another; it is public when the function Dash calls, or one it wraps (`__wrapped__`), carries `_mrsm_public_callback`: the login callbacks, the registration callbacks during first-admin bootstrap or while `api:permissions:registration:users` is on, the page router (marked by its output `page-layout-div.children`, `ROUTER_OUTPUT`), the callbacks of `@dash_plugin(public=True)` (found by diffing `callback_map`, the `DashProxy` blueprint, `dash.callback` and the `dash_extensions` globals around the call) and `@web_callback(..., public=True)`. Without a session the answer is `401` `{"success": false, "message", "login"}` with `X-Mrsm-Login`; `assets/session_guard.js` wraps `fetch` and navigates to `/dash/login?next=...` (never from the login or registration form, at most 3 redirects per 30 s), and the login returns to a same-site `next` (`safe_next_path`). A console callback the renderer fires by itself (no changed input, or only unset ones) gets `204` instead. Callback API routes (`@callback(api_endpoint=)`) follow the same rule, and Dash's MCP server accepts a session or an API token. `api.dash.callbacks_require_session` (default `true`) and `--no-auth` turn the guard off. Flask routes a plugin adds to `dash_app.server` are not callbacks and are not guarded.
- **Helpers for `@api_plugin` (D26).** `session_user`, `optional_session_user` and `mount_static` (`meerschaum/api/_plugin_helpers.py`, exported from `meerschaum.api`). `mount_static(app, path, directory, auth=True, html=False)` wraps Starlette's `StaticFiles(follow_symlink=False)`: hidden path segments answer `404`, web content types are registered, `nosniff` is set, and `auth=True` needs a console session or an API token (`principal_from_authorization()` in `api/host/_auth.py`: a user JWT's `sub` through the user loader, or a `mrsm-key:` token; internal host tokens never count), sending browsers to the login page (`303`) and others a `401`. Reserved prefixes (`/`, `/dash`, `/static`, `/_pages`, `/_mrsm`, `/webterm`, `/docs`, `/redoc`) are refused.

### 7.4 Access model

`meerschaum_core::access` owns pure permissions, roles, teams, `PipeAccess`, locks and principal rules. Admin user types hold all permissions. Explicit scopes, including an empty list, take precedence over stored/default roles. Viewer, Editor and Operator presets are cumulative; Editor is the shipped default and Operator is required for actions and webterm. An explicitly configured legacy action grant maps the default to Operator. Tokens are intersected with the user's current permissions at request time. User-store failures deny access.

The first user becomes admin under a serialized bootstrap; registration is otherwise off by default. Teams live in an internal `mrsm:teams` pipe with UUID identity, unique names, member/manager roles and an implicit Everyone team. A primary team defaults new pipe/job ownership. Team renames and deletions rewrite pipe access, primary-team references and jobs; deleting users clears ownership.

`meerschaum_core::access` owns pure role and permission rules: Viewer, Editor (the default), Operator, Admin and explicit custom permissions. Empty custom permissions grant nothing. Legacy explicit scopes expand their previous grants; a token is intersected with its user's current effective permissions at each request. The server caches principals for at most five seconds and pipe access for three, and its own mutations invalidate those caches. Python mirrors the same decisions in `meerschaum.core.access`; database credentials remain the local trust boundary.

`parameters.access` stores owner, team, visibility (`team|private|everyone`) and edit mode (`team|owner`). HTTP, MCP and console enforce object visibility and edit rights, filter derived Pipeline/run/status/lineage data and anonymize hidden members. Only owners, team managers and admins manage access and locks. SQL definitions require `pipes:define_sql`; guards check internal and hidden targets before and after template resolution. Connector `teams` restrict use; direct DB credentials remain the isolation boundary. Email reads require self, admin or a manager of the target's team.

`parameters.locks` stores `parameters|sync|clear|drop|delete|all`. Shared connector checks re-read registered locks on every mutation; custom Python instance calls check at the façade boundary. Locks apply locally as well as remotely, with no force bypass. Schema changes are drop-class operations; replaced windows also need clear unlocked. Engine `Action::Locked` / `NodeStatus::Locked` skip those nodes without failing the run, allowing children to use existing data. Copies reset access and preserve locks. API/console-created jobs record owner/team; local jobs belong to Everyone.

The new access routes (`/teams/*`, `/users/*/permissions`, `/pipes/{keys}/access`, `/lock`, `/unlock`) use the common JSON envelope. Team administration belongs to admins; managers may update their team's members. A new remote pipe is stamped with the caller as owner and defaults to their primary team; only an admin may assign another owner. Saved Pipeline access is registered atomically with its definition, preserved on rename and reset on copy; copied locks remain in force.

Job visibility lives in `meerschaum_core::job_access`: team members, owner and admins see ordinary remote jobs; temporary console executions are limited to owner, team managers and admins. Parent jobs pass their ownership to child jobs. `owner` and `team` are file-owned properties so a supervisor cannot overwrite team changes with stale state. A launch ID and checks before/after startup distinguish a deleted or superseded launch; supervisors never recreate a removed job directory.

Native TLS uses `meerschaum_server::tls`: rustls with HTTP/2 and HTTP/1.1 ALPN, PEM validation before binding, certificate reload on content changes/SIGHUP and a loopback-only HTTP listener for the Python API host. Plain HTTP to a TLS port answers healthchecks and redirects other paths to HTTPS.

## 8. Web console (goal 5, D21)

The console is **v4's Plotly Dash app**, ported onto the Python façade and served by the Python API host. The original plan (5.0.0 pre-releases through rc1) rendered it from Rust (`askama` templates, HTMX, vendored Plotly.js/MapLibre/cytoscape.js); user feedback found it too basic next to v4, and D21 (5.0.0rc2) reversed it: that Rust console is deleted. Rust keeps the web terminal, the job-log stream and the pointer page; everything else on `/dash` is Dash.

### 8.1 Console

- `meerschaum/api/dash` (the v4 `pages/`, `callbacks/`, `assets/`, `components`, `keys`, `pipes`, `jobs`, `plugins`, `tokens`, `users`, `graphs`, `connectors` modules, with the deleted v4 internals replaced by façade calls) builds **one** Dash app lazily (`build_dash_app()`; importing `meerschaum.api.dash.sessions` from a plugin builds nothing). It is mounted at `/dash` in the API host (§7.3) with a2wsgi, at the same paths as v4: `/dash`, `/dash/pipes`, `/dash/jobs`, `/dash/plugins`, `/dash/users`, `/dash/tokens`, `/dash/login`, `/dash/register`, `/dash/password-reset`, plus the new `/dash/pipelines` (§8.2), `/dash/pipes/<keys>` and `/dash/pipes/new` (§8.2), `/dash/terminal` and `/dash/connectors`. Bookmarks, reverse proxies and `requests_pathname_prefix` assumptions hold: `/dash` with a command-builder query (`?action=`, `?connector_keys=`, ...) opens the Terminal page, and old pipe links keep working.
- **Shell (D26).** One top navigation (`components.build_pages_navbar`) on every console page: the logo opens the Overview; Pipes, Pipelines, Jobs, Connectors, Plugins and Terminal; a **Pages** menu of plugin pages by `page_group` (only when plugins add pages, since the logo's offcanvas page list is gone); the global instance selector (`pages-instance-select`, cookie `mrsm-instance`; the Terminal page's own is `instance-select`); and a user menu (Users & Teams, Tokens, Settings, Sign out). Items follow the router's `_paths` (the route allowlist) and the viewer's current permissions: Terminal needs `webterm:use`, Connectors needs `connectors:read` (both administrators-only under `--secure`); unavailable controls are hidden. The router renders pages inside `console_nav_context(pathname, session_id)` and rebuilds a module-level layout's navbar per request (`personalize_navbar`); the toggler is a clientside callback, so it works without a session. The current page is marked, the bar stays at the top, and on a phone it folds behind ☰ with 44 px rows. Plugin pages keep the plain bar (logo and Sign out, `build_plugin_navbar()`) unless `navbar=True`, and `skip_navbar=True` removes it. Icons are inline CSS-mask SVGs (`build_icon`), so no glyph depends on a font. No page has subtitles or helper captions, the theme is dark by default, and every page works at 390 px (no horizontal scroll, 44 px touch targets).
- **Overview (`/dash`, D26).** Per request (`pages/overview.py`, `overview.py`, `callbacks/overview.py`): tiles for the selected instance's Pipes (the count without internal `mrsm` pipes; failing from one `mrsm.get_sync_statuses()` read: `consecutive_failures > 0` or `success` false), Pipelines (`_saved.list_pipelines` and one read of the engine's runs: each Pipeline's last run), Jobs (the context executor's jobs, automatic runs excluded: running, stalled, failing and stopped from `job.health` and the recorded result, with the same state function as the Jobs page's `?status=`) and Recent runs (the latest run per Pipeline or target set, failures first, `×N` for a job that repeats it). One bulk read per tile, each tile its own callback with a 30 s refresh, unchanged tiles not redrawn, a read failure shown inside its tile. Every number links to its page filtered (`/dash/pipes?status=failing`, `/dash/jobs?status=stalled`, a Pipeline on its last run). An instance without pipes shows "No pipes yet" with New pipe and Open terminal inside the Pipes tile; the other tiles always render.
- **Terminal page (`/dash/terminal`, D26).** v4's dashboard moved unchanged (key filters, the command builder with action, flags and **Exec**, the Pipes, Jobs and Pipelines cards, the web terminal) apart from the navigation; `/dash/webterm` is the same page and `pages.dashboard.layout` the same object.
- **Connectors page (`/dash/connectors`, D26).** A read-only list (`connector_listing.py`) from the configuration (with the `default` label inherited), environment connectors (`MRSM_<TYPE>_<LABEL>`, `MRSM_CONFIG` / `MRSM_PATCH`), data plugins and connectors created at run time, with the source (Config, Default, Environment with the variable's name, Plugin, Runtime), the type and the flavor, host, port and database. An allowlist (`PUBLIC_ATTRIBUTES`: connection settings such as flavor, host, port, database, username, schema, driver, `sslmode`, timeouts and pool sizes) decides which values reach the browser; every other value is masked whatever its name, a group of settings is judged setting by setting, URIs and connection strings (`uri`, `dsn`, `connection_string`, `conn_str`, `odbc_connect`, `options`) are rebuilt from their public parts (`mask_connection_string`: the password runs to the last `@`, and a non-database type's URI path is masked because a webhook's path is its secret), secret-looking values are scrubbed from every shown field, and every masked value is scrubbed from connection-test errors. The page requires `connectors:read` (administrators only under `--secure`). Non-administrators see keys, type and source; connection attributes and **Test connection** are administrators-only, checked in the callback, with tests bounded by `connect_timeout` + 2 s. The API host's own `MRSM_API_HOST*` variables, which the environment layer reads as `api:` connectors, are hidden here and from every instance selector (`is_internal_connector`).
- **Jobs, Users, Plugins and Tokens pages (D26).** Jobs: **New job** (an action, a selection of pipes or a saved Pipeline, extra arguments, Once / On a schedule / Continuously, a name, and the equivalent command) creates a job in the API host with the context executor when it is `local` or `systemd`, else `local` (`CONSOLE_EXECUTOR_KEYS`); creating needs `is_session_authenticated` and the `jobs` route group, and a non-administrator's command is validated by `POST /execute/validate`. Every job has Start / Pause / Stop / **Restart** / **Delete** (typed name; a paused job is stopped first); the status dot and text come from the C3 health (§6.4), a stopped job counting as failed when its health reports failed laps or its result failed and it was not stopped by hand; past 8 jobs the tab is a compact table with a filter and a row menu (a list on phones), and `?status=` filters by state. Users & Teams: role presets and a custom permission grid, memberships, manager roles and primary teams; administrators create and edit users and teams, and team managers maintain their members. Instance user methods preserve unchanged attributes; a last-administrator guard and `end_user_sessions` apply after a demotion, password reset or deletion. Email fields are filtered to self, administrators and managers of a target's team. Plugins: an Installed tab read from the manifest caches and the plugins directories (no plugin import), and a Repository tab; Install, Reinstall, Update and Uninstall run as console runs (`execute-*` jobs, `mrsm_execution.kind = temporary_execution`), installs from the server's own repository through a job-scoped `api:this_server` connector, which on a `--private` server carries a 30-minute `plugins:read` token of the acting administrator. Tokens: a **New token** button; "Grant all scopes" starts on only for administrators and holders of `*`.
- **Packaging.** `pip install meerschaum[dash]` installs a working console (`dash`, `dash-bootstrap-components`, `dash-ace`, `dash-extensions`, `a2wsgi`, plus the `api` extra and `pandas`; §12.1). The base wheel stays dependency-free. The `full` Docker image carries it; the `minimal` image and `cargo install meerschaum` do not.
- **Serving.** The Rust server proxies every method and websocket upgrade on `/dash` and `/dash/*` to the host when the host reports (`GET /_mrsm/host/status`, `console.mounted`) that the Dash app mounted. The host starts for the console whenever a probe finds `dash`, `dash_bootstrap_components`, `dash_ace` and `a2wsgi` importable (a `console` reason beside the plugin reasons of §7.3); the host never installs them itself. Otherwise, and with `--no-dash`, `/dash` serves a static **pointer page** ("The web console comes with the Python package: `pip install meerschaum[dash]`"; 200 at `/dash` and `/dash/`, 404 below it; `--no-dash` is a plain 404) and one warning is logged.
- **Sessions.** Session IDs, the `mrsm-session-id` cookie, expiry and the session payload keep v4's shape. The hosted console always uses the instance through the users pipe pattern, so the Rust terminal and log stream share its store even when Valkey is configured. Lookups are cached per process for 5 s and dropped on logout. Only UUID session IDs reach the store (§7.3), and every callback is checked for a session first (§7.3). API plugins (`meerschaum.api.dash.sessions`), plugin Dash pages, the Rust webterm and the log stream all read the same store.
- **Execute console (D24).** Exec validates authorization with `POST /execute/validate` and submits the composed command exactly once into the existing, always-mounted webterm iframe, preserving its session, quoting and the selected instance; readiness/acknowledgment comes from the terminal, and a busy or disconnected session shows its state instead of interrupting or replaying. No other callback starts a second execution. The **Manage** commands (a dropup) of the Terminal page's pipe and Pipeline cards go through the same authorized webterm submission. A pipe page's actions (§8.2) and Pipeline Run/Sync actions start background runs through `POST /execute` and follow `GET /logs/<job>/stream`; there is no host-side execution fallback. Destructive actions preview and confirm before running with `--yes`.
- **Cards and terminal.** On the Terminal page, cards and the terminal are mutually exclusive: submitting a command selects the terminal, opening a card view hides it. Pipeline cards occupy one column and read only registered definitions (name, registry, member/instance counts, health, schedules, Open/Plan/Sync/Manage); execution history loads lazily on expansion, with no per-card history query or graph traversal on first render. Automatic worker cards and retained run summaries are the Jobs page's Runs tab (`/dash/runs`), in the same grid as Jobs (default Jobs cards exclude workers, §6.4).
- **Rendering rules (D26).** Dash's renderer slows down faster than the number of components one callback returns (in a bare Dash 4.4 app, 100 table rows of components took 4.3 s and 200 took 18 s, against 0.1 to 0.2 s as one HTML block), so long lists are one escaped HTML block in `dcc.Markdown` (parsed as JSX: `{`, `}` and newlines escaped too) or are paged small. A cycle of callbacks runs once per chain, and a callback whose inputs a pending callback writes waits for it, so follow-up work (the Pipes table's statistics) is requested in a new chain (`set_props` after a `setTimeout`). Under the console's `MultiplexerTransform`, a prop written by two callbacks (`allow_duplicate=True`) does not trigger the callbacks listening to it, so a store that drives other callbacks has exactly one writer. After `history.replaceState`, a `dcc.Location`'s `search` and `href` props are set to the new address, or the component pushes its old `href` back.
- **Callbacks on dynamic layouts.** Callbacks are scoped to their layouts or use genuinely optional Inputs with guards, so direct single-Pipe navigation, page switches and authentication changes never raise missing-Input errors (suppressing layout validation alone does not fix runtime Inputs).
- **Webterm.** The Terminal page embeds the Rust terminal (`/webterm/<session-id>`, assets at `/webterm/assets/*`) in an iframe, on the terminal's own tmux server (§7.1). No `tornado`/`terminado`.
- **Theme.** The dark/light theme and the `mrsm-theme-*` CSS classes keep their v4 names.
- **Windows.** The host listens on TCP loopback with a per-start token (`X-Mrsm-Host-Proxy-Token`) instead of a Unix socket (§7.3). Background execution remains subject to the platform Job backend; Exec uses the available webterm session.

### 8.2 Pipes and Pipelines pages

**Pipes (D26).** The Pipes pages follow the Pipelines pages' list-then-detail model.

- **The table (`/dash/pipes`).** One searchable, sortable table of the selected instance's pipes (internal `mrsm` pipes left out unless `-c mrsm` is asked for): `Pipe('ck', 'mk', 'lk')`, its row count (`pipe.get_rowcount(estimate=True)` where the façade accepts it, shown as `~1.2M` only for an estimate of at least 100,000 rows), the sync time, the C2 status (Synced N min ago, Failed N times with the error on hover, Never synced; a dash for a pipe with data but no recorded sync), tags, and the jobs that sync it. The jobs index comes from `get_jobs()` plus `parse_arguments` over `sync pipes`, `verify pipes` and `sync pipelines NAME` jobs, the `sync` / `verify` steps of action chains, and a job's own instance from its `MRSM_PATCH` / `MRSM_CONFIG` (compose projects put theirs there). Search (every word, over keys, targets and tags), the key, tag and `status` (`failing`, `ok`, `never`) filters and `q` live in the URL (`q` through `history.replaceState`, so typing adds no history entries); old `?connector_keys=&metric_keys=&location_keys=&tags=&instance=` links keep working. The table loads in two steps: the keys, tags and targets from one `fetch_pipes_keys` render first, then the statistics of the visible page (100 rows per page) are requested in a new callback chain and computed concurrently when the instance connector is thread-safe, with the statuses in one bulk read and 30 s caches; rows reload only when the instance or the key and tag filters change. Sorting by a slow column or filtering by status computes the statistics of every matching row (capped at 2,000). The table is one escaped HTML block (§8.1, rendering rules) whose rows link in place and whose sort headers call back through `assets/pipes.js`; on a phone the rows are cards with a Sort menu.
- **A pipe's page (`/dash/pipes/<ck>/<mk>[/<lk>]?instance=`).** A header with `Pipe(...)`, an instance badge when it is not the global instance, and **Sync**, **Verify**, **Edit** and **Manage** (Copy, Clear, Drop, Delete) for sessions that may act (`pipes_access`: read = a session or `--no-auth`; act = `is_session_authenticated`; edit, copy and register also need `pipes:write`, and register needs `api:permissions:registration:pipes`). The actions run through `POST /execute` and stream `/logs/<job>/stream` into an output panel; Clear, Drop and Delete need the metric key typed, Clear takes an optional Begin/End, Copy registers new keys with the same parameters (its own table) or copies to another instance with `copy pipes`. Tabs (`?tab=`): Overview (row count with an exact Count, sync time, the last sync and its message, target, tags, jobs, columns with dtypes and database types, indices), Data (recent rows, a query by params/begin/end, Download CSV), Parameters, Definition (a `sql:` pipe's SQL as written, `{{ Pipe() }}` templates kept), Lineage (parents and children, Explore graph) and Runs (hidden when the instance's engine runs cannot be read). The tabs reuse the pipe card's section builders (`meerschaum/api/dash/pipes.py`) and their callbacks; editing happens in Edit mode only, which never offers to save a resolved query. A read error says "Could not read <instance>: <error>" (secrets masked) and offers no actions; a pipe that is not registered offers **Register**, which opens New pipe filled in. Delete returns to the table only once the pipe reads as gone.
- **New pipe (`/dash/pipes/new`).** Mirrors `bootstrap pipes`: connector (the defined connectors and plugin connectors, or any typed keys), metric, location, instance; for a `sql:` connector a query editor and **Preview**, which runs the query through a temporary pipe's fetch path limited per flavor (`TOP` on SQL Server, `ROWNUM` on Oracle, `LIMIT` on a derived table elsewhere; `{{ Pipe() }}` references resolve on the chosen instance), fills the datetime and ID choices with its columns and guesses the datetime column. **Register** opens the new pipe's page and **Register and sync** also streams its first sync there; nothing is saved before. Preview and every sync of a registered SQL pipe read with the connector's credentials, which is documented as a policy: limit who may register pipes where that matters.

**Pipelines.** `/dash/pipelines` is the registered-Pipeline workspace (§5.2.1). Data comes from the engine bindings behind the `/engine/*` routes, in process. A pipe's page has the Lineage tab, and the Terminal page's pipe cards keep a "Parents & Children" section with two tabs.

- **List, then detail (revised 2026-10-26, 5.0.0rc14).** `/dash/pipelines` lists the Pipelines registered on the console's global instance (the registry; no page-level instance selector, and changing the global instance returns to the list) as one-column cards: name, member and instance counts (singular for one), last run, schedule, Open/Sync/Plan/Manage; history loads on expansion. **New pipeline** and **Find Pipe** sit above the list; Find Pipe opens a read-only connected-graph canvas at `/dash/pipelines/explore?pipe=…` with **Save as Pipeline**. `/dash/pipelines/<name>` is one Pipeline: a header (`Pipeline('name')` with its registry badge; Sync, Plan, Edit and a Manage dropup with Analyze/tags, Schedule, Copy, Rename, Clear, Drop, Delete) over **Canvas** and **Runs** tabs; Runs is scoped to that Pipeline (all runs live on the Jobs page's Runs tab). Legacy `?name=&run=` links redirect. No subtitles or helper captions: a page that seems to need one is redesigned.
- **Canvas.** Only explicit members are drawn at first; traversal Pipes collapse into expandable "+N upstream" / "+N downstream" nodes, and large Pipelines (over about 25 nodes) start grouped by connector. Expansion, zoom and pan are remembered per Pipeline in the browser; a shared layout is saved only from Edit mode. Members on other instances carry instance badges. Clicking a node opens the inspector as a right-hand drawer (a full-screen sheet on mobile) with an Open Pipe card link. Dragging never selects page text or fires an accidental node click; query and output text stay selectable. Every context menu has keyboard and touch alternatives. Fullscreen holds the canvas tools, inspector and output; Escape restores the previous view.
- **Creating and editing.** `/dash/pipelines/new` is a stepper mirroring `bootstrap pipelines`: Name (registry shown), Members (search existing Pipes on any instance, or register one inline with keys, instance and optional parameters JSON), Traversal (parents/children and depth), Review (plan preview, missing-reference and cycle checks, the exact `pipeline-{name}` tag changes with an "Apply these tags" checkbox, ticked by default, beside Create: the visible list plus Create is the approval), Create (lands on the detail page). Nothing is persisted before Create. An existing Pipeline is read-only until **Edit**: Edit mode shows Save/Discard/Undo/Redo, a Draft badge and the unsaved-change count, confirms before leaving, and checks the revision on save; Add Pipe uses the stepper's member panel, a node menu offers Remove from Pipeline, and dragging between nodes proposes a `parents`/`children` edge applied on Save. Unfinished stepper and Edit drafts persist in the browser with Resume draft / Start over.
- **Actions.** Background right-click/Add offers an instance-aware existing-Pipe picker and new-Pipe registration. Node menus and the inspector offer Sync this Pipe plus explicitly scoped parent/child syncs (scope and bounds shown); a single-Pipe run uses the same execution protocol without pretending to run the whole Pipeline. Node status: queued, running (spinner, reduced-motion aware), succeeded, failed, skipped, blocked.
- **Inspector.** Opens and highlights immediately; expensive sections load lazily, keyed by selection ID so stale responses never overwrite the current selection, with per-section retry. Query has a toggle (labelled Resolve symlinks) that shows the query with its `{{ Pipe() }}` references resolved, like the pipe page's Show resolved query switch (same defaults and errors, resolved in the member's instance; it changes only the displayed SQL). Editing goes through the ordinary Pipe editor.
- **Drafts and edges.** Membership and dependency edits are drafts with Save/Discard, undo/redo, unsaved-change indicators and revision-conflict detection. Saved layouts are shared metadata; the viewport is personal; historical runs stay distinct from editable state. Editing an edge edits real shared Pipe parameters and previews which Pipes change; cycles are validated; explicit `parents`/`children` declarations are drawn distinct from inferred `{{ Pipe() }}` references, and removing an inferred edge means editing its query. Removing a node removes membership only; dropping data or deleting the Pipe are separately named actions. Pipeline deletion requires a confirmation naming the Pipeline and registry, validates that identity and revision, preserves member Pipes, data and history, and refuses definitions referenced by scheduled Jobs; success clears the selection and live output, cancel changes nothing.
- **Output.** Run now selects its new run and opens output on the canvas as a closeable full-size drawer (the Output pane on mobile); View output reopens retained output; closing never cancels. Each node has an accessible output control. Pipe output and whole-Pipeline output are separate, explicitly attributed modes; lines are attributed by run, Pipe, attempt and sequence at emission time, never by matching interleaved text. Logs name the Pipeline, run ID and worker status. Output has no heading or expansion toggle, its close button sits on the right, cancellation (targeting that run only) is offered only while it is active, ANSI colors render as escaped HTML, and scrolling follows until the user scrolls up. A live worker's status may override only its own run, never a selected historical one.
- **Plan and Runs.** The plan table (§5.9) uses Pipe representations, with the planner's sentence in a Reason column and the window in words (`bounds_text`) in a Window column; run counts read "2 synced, 1 up to date", the canvas counts dependencies, Pipeline cards count the Pipes a Pipeline syncs ("3 Pipes", or "1 Pipe + children" before its first run), and the run log reads "Synced Pipe(...): 1,200 inserted" instead of event names. The saved-state overview has columns for identity, explicit members and latest run. Runs shows observed intervals across recent runs; selecting a run or stage uses local Dash state and never navigates or resets the canvas, while URL query parameters stay supported for deep links. History links keep the registry, name and requested run through dropdown hydration, refresh and polling, and polling keeps the selected run; choosing another Pipeline clears the run. Empty history, an unknown run ID and a run of another Pipeline get distinct explanations with a return-to-recent-runs action. Plotly keeps hover and selection but has no export/image-download control, drag or wheel zoom, or double-click reset (unrelated data exports stay).

### 8.3 Plugin pages (the page contract)

The page contract is language-neutral and is kept: a plugin page may be **HTML** instead of a Dash layout, and the Dash console frames it. The contract is the same for Rust and Python plugins:

- **Figures (D19).** A fragment embeds a chart as `<div data-mrsm-figure='<Plotly figure JSON>'></div>` (or references a route that returns the JSON). The contract's JS layer renders every such element with Plotly.js, on load and after each HTMX swap. Python plugins build figures with `plotly.py` and emit `fig.to_json()`; Rust plugins build them with the `plotly` crate. Corpus A's figures (about 160 `go.*` constructions across 19 files) carry over unchanged.
- **Maps.** `<div data-mrsm-map='<GeoJSON or layer spec>'>` renders with MapLibre GL JS, loaded on demand. This is the replacement for dash-leaflet in new pages.
- **Interactivity** is HTMX against plugin routes (Rust `api_routes`, or a Python `@api_plugin` route through the host). No component tree, no callback graph.
- **Registration.** Rust plugins declare `web_pages` in their manifest and render them with the `page` call (§9.1). Python plugins use `@web_page(path, login_required, skip_navbar, page_group, dark_theme, theme, head, navbar)` on a function that returns a string (or a `(html, status)` pair). `@web_page` on a function that returns a Dash layout is the Dash page model (§8.4).
- **Themes and head tags (D26).** `theme` is `'dark'` / `'light'` (aliases darkly / flatly) or a stylesheet URL, and `dark_theme` resolves from it (the stored page entry still carries a `bool`); `head` takes HTML strings, dictionaries (`tag` in meta / link / script / style / noscript, attributes escaped) or Dash components, and `add_head(*tags)` adds tags to every page (unloaded with its plugin). For Dash pages the host overrides `dash_app.interpolate_index` (`meerschaum/api/host/_page_heads.py`; a plugin's `index_string` still applies) to add the `add_head()` tags and, when needed, an inline script at the end of `<head>` that, per path (longest prefix), points `#mrsm-theme-dark` and `#mrsm-theme-light` at the page's stylesheet (so the per-route toggle still enables exactly one), adds the page's non-script tags while it is open and its scripts once, following `pushState` / `popstate` / `_dashprivate_pushstate`. Page-contract documents take both server-side. `navbar=True` gives a page the console's navigation (§8.1).
- **Rendering.** The bare plugin route stays the fragment. The console shows the page at `/dash/<path>` as an iframe of `/_pages/<path>?frame=1`, a full document carrying the theme, HTMX, `contract.js` and the figure/map layer. Native Rust plugin pages are fetched by the host as fragments from the Rust server (`GET /_mrsm/native-pages/{path}`, internal token plus `X-Mrsm-User`) and framed the same way. The navigation's Pages menu lists every plugin page by `page_group`, whichever mode serves it.
- **Assets** are vendored and never loaded from a CDN, because corpus A runs on cellular edge hardware: Dash's own bundles, the contract layer (`meerschaum/api/resources/static/contract/`: HTMX, `contract.js`, MapLibre) and Plotly.js from the installed `plotly` package; xterm.js in `meerschaum-web`.

### 8.4 Dash plugins

Plugins add Dash pages with `@dash_plugin` (which receives the core `dash_app` and registers callbacks, mutates `index_string` and `external_stylesheets`) and `@web_page(...)` returning Dash layouts, exactly as in v4. Corpus A registers 23 pages and refers to core component IDs (`session-store`, `mrsm-location`, `mrsm-theme-*`) in 190 places; corpus B registers 4 pages with dash-leaflet.

- **One app.** Plugins register into the one core app at the v4 paths (`/dash/<path>`), so core IDs, core stores, `dash.sessions.*`, `dash.components.build_cards_grid`, `keys`, `pipes` and `graphs` behave as in v4, and a plugin can patch core pages by component ID again. `make_dash_app()` / `get_dash_app()` remain as aliases of that app.
- **Custom applications.** `web_page('login', ...)` overrides, custom Dash callbacks, sessions, redirects and sign-out keep working in the one shared app; with `api.permissions.routes.disabled` (§7.1) an application replaces the native login surface entirely.
- **Public callbacks (D26).** Plugin callbacks need a session like the console's own (§7.3). A page anyone may open marks the callbacks its visitors run with `@dash_plugin(public=True)` (every callback the decorated function registers) or `@web_callback(..., public=True)`. `@web_callback(*deps, public=False, output=None, inputs=None, state=None, **kwargs)` registers a callback at the plugin's top level, immediately when the console exists and otherwise deferred through `_dash_plugins`; `output` / `inputs` / `state` take `'id.property'` strings so the plugin need not import Dash. Bare `@dash_plugin` is unchanged. The console's own new callbacks are never public; any shell callback that fires by itself with a set input on a public plugin page must be public or clientside.
- **Assets.** A plugin's `assets/` is served at `/dash/_plugin-assets/<plugin>/` and its css/js is loaded by the console.
- **rc1 URLs.** 5.0.0rc1 mounted a Dash app per plugin at `/dash/<plugin>/`. Those URLs redirect (307) to `/dash/<rest>`; the per-plugin shim is gone.
- **Status.** Maintained for the life of 5.x. The console tracks Dash majors: the `dash` extra sets a floor (`dash>=4.1`) and the Playwright suite (§14) drives the real console.

## 9. Rust plugins (goal 7, D1)

### 9.1 Contract

- A plugin is a `cdylib` that exports `mrsm_plugin_v1() -> *const MrsmPluginV1`, a static `#[repr(C)]` table: a permanent prefix `abi_version: u32`, `struct_size: u32` (the host reads only these before rejecting an incompatible or truncated table), then three function pointers: `describe() -> CallResult` (name, version, ABI version and the plugin's worker-shaped manifest as JSON), `invoke(request: Bytes, input: *mut FFI_ArrowArrayStream, output: *mut FFI_ArrowArrayStream) -> CallResult` (one entry point for every operation) and `free_bytes(OwnedBytes)` (the plugin frees every payload it allocated; the host never does).
- **Requests** are one UTF-8 JSON envelope `{method, connector_type, label, config, context}`; `method` selects the operation (`fetch`, `sync`, `action`, `pre_sync_hook`, the instance methods, `api_route`, `mcp_tool`, `mcp_resource`, `mcp_prompt`, `page`, ...) and `context` carries pipe keys, parameters, begin/end and kwargs. New operations are new method names, not new table fields, so they never change the ABI.
- **Data** crosses the boundary only as `FFI_ArrowArrayStream`: the input stream is moved into the plugin, and `fetch` writes the output stream.
- **Errors** come back as a status (`0` JSON result, `1` error, `2` caught panic, `3` unsupported method) plus owned UTF-8 bytes. Panics are caught with `catch_unwind` at every boundary.
- **Optional extensions** are separate exported symbols, so v1 libraries without them keep loading: `mrsm_plugin_invoke_host_v1` (the same call plus a versioned table of synchronous host callbacks, valid only during the call) and `mrsm_plugin_invoke_rows_v1` (JSON rows for single-file plugins).
- **Capabilities are declared in the manifest** (`describe`), so the host lists actions, flags, hooks, connector types, routes, MCP entries and pages from the cached manifest without loading code, and loads the library on first use.
- **Server extensions.** Routes are the manifest's `api_routes` (`{name, method, path, scopes, public}`; any method or `*`; Starlette path syntax: one `{param}` per segment with an optional static prefix and suffix and an optional `int` / `float` / `uuid` / `str` converter, and a final `{*rest}` or `{rest:path}`), served by the `api_route` call: the context is the whole request (method, path and query parameters, headers without credentials, the body base64-encoded, the authenticated principal and its scopes) and the reply is `{status, headers, body_base64}`. The server checks credentials and the declared scopes before the call and refuses at startup a route that would shadow a core route (including the console's `/_pages`) and a `public` route that declares scopes. The four server calls are not serialized with the plugin's other calls (like the stream calls): they run concurrently on blocking threads, at most 32 per plugin with a 30 s queue that then answers `503`, so plugins must make them thread-safe. Routes and MCP entries are read when the server starts. MCP tools, resources and prompts are the manifest's `mcp_tools` / `mcp_resources` / `mcp_prompts`, served by `/mcp` and `mrsm start mcp` through the `mcp_tool` / `mcp_resource` / `mcp_prompt` calls, with the same scope and read-only filtering as built-in tools and arguments validated against the plugin's input schema. Pages are the manifest's `web_pages`, rendered by the `page` call as HTML fragments under the page contract (§8.3), with figures as Plotly figure JSON. These are the Rust-native equivalents of `@api_plugin`, `meerschaum.mcp.tool(...)` and `@web_page`, served by the Rust server with no host process. Native HTML pages never run Python Dash callbacks; they are fetched by the Dash console (`/_mrsm/native-pages`) and framed (§8.3), so they appear in the console only where the Python console runs. Plugins from before `api_routes` (an `api_plugins` name plus `routes` / `route` methods with static paths and text bodies) keep working.
- The `meerschaum-plugin` crate hides the `unsafe` code: a plugin implements the safe `Plugin` trait (`manifest`, `fetch`, `sync`, `api_route`, `mcp_tool`, `mcp_resource`, `mcp_prompt`, and `call` for every other method) and exports it with one macro; there are no attribute proc-macros in the Cargo SDK (single-file plugins get attribute spellings from the host-generated adapter):

  ```rust
  use meerschaum_plugin::prelude::*;

  #[derive(Default)]
  struct Noaa;
  impl Plugin for Noaa {
      // The name and version are the Cargo package's; `const NAME` / `VERSION` override them.
      fn manifest(&self) -> Value { Manifest::new().fetch().into() }
      fn fetch(&self, request: &Request) -> Result<Option<Frame>> { … }
  }
  meerschaum_plugin::export_plugin!(Noaa);
  ```

- **Manifest builder (D26).** `export_plugin!` exports a vtable whose `describe` passes the invoking crate's `CARGO_PKG_NAME` / `CARGO_PKG_VERSION` (`Export::describe_package`); `Plugin::NAME` / `VERSION` default to `""` and `manifest()` to an empty `Manifest`. The `Manifest` builder (`.fetch()`, `.sync()`, `.action(name, doc)`, `.flag(...)`, hooks, `.connector(ConnectorType::new(...).instance().streaming())`, `.executor_type(...)`, `.api_route(RouteSpec)`, MCP entries, `.web_page(...)`, `.required(...)`, `.set(key, value)`) declares capabilities, and `meerschaum_plugin::manifest::complete` fills only what is missing (the envelope, `schema_version`, this SDK's `meerschaum_version`, `python_version`, the fingerprint, the entry's name and version, connector and executor types' `plugin`, the top-level hook lists). Complete hand-written manifests load unchanged, and the loader still compares `plugin.toml`'s name and version with the package's. `FrameExt::{from_rows(rows, dtypes), to_rows()}` builds typed frames from JSON rows over the kernel's dtype enforcement, so plugins need no `meerschaum-kernel` dependency; the SDK re-exports `chrono` and `indexmap`, `Bound` gains `as_int`, `as_str`, `to_datetime` and `From` conversions, and `meerschaum_plugin::prelude` brings in the common names. `bootstrap plugins` generates crates this way.
- **Host calls (D26).** The `HostV1` host-call extension carries a JSON envelope `{"method", "pipe", "args"}` in its method bytes (bare names keep meaning `get_sync_time` / `sync` on the request's Pipe, as every older host understands), and the call's Arrow stream is in/out: the host moves the plugin's frame out and may write its result frame back in its place (`get_data`, `read_sql`). Unknown methods answer status 3 and the SDK maps that to an upgrade message, so no ABI version bump is needed. The rows ABI host callback takes the same envelope plus `data` rows. Methods (`meerschaum_plugin::callbacks::method`): `get_sync_time`, `sync` (optionally `{"replace": true, "begin", "end"}`, a `null` bound meaning "from the rows"), `get_data`, `get_rowcount`, `clear`, `get_columns_types`, `exists`, `register`, `pipe`, `read_sql`, `exec_sql`, `plugin_config`, `write_plugin_config`, `config`. Hosts implement `HostServices::host_call(request, HostCall { plugin, method, pipe, args }, data) -> HostReply { value, data }` (the default serves only the original calls); the loader sets `HostCall::plugin` from the loaded library, never from plugin bytes. Host services are offered on every host path: engine runs (fetch, sync, hooks, `subscribe` and each stream batch), CLI actions, `setup`, a connector's `register` hook, every native executor method, API routes, MCP entries (stdio has local trust), console pages and the Python façade's native connector calls. In API contexts each call runs for the caller (`NativeRouteRequest.caller`, MCP's `Caller.principal`, a page viewer's user, who gets exactly the scopes `/login` would grant): reads need `pipes:read`, `sync` / `clear` / `register` `pipes:write`, `read_sql` `sql:read` and a read-only query, `exec_sql` the `/actions` rule (`is_user_allowed_to_execute_with`; never under `--secure` for non-administrators, never for anonymous callers), and `config` every scope. `read_sql` and `exec_sql` from API callers refuse text that names internal tables (`mrsm_*`, `_mrsm_*`, the protected tables, functions that read tables named in text, `U&` escapes); pipe calls reach only the instances the server allows and never `mrsm` keys, while SQL calls take any configured `sql:` connector. A route's or page's `host_scopes` add named scopes (never `*`) for every caller. Writes respect protected connectors (§6.5). A command's host calls share the runtime's own `Config` (moved into an `Arc` for the call and handed back), so a compose project's in-process commands use its root; plugin-config writes are a read-modify-write of the `plugins` file that keeps the other plugins' sections as written, are recorded per config directory so later reads in the process read the file, and are absorbed into the Python façade's live config at its next native call.

- The interface is also written as **WIT** (`crates/meerschaum-plugin/wit/plugin.wit`), so the WebAssembly host in §9.5 implements the same contract.

Single-file data plugins use a lightweight, host-generated runtime whose only external
dependencies are Serde and `serde_json`. An optional `mrsm_plugin_invoke_rows_v1` C ABI extension
carries JSON rows and synchronous host callbacks. The host owns frame conversion;
single-file `Frame` is a row container, with no Arrow schema or Polars dependency.
The full Cargo SDK retains typed Arrow interchange for bulk data. Both extensions
retain the v1 metadata table, allocator ownership and panic containment. Generated
plugins share dependency build output and use a low-latency unoptimized profile.
A single file declares actions, connectors, `fetch` / `sync` / `register` / `setup` /
`subscribe`, `#[pre_sync_hook]` / `#[post_sync_hook]` functions, `#[add_plugin_argument(...)]`
flags, `#[api_route]` routes, `#[mcp_tool]` / `#[mcp_resource]` / `#[mcp_prompt]` entries,
`#[make_executor]` executor modules, streaming connectors (`fn subscribe` in a connector
module, with an optional `fn ack`), instance connectors (`#[make_connector(instance)]`, whose
functions named after the instance methods answer them), console pages (`#[web_page]`), and its
version and `required` list as `const VERSION` / `const REQUIRED`: everything a packaged plugin
provides. Route paths are checked at generation with the server's rules
(`meerschaum_plugin::api::check_route_path`, kept equal to the server's check by a test). The
generated runtime keeps the stream handle tables and answers
the unserialized stream calls itself; native hook
results are printed like Python hooks' (`(False, "Failed to execute sync hook ...")` for
an error).

### 9.2 Compatibility

- `abi_version` is checked at load time. Breaking the vtable requires `mrsm_plugin_v2`, and the host keeps loading v1 for at least one major release.
- The host and the plugin do not need to share a Rust compiler version. Only `extern "C"` and the Arrow C interfaces cross the boundary.

### 9.3 Distribution

- Plugins live in `MRSM_PLUGINS_DIR` as `<name>/plugin.toml` plus a `lib<name>.{so,dylib,dll}`.
- The plugin repository stores **per-target-triple artifacts** plus a source tarball. On install, the matching triple is downloaded; if none matches, the plugin is built with `cargo build --release` when a toolchain is available.
- A plugin directory that is a Cargo crate (`plugin.toml`, `Cargo.toml`, `src/`) with no up-to-date library is a **source plugin**: when `cargo` is on `PATH`, Meerschaum builds it with `cargo build --release` into `<root>/cache/native_build/<name>` and loads the library from there, rebuilding only when the source fingerprint changes. Without `cargo` it is skipped with a warning; the prebuilt library remains the contract for the slim image.
- Python plugins are unchanged, including `required` with `plugin:name@api:repo` entries, `.mrsm_origins.json`, and multi-directory `plugins_dir`. A plugin directory may contain both kinds; Rust entry points take precedence (R9), and a same-name native plugin replaces the entire Python plugin. Gradual adoption therefore uses a differently named native plugin for selected fetch/sync/connectors/hooks/actions beside the Python one (a synthetic hybrid example ships in the docs); Python Dash plugins stay supported.
- The Python `Plugin` class recognizes a directory with `plugin.toml` as a Rust plugin and delegates to `_core`, so `show plugins`, `install plugin` and `register plugin` treat both kinds uniformly.

### 9.4 Rust plugins inside a Python host

`meerschaum._core` loads Rust plugins itself, so Python users can sync Rust-plugin pipes without the CLI.

### 9.5 WebAssembly (v5.x)

A wasmtime component host for the same WIT interface, for sandboxed, capability-limited plugins. Data crosses as Arrow IPC buffers, which means a copy.

## 10. Kernel, geometry and parity (goal 2)

### 10.1 Kernel

- `meerschaum-kernel` implements, on Arrow and Polars: the dtype system (Meerschaum dtype strings ↔ Arrow types ↔ DB types); `enforce_dtypes`; the `filter_existing` diff (anti-join plus a value comparison keyed on the index columns, with the partial-row update semantics preserved); serialization for json, uuid, numeric, bytes, date and geometry; `query_df` with the `_` negation grammar.
- **Geometry (D10).** Canonical storage is the GeoArrow `geoarrow.wkb` extension type with the CRS from the `geometry[...]` dtype. `as_polars=True` returns GeoPolars when installed, else Binary WKB with CRS metadata. **The pandas path returns a GeoDataFrame with `.crs` set**, as today, because corpora call `.to_crs`, `.dissolve`, `.sindex`, `.force_2d`, `.to_json(to_wgs84=True)` on it. Rust uses the `geoarrow` and `geo` crates. If GeoPolars has not released by 5.0, the WKB path ships anyway.

### 10.2 Reference harness and parity gate

With no Python core in the package (D14), parity is measured against **v4.1.x installed in a separate venv in CI**:

- The full pytest suite runs against the v5 package on every flavor in `tests/connectors.py`. Tests that assert on exact messages are updated; tests that assert on data, schema, counts and return shapes are not.
- **Golden SQL tests** snapshot the exact query text the Rust connector emits for each flavor and each pipe shape (upsert, partitioned, integer axis, no datetime, geometry, autoincrement, autotime) and diff it against what v4.1 emits for the same pipe. Differences must be explained in the snapshot file.
- **Golden dtype tests** diff kernel output against v4.1 output for every dtype in `utils/dtypes`, including `large_string[pyarrow]` versus `string`.
- **Corpus replays** (§11.3) run on every pre-release.

  - `start pipeline` starts saved Pipelines' jobs; action chains serialize under the hidden `chain` action, and v4's `start pipeline ... -P` form still runs.
  - Every root uses the systemd executor when available (§6.4); `copy pipes` fails when any pipe fails; `compose up` checks job ownership before registering anything; `mrsm python <file>` passes every later word to the script; `start api` supports native HTTPS when a key/certificate pair is supplied.

  - Permissions fail closed (`503`), and the Valkey connector's user reads raise `ConnectionError` on a failed read.
  - The v5-only routes (`/pipelines*`, `/engine/*`, `/execute*`) share one response shape (§7.1); v4's routes are unchanged.

## 12. Python package after v5

The `meerschaum` wheel contains: the `_core` extension module; the façade (`Pipe`, connectors, config, users, tokens, actions dispatch, `parse_arguments`); the plugin SDK (§4.4); the API host and `meerschaum.api` surface (§7.3); the Dash console and `meerschaum.api.dash` surface (§8); the MCP SDK; the worker (`meerschaum.worker`). It provides the `mrsm` command itself (D8) and depends on **nothing else** (§12.1).

- **Floor: 3.11** (D6). `abi3-py311` wheels; CI covers 3.11 through 3.15.
- **Lazy imports (PEP 810, Python 3.15).** Adopt `__lazy_modules__` in SDK modules after confirming the mechanism against the final PEP text and the 3.15.0 release. `attempt_import(lazy=True)` keeps working as the pre-3.15 mechanism.
- Free-threaded wheels (3.14t/3.15t) ship as **experimental** (R8): `_core` declares `gil_used = false`; the pandas paths of the façade hold a lock because pandas is not free-threading safe.
- **SDK additions (D26).**
  - `meerschaum.utils.cache` (`cache = Cache()`): `@cache(ttl=300, pipes=[...])` keys a function's results by its arguments, and `get` / `set` / `delete` / `clear` work by key. Values live in Valkey through `api.cache.connector` (default `valkey:main`; the first lookup probes, later re-probes run in the background) when it answers, else in a thread-safe LRU bounded by entries and bytes. Entries are versioned text (`header JSON\npayload`; base64 for binary, because the Rust Valkey binding stores UTF-8 text) holding JSON, tagged dates, `Decimal`, `UUID`, bytes and pandas or Polars frames (Arrow IPC), never pickle. An entry stores each listed pipe's version (`get_sync_status()['last_success']`, else `get_sync_time()`), so a recorded sync makes it stale. The API host warns once at startup when a plugin uses the cache and the connector does not answer.
  - `meerschaum.testing`, a pytest plugin: `mrsm_root` (an in-process root swap: every `MRSM_*` variable and `TMUX` / `TMUX_PANE` set aside, `paths.set_root`, config and plugins directories, venvs, a fresh config store, the connector cache cleared and plugin registries unloaded, all restored at session end), `mrsm_instance` (a SQLite `sql:test` per test, the default instance for subprocesses too), `mrsm_pipe(...)`, `mrsm_api` (the API host in the test process with a `TestClient`, users, sessions and tokens) and `render_page(path, as_user=...)`.
  - `from meerschaum.api import session_user, optional_session_user, mount_static` (§7.3); `@web_callback`, `@dash_plugin(public=True)`, `@web_page(theme=, head=, navbar=)` and `add_head()` (§8.3, §8.4); `@make_action(name='weather wait')` (a string first argument works too; words may use hyphens, not underscores, because v4's `remove_leading_action` rewrites a word with `_`; a collision warns and keeps the existing action); `meerschaum.connectors.allow_protected()` (§6.5); `meerschaum.utils.formatting.ansi_allowed()` (§4.3).

### 12.1 Dependencies (D20)

**Audit.** v4.1 makes 357 `attempt_import` calls across 79 distinct packages, and `_packages.py` declares 112 install names in 20 groups. On the development machine the shared `mrsm` venv holds 174 distributions and 1.3 GB per Python version: 553 MB declared by Meerschaum's groups and 732 MB pulled in by plugins calling `attempt_import('x')` with the default `venv='mrsm'`. The `bmeares/meerschaum` image is 1.86 GB. Three findings drive the policy below:

1. **Most calls belong to code that moves to Rust.** `rich` (61 calls), `sqlalchemy` (58), `prompt_toolkit` (16), `dateutil` (15), `fastapi` (11), `packaging` (9), `psutil` (8), `dask` (6), `dill`, `daemon`, `watchfiles`, `tornado`, `terminado`, `websockets`, `httpx`, `valkey`, `jose`, `fastapi_login`, `uvicorn`, `gunicorn`, `envyaml`, `dotenv`, `semver`, `update_checker`, `pathspec`, `virtualenv`, `binaryornot`, `more_itertools`, `aiofiles`, `certifi`, `dataclass_wizard`, `humanfriendly`, `tabulate`, `asciitree`, `pprintpp`, `more_termcolor`, `colorama`, `pygments`: the module that imports each of these is in the §6.1 port table. They are deleted from the Python package, not kept as optional.
2. **`dask[complete]` is the single largest avoidable dependency.** It pulls `distributed`, `bokeh` (34 MB), `lz4`, `jinja2` and `cloudpickle` into every `[sql]` install for a chunking path that corpora never use and that the Rust kernel replaces with streaming record batches. The `drivers` group installs three PostgreSQL drivers (`psycopg`, `psycopg2-binary`, `asyncpg`) plus `databases`, `aiosqlite` and `aiomysql` for async paths that move to Rust.
3. **The default venv is a dumping ground.** Corpus plugins make 290 default-venv `attempt_import` calls across 16 packages. `pandas` (115), `dash` (64), `requests` (34), `plotly` (27), `dash_bootstrap_components` (23) and `geopandas` (12) are the bulk; `PIL`, `pypdf`, `pyogrio`, `markdown` and `icalendar` are packages Meerschaum never declared that now live in the shared venv because a plugin asked for them there. Plugins rely on `[dash]` having installed `dash_bootstrap_components` for them.

**Policy.**

- **The base wheel has no runtime dependencies.** YAML, HTTP, formatting, prompting, scheduling, venv creation and version checks are Rust. `pprint`, `print_tuple`, `print_options`, `prompt`, `yes_no` and `wget` in the SDK call into `_core` (prompts from a plugin action running in a worker are forwarded over the worker RPC and rendered by the Rust host, which owns the TTY). `importlib_metadata` and `typing_extensions` are stdlib on 3.11. The `_core` extension embeds Polars and Arrow, so `get_data(as_docs=True)`, `pipe.sync(list_of_dicts)` and plugins that return dicts need no data library in Python.
- **Extras**, each importing its framework only when used:

  | Extra | Contents | Replaces |
  |---|---|---|
  | `[pandas]` | `pandas`, `pyarrow` | pandas inputs and outputs, including the compatibility pin on upgraded roots |
  | `[polars]` | `polars` | new-root default outputs and Polars inputs; no pandas dependency |

  | `[gui]` | `pywebview` | `gui` group (excluded from `[full]` from now on) |
  | `[full]` | `[pandas,polars,geo,sql,api,dash,shell]` | `full` |

What changes is accounting: every install into a venv records the requesting plugin (or `meerschaum` for an extra) in `venvs/<name>/.mrsm_requests.json`; `mrsm show venvs` lists venvs with their size and per-package requesters; `mrsm prune venvs` removes packages no installed plugin or extra requests (with `--dry`); and the manifest builder (§4.3) warns when a plugin calls `attempt_import('x')` for a package that is neither in its `required` list nor provided by an installed extra. - **Docker** (D25). `bmeares/meerschaum` publishes `rust` (the native binary, no Python, at most 250 MB), `rust-full` (+ Cargo/rustc and native build tools, at most 1600 MB), `slim` / `minimal` (the base wheel, no extras or compiler, at most 250 MB) and `full` / `latest` / deprecated `api` (the native binary, the Python SDK with every extra and both language toolchains, at most 2500 MB); sizes are uncompressed and enforced by `scripts/docker/size_gate.sh` on every release build. ## 14. Test strategy

- **Parity gate** (§10.2) on every flavor in `tests/connectors.py`, with v4.1.x as the reference. Rust-only behavior gets Rust unit tests in its crate; behavior visible from Python gets a pytest test as well.
- **Corpus replays** (§11.3) in CI on private checkouts, from a2 on.
- **Planner golden tests.** JSON graph fixtures (`crates/meerschaum-engine/tests/fixtures/`) with the expected plan table checked in: a diamond, a cross-instance edge, an aggregate child, an integer-axis parent under a datetime child, a stream source, a cycle, a pipe without a datetime column, a stale reference, and corpus B's six-level chain.
- **Crash injection** between the ledger write and the data commit, and between the data commit and the cursor advance.
- **Lease contention** across processes on each instance type.
- **Stream tests** against a local Mosquitto container under QoS 1 with redelivery and a forced crash mid-flush, through both the `subscribe` path and the v4-pattern adapter path.
- **Server contract tests.** The recorded request/response pairs of every v4.1 route, replayed against the Rust server; websocket log streaming; webterm; proxying of plugin routes, middleware, static mounts and websockets through the API host.
- **Console tests.** Playwright (`tests/console`, opt-in) against every Dash console page, the pipelines page, Exec through the server, page-contract pages from a Python and a Rust plugin (in their frame) and a plugin Dash page, including the login round trip, the rc1 `/dash/<plugin>/` redirects, the pointer page without Dash, and session sharing between the console and an API plugin; `tests/api_host` covers the host and console support in process.
- **Pipelines and workspace (D24).** Registered Pipelines: cross-instance exact identities, duplicate Pipe triples, shared membership, missing instances, tag approval and rejection, partial failures, stale proposals, renames and schedule references; every Pipeline action is discoverable and manageable from the native CLI without Python. Compose: conventional, custom and included filenames. Browser checks (synthetic fixtures): immediate selection feedback and stale responses, fullscreen, pan without text selection, builder edits, single-Pipe sync, node-local output close/reopen, symlink toggles, observed-time rendering, Pipeline cards, exactly-once Exec, dynamic layouts, desktop and mobile Run now, deep-linked history hydration and reload, a second execution after viewing history, and canceled/confirmed Pipeline deletion. Jobs stay usable under many automatic runs and cleanup happens without another request. Custom login and route disabling are tested with synthetic fixtures and validated privately against both corpora.
- **Argument parity.** CI diffs the clap JSON schema against v4.1's parser, everything but `help` (D26). The help fixtures (`crates/meerschaum-cli/tests/fixtures/help/*.txt`) are checked for coverage, not byte equality: every v4 option is listed in `--help`, and every recorded page still has help mentioning the flags its v4 page mentioned (`show data --gui` is the documented exception).
- **Plugin tests.** Plugin authors test with the `meerschaum.testing` pytest plugin (§12), which the repository's own tests exercise through `pytester`.
- **Benchmarks.** A fixed sync benchmark set runs on each pre-release against v4.1. Regressions block the RC.

## 15. Risks

- **Scope.** About 74,000 lines of Python are rewritten in one release with no shipped fallback. Mitigations: the kernel-first train with exit criteria per pre-release, the reference harness against v4.1, corpus replays from a2, and the fact that v4.1.x stays installable and supported for security fixes until 5.1 ships. If a3 slips by more than a quarter, the fallback is a longer alpha series, not a smaller 5.0; the clean break is the point.
- **Façade fidelity.** Plugins depend on live dicts, private attributes, duck typing and SQLAlchemy objects. Mitigation: D16 keeps explicit SQLAlchemy engines and compiles SQLAlchemy constructs at the native SQL boundary, the preserved-behaviors list in §4.4, and the corpus replays.
- **Extension host.** One proxied Python process adds failure modes (host crash, socket permissions, startup order, websocket proxying). Mitigation: the host is supervised like a job, starts only when needed, and is covered by server contract and Playwright tests. Plugins that wrapped core routes with middleware lose that ability; §11.2 documents it. Core Dash pages are patchable again (D21), and Dash version churn is the console's to track (the `dash` extra sets a floor).
- **Driver coverage.** `sqlx`, `tiberius`, `oracle` and `duckdb` do not match SQLAlchemy's dialect coverage in every corner. Mitigation: the row-batch fallback, the SQL golden tests, and Oracle's Instant Client requirement being the same as today's.
- **GeoPackage.** Writing valid GeoPackage files (metadata tables, R-tree triggers) in Rust is new work with no prior art in the codebase. Mitigation: a2 ships it with corpus B's GeoPackage instances as the acceptance test.
- **Wheel build matrix and Windows** (named pipes for workers, plugin `.dll` loading, `tiberius` TLS, PTY for webterm). Set up CI in a1.
- **Engine metadata load on instances.** Mitigation: the engine-state write path and its two-statement cost target.
- **Crate names on crates.io.** Check and reserve `meerschaum`, `meerschaum-*` and `mrsm` early.

## 16. Resolved questions

- **R1.** A bare `pipe.sync()` keeps v4 behavior: no capping and no graph traversal.
- **R2 (revised 2026-10-12).** On an `api:` instance, pipelines run on the client. Engine state travels over a dedicated `/engine` route family because the server refuses `mrsm` pipes over the generic routes.
- **R3.** The `+` and `:` syntax is preserved unchanged.
- **R4.** The `rust` branch was triaged on 2026-10-11; everything on it is already on `main`. Nothing needs to be kept.
- **R5.** No local engine database. Engine state lives on the instance as internal `temporary` pipes; leases use one optional `InstanceConnector` method pair with a file-lock fallback.
- **R6.** Chunk-level overlap is off by default (`system.engine.chunk_pipelining`, `--chunk-pipelining`).
- **R7.** Implicit `{{ Pipe() }}` edges are on by default (`system.engine.implicit_edges: true`); one corpus relies on them exclusively.
- **R8 (revised).** Free-threaded wheels ship in 5.0 as experimental.
- **R9.** When a plugin ships both Rust and Python entry points, Rust takes precedence.
- **R10.** The language bridge is inverted (D12).
- **R11.** The planner's primary signal is the edge cursor, not a watermark comparison.
- **R12.** `rebuild` clears before re-syncing and never blocks a non-interactive run.
- **R13.** Persisted engine state keys on `pipe_ref`, not `pipe_id`.
- **R14 (2026-10-12).** v5 is a clean break: the Python core is removed from the package, the server is Rust (and the console was, until D21), and there is no v6 to finish the port. Python survives as SDK, façade and the API host.
- **R15 (2026-10-12).** `@api_plugin` runs in the proxied Python API host, not in Rust, because it is a Python object bound to FastAPI. `@dash_plugin` runs as a plugin-owned Dash app mounted inside that same host (superseded by D21: it registers into the one console app). Rust plugins get native `routes` and `pages` instead.
- **R16 (revised).** User SQL from Python (`read`, `exec`, `exec_queries`, `value`, `to_sql`) uses the Rust connector for every flavor; SQLAlchemy constructs compile at the boundary. `.engine`, caller-provided SQLAlchemy connections, and helpers that return SQLAlchemy `Table` objects remain optional SQLAlchemy integrations.
- **R17 (2026-10-12).** All twelve SQL flavors ship Rust drivers in 5.0, including GeoPackage (a live instance flavor in corpus B) and Oracle with its Instant Client requirement.
- **R18 (2026-10-12).** Plotly figure JSON is the charting contract (D19). It is language-neutral, the ecosystem already emits it, and a Rust crate exists; ECharts's advantages do not pay for rewriting every existing figure. MapLibre GL JS covers maps.
- **R20 (2026-10-12).** Dependencies were audited call by call (357 `attempt_import` calls, 79 packages, 20 groups). Everything imported only by code that moves to Rust is deleted; the base wheel depends on nothing; `dask`, duplicate PostgreSQL drivers and the console-only Dash components leave the extras; plugin installs into the shared venv become attributed and prunable (D20, §12.1).
- **R19 (2026-10-12).** The Meerschaum-owned Dash host is dropped. The FastAPI host is cheap, stable and has a Rust successor; a Dash host shares the `/dash` prefix, replicates Dash internals and has none. Dash plugins instead own their app, mounted in the API host under `/dash/<plugin>/` with the core stores pre-populated by a shim (§8.4). *(Superseded by D21: the console is Dash again and plugins register into it.)* This resolves the former Q12: a `@web_page` that returns HTML is the native page model (§8.3), and Dash is the legacy mode.

# Meerschaum v5.0.0rc6 specification addendum

Date: 2026-10-21

Status: **Approved for implementation.** This addendum incorporates the user's decisions
following Astra's design review. It revises D4 and the CLI, console, extension-host, and release
contracts in [the v5 spec](v5.0.0.md). These requirements take precedence over conflicting older
text. Implementation and validation status must be reported separately from this specification.

## 1. Registered Pipelines and membership

Pipelines are registered on instances just like Pipes. Their registrations own their names,
identities, exact target references, traversal settings, execution defaults, and revisions.
A member reference includes its own instance keys; selecting the Pipeline registry with `-i`
never rebinds its members. Preserve existing saved definitions during migration. Pipeline names
are unique within a registry; identical names on different registries are distinct Pipelines.

The implicit Pipe dependency graph remains authoritative for dependencies. A Pipeline is a
persisted selection over that graph, not a second dependency graph. Multiple Pipelines may
share a Pipe. Record the resolved selection and definition revision for each admitted run;
subsequent edits affect subsequent runs. Preserve shared-Pipe synchronization protections.

Missing instances, credentials, or members are visible errors, never silently omitted targets.
Changes across instances report partial failures rather than promising atomic rollback.
Definitions contain connector references, not credentials. Schema/revision migration preserves
existing target references and schedules.

## 2. Pipeline analysis and approval of tags

Use `pipeline-{name}` as the tag on explicit members and detected traversal pipes. This is
separate from Compose's unprefixed project-name tag. Tags are indexes; editing a tag alone does
not rewrite a Pipeline's registration. Track ownership so same-name Pipelines on different
registries, pre-existing tags, and overlapping membership cannot cause wrongful tag removal.

`show pipelines` reads registered state only. `analyze pipelines [NAME ...]` performs the more
expensive graph work: resolve exact members and configured traversal, detect missing/unavailable
references and cycles, identify shared members, and compare actual tags with expected tags.
Present discovered pipes, their instances, why they are included, and the proposed tag changes.

Tagging requires user approval in the CLI or Pipelines page. Analysis first prints its findings
and then offers to edit Pipe tags; explicit `--yes` may approve the displayed proposal in batch
mode. Noninteractive analysis without explicit approval reports only. No discovery, page load,
read-only plan, or ordinary sync silently applies tags. Save/edit can offer analysis and approval
but may not hide the mutation in a save operation. Informational notices for untagged pipes tell
the user to run `analyze pipelines` to detect traversals and approve editing Pipe tags.

The Pipelines page exposes Analyze and an explicit Apply tags confirmation for the same findings.
Re-resolve before applying a stale proposal and require renewed approval if its targets changed.
Only fully resolved analysis can propose removing stale owned associations; failed reads keep
reconciliation pending. Failed writes report individual pipes and support retry. Deleting or
renaming a Pipeline removes only associations it owns, preserving pre-existing or still-owned
tags. Deleting a Pipeline preserves its member registrations and data.

Opening the Pipelines page does not automatically register discovered connected components.
Offer them as suggestions that the user may explicitly save.

## 3. CLI contract

Expose `pipelines` consistently in action discovery, help, contextual completion, the Python
façade, and API discovery. Preserve singular aliases. Do not hide additive v5 actions to match
v4 fixture listings. Complete names from the selected registry.

| Action | Behavior |
| --- | --- |
| `show pipelines [NAME ...]` | Read registered definitions, membership, registry/instance counts, and available status without discovery or edits. |
| `analyze pipelines [NAME ...]` | Resolve dependencies and traversal, diagnose issues, preview tag changes, and offer approved repairs as described above. |
| `bootstrap pipelines NAME` | Guided creation from existing pipes or a new-Pipe registration flow. |
| `register pipelines NAME` | Create/import a versioned definition without accidental overwrite. |
| `edit pipelines NAME` | Edit membership, traversal, name, description, and defaults; validate revisions. |
| `plan pipelines NAME` | Read-only preview of resolved actions, dependencies, and bounds. |
| `sync pipelines NAME ...` | Execute resolved selections with existing bounds/workers/retries/force options and report run IDs. Deduplicate identical member references for a combined selection. |
| `delete pipelines NAME` | Delete the definition and owned tag associations, preserving Pipe data and history. Refuse deletion while scheduled Jobs refer to it until removed or reassigned. |
| `drop pipelines NAME` | Apply existing drop-Pipe semantics to explicit members, preserving registrations and the definition. |
| `clear pipelines NAME` | Apply bounded clear-Pipe semantics to explicit members. |
| `copy pipelines NAME NEW_NAME` | Copy the definition, referencing the same pipes, with a new identity. |

For drop/clear, freeze and preview the exact targets, instances, and shared membership before the
normal destructive-action confirmation. Do not inherit traversal implicitly. Report per-Pipe
results. Copying a definition does not copy data. Import/export uses the same definition schema.
Use existing run/history/log commands with Pipeline, run, and Pipe filtering. Scheduling remains
an ordinary Job referencing the registered Pipeline; start/stop/pause acts on named Jobs and
cancellation acts on a specific execution, never ambiguously on every Job sharing a Pipeline.

## 4. Compose project naming

An explicit/effective `project_name`, including the existing environment substitution, wins.
Otherwise, custom filenames default to their filename without the final `.yaml` or `.yml` suffix.
Conventional `mrsm-compose.yaml` and `mrsm-compose.yml` retain the containing directory name.
Preserve dots in that directory name rather than stripping its suffix. Each included file derives
its own name from its own path. Duplicate names in a composition remain a validation error.
Examples: `/acme/metrics.yaml` becomes `metrics`; `/acme/mrsm-compose.yaml` becomes `acme`.
Compose continues to use its unprefixed project-name tags. Document the changed implicit identity
for existing custom-named files and recommend explicit names when preserving an old identity.

## 5. Interactive Pipelines workspace

Fullscreen includes the canvas, inspector, menus, and output dock. Escape restores the previous
view, preserving zoom, pan, selection, and dock state. Dragging must not select page text or cause
an accidental node click. Query and output text remain selectable. Provide keyboard/touch
alternatives to context menus.

Background right-click/Add offers an instance-aware existing-Pipe picker and new-Pipe registration.
Node menus and the inspector offer Sync this Pipe and explicitly scoped parent/child choices.
A single-Pipe run uses the same execution protocol without pretending to execute the whole
Pipeline. Show scope and bounds for expanded operations. Node status includes queued, running,
succeeded, failed, skipped, and blocked.

Open an inspector shell and highlight selection immediately; load expensive sections lazily.
Associate responses with selection IDs so stale results cannot overwrite the current inspector.
Offer section-level retry. Query has the existing Pipe card's Resolve symlinks toggle with the
same defaults and errors, resolving references in the correct instance context. It changes only
the displayed SQL. Add direct sync controls to the inspector.

Use draft Save/Discard for membership and dependency edits, with revision conflict detection,
unsaved-change indicators, and undo/redo for draft changes. Saved layouts are shared metadata;
viewport state is personal. Add search/center, fit selection, instance badges, group collapse,
status filters, and multi-selection. Keep historical runs distinct from current editable state.

Editing an edge edits real shared Pipe facts and previews which Pipes change. Validate cycles.
Distinguish explicit parent/child declarations from inferred query references. Removing an
inferred edge requires editing its query/reference. Removing a node removes membership;
dropping data/deleting the Pipe are separately named actions. Do not create meaningless arrows.

Canvas-local output tabs identify the run and fully qualified Pipe and remain available after
completion. Attribute concurrent output by run, Pipe, attempt, and sequence at emission time;
never infer ownership by matching interleaved text. Keep a stable selected run while inspecting
logs. Cancellation targets a run; never interrupt unrelated work.

## 6. Plan and actual Timeline

Plan displays dependency order, readiness, planned actions, bounds, and relevant worker limits.
It has no required time axis. Optional forecasts label historical versus default estimates and
their provenance. Existing engine priority estimates may remain internal. Their current defaults
are a per-Pipe/action exponentially weighted average (alpha 0.3), any-action history fallback,
and then 30 seconds; CPM does not account for worker/semaphore contention.

Timeline displays observed starts/finishes, elapsed time, concurrency, retries, and live running
intervals. Distinguish queued time, skipped work, and successful work. Estimated bars are not
the default. Preserve existing history fields and snapshot estimates rather than recomputing
old forecasts from newer history. Apply this separation coherently to terminal output as well.
Remove the Plotly image-download control, preserving unrelated data exports.

## 7. Jobs, Runs, and retention

Reuse the Job supervisor but distinguish persistent user-managed Jobs from temporary execution
workers. A manually created one-shot Job remains a Job. Default Jobs views/cards exclude
automatic workers; Runs and their Pipeline expose active and historical automatic executions.

Record kind, origin, owner, Pipeline identity/revision, run ID, parent Job, and retention policy
explicitly; do not infer security or retention solely from the `execute-` prefix. Preserve
compatibility for legacy records. Store Pipeline identity directly rather than parsing run IDs.
Retain automatic successful output for 24 hours, failed output for 7 days, and run summaries for
30 days, configurable. Prune at startup and in the background without needing a new execution.
Never expire active work. Preserve retained output links independently of worker cleanup and
allow a temporary execution to be retained/promoted into a persistent Job.

## 8. Console and terminal behavior

Add Pipeline cards exposing name, registry, member/instance counts, health, latest execution,
schedules, and Open/Plan/Sync/manage controls. Put Pipelines in Term's current button position,
with a smaller Term button to its right. Reuse the same Pipeline and execution services.

Exec submits the composed command exactly once into the existing webterm iframe and keeps it
mounted. Preserve quoting and selected-instance behavior. Use terminal readiness/acknowledgment;
disconnected or busy sessions show a clear state rather than blindly interrupting or replaying
commands. Do not also start a second execution from another callback. Keep authorization aligned.

Fix the missing filter Input error during direct single-Pipe navigation, page switching, and
authentication changes. Scope callbacks to their layouts or use genuinely optional Inputs with
guards; suppressing layout validation alone does not fix missing runtime Inputs.

## 9. Interactive SQL

Rainfrog is approved as the preferred external Rust TUI for supported flavors. Provide
configurable per-flavor client preferences, keep Python clients as explicit choices/fallbacks,
and make `--nopretty` force the plain flavor client. If a preferred executable is missing, provide
a documented fallback and installation guidance. Do not put credentials in argv.

Verify launch arguments, TLS/connection settings, terminal restoration, exit behavior, and Web
Terminal use. Rainfrog's documented support is PostgreSQL, MySQL, SQLite, DuckDB, and Oracle;
Oracle requires client libraries and some targets omit DuckDB. Keep existing MSSQL choices.
Reference: [Rainfrog upstream](https://github.com/achristmascarl/rainfrog).

## 10. Custom applications and native plugins

Preserve `web_page('login', ...)` overrides, custom Dash callbacks, sessions, redirects, and
sign-out in the one shared Dash app. Namespaced API login remains supported through the host.
Python `app.router.routes` mutations cannot remove native Rust endpoints.

For rc6 provide explicit disabling of native login/core route groups, document migration away
from Python route stripping, and test the effective external endpoint surface. A disabled route
must not reappear through host fallback. Exact method/path core-route replacement by plugins is
deferred; document that limit rather than claiming parity with arbitrary FastAPI mutation.

Keep Python Dash plugins supported. Gradual Rust adoption uses a differently named native
plugin for selected fetch/sync/connectors/hooks/actions; a same-name native plugin replaces the
entire Python plugin. Native HTML pages do not run Python Dash callbacks. Provide a synthetic
hybrid migration example and document the native HTTP adapter's current limits: parameterized
paths, reserved namespaces, scoped principal context, headers/cookies, redirects, and binary
responses require an audit before promising an API-plugin rewrite. Corpus identities remain
private in public docs and fixtures.

## 11. Acceptance and release

Exercise cross-instance exact identities, duplicate Pipe triples, shared membership, missing
instances, tag approval/rejection, partial failures, stale proposals, renames, and schedule
references. Verify all supported Pipeline actions are discoverable and native CLI management
works without a Python-only core. Test conventional/custom/included Compose filenames.

Browser checks cover immediate selection feedback and stale responses, fullscreen, pan without
text selection, builder edits, individual sync, node-local output, symlink toggles, actual-time
rendering, Pipeline cards, exactly-once Exec, and dynamic layouts. Verify Jobs remain usable
under many automatic runs and cleanup happens without another request. Test custom login and
route disabling with synthetic fixtures and privately validate both compatibility corpora.

Release `5.0.0rc6` / Cargo `5.0.0-rc.6` from `v5` after local checks and full exact-commit CI.
The user authorizes implementation, delegation, release commits/branch push, PyPI, crates.io,
the annotated git tag, GitHub prerelease, and DockerHub version-qualified images. Prerelease
artifacts are Linux x86_64; do not move stable/latest Docker tags. Follow the release skill's
packaging, publication dry-run, artifact verification, and smoke checks. Never publish a failed
or unvalidated release. Report any remaining limitation rather than silently omitting scope.
